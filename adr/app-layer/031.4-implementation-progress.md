## Deviations

Each entry names the ADR text it changes, why, and the commit that carries both.

1. **Unamended structures keep their bytes (§1.9, §5.8).** A document without rules and a
   receipt whose steps record no rule failure contain no structure this ADR amends, so they
   encode exactly as before and decode identically; `ir.forward`, `receipt.accepted`,
   `receipt.rejected`, `expression.threshold` and `expression.fact-role` are byte-identical.
   No byte string is read differently by the two layouts, which is the property the in-place
   rule protects. Every amended structure (a rule, a rule failure) changes its arity and fails
   decode in its old form. The ADR's §5.8 now says so precisely, as ADR-031.3 deviation 13 did.
2. **CDDL spelling and the pinned validator (Phase 0).** `cddl-cli` 0.10.5 accepts any array for
   a member typed as a choice between a choice of arrays and `null`, so `rule-trace` is spelled
   as two named alternatives (`rule-trace-held`, `rule-trace-failed`); that spelling also states
   the Java invariant that a failure cannot follow 16 held rules. The validator also checks only
   the first element of a keyed repetition (a second step of `"garbage"` passes), so the
   pre-ADR two-step `receipt.derived-denied` is checked through its failed step alone. Because
   the validator does not anchor regular expressions or enforce array upper bounds, a namespace
   such as `Holders` or `1x`, and a rule with five reads, pass it; the Java codecs enforce those
   grammars and bounds, and the codec tests cover multi-step receipts. This extends ADR-031.3
   deviation 11.
3. **`startsWith` and `size` are ordinary dialect operators (§5.2).** The ADR did not say where
   they are legal. They are pure text/bytes operators with no rule-only input, so they are
   legal in binding conditions and mappings as well as rules, and CEL's member form
   `a.startsWith(b)` lowers to the same operator.
4. **Grammars (§5.1, §5.7).** Read names and view field names are CEL identifiers (they are
   selected as `reads.<name>.<field>` and `w.<field>`), excluding CEL reserved words; reads are
   sorted by name like parameters. A namespace is `""` or the map's collection-id grammar
   `[a-z0-9][a-z0-9._-]{0,63}`. `present` is reserved for plain fields only: value fields may use
   any name, including `present` and `value`, because the `value.` prefix keeps them apart, so a
   map schema member named `present` stays exposable (Phase 1 review). A view with value fields
   cannot also declare a plain field named `value`, so `reads.x.value` and `reads.x.value.f` never
   collide.
5. **Which write decided (§5.2, §5.5).** The ADR said `writeIndex` names the element that decided
   an `all` or raised an error. The frozen definition is "the element at which the failing
   clause's most recently completed quantifier stopped early" (the first `false` of `all`, the
   first `true` of `exists`, or an error), and `null` when that quantifier ran to completion or
   none ran. So `!writes.exists(…)` also names the write that refused it. A failure before any
   clause has no index.
6. **Write-element value fields (§5.2, §5.6, §5.7).** `value.<f>` on a write element is typed
   through the kernel's value views: it is declared when some view declares value field `f` and
   every view that declares it agrees on the type, and an element carries only such fields (a
   kernel omits a conflicting member). This keeps the host contract to the seven methods of §5.7
   (no separate write value-field method) while typing `w.value.price` statically. Bounds are now
   stated: at most 64 entries in one decoded read or write element (32 fields plus 32 value
   fields), and at most 64 × 32 names in the union used for typing.
7. **Read-time failures (§5.5).** Reads run before the clauses, so a read that fails before any
   clause (key build or `ruleValueKey` rejection, declaration violation, exhausted work)
   records clause `-1`, like the ADR-031.3 input failures.
8. **Host value conventions (§5.4, §5.7).** `ruleValueFields` and `ruleWrites` use flat keys,
   with value fields as `value.<name>` (a `RuleFact` name cannot contain a dot, so this is
   unambiguous). `ruleValueKey` signals an unacceptable namespace or key with
   `IllegalArgumentException`, which the engine turns into `ADMISSION_RULE_ERROR` as it does for
   `lookupKey`; every other exception propagates (ADR-031.3 deviation 12). A value that cannot be
   represented in its declared type (an integer outside int64) is returned unchanged and fails
   closed with `ADMISSION_RULE_INPUT`; a record the kernel cannot decode yields no fields, so any
   field read fails closed with `ADMISSION_RULE_ERROR`.
9. **Structured refusal reasons (§5.9, bloxbean/yano#153).** The issue offered parsing the
   `CODE/detail/detail` convention or an explicit overload; the host uses the explicit
   `AdmissionResult.reject(code, details)` overload and does not parse strings. `write` is
   bounded to 0..65535 and accepts every platform integer width. `reject` keeps only text keys with
   `String`, `Long`, `Integer`, `Short` or `Byte` values (Phase 1 review Blocker), so no
   plugin-defined object crosses the plugin boundary inside an `AdmissionResult`. The host adds
   public constants beyond §5.7 and §5.9: `RuleValueView.PRESENT`,
   `AppSubmissionRejectedException.DETAIL_KEYS` (the client order) and `MAX_WRITE_DETAIL`, and
   `AdmissionResult.MAX_DETAILS`. The REST body adds `details` only when a detail survived, so every
   existing body is unchanged. Yano X ingress now passes the bare code as the reason; the CLI
   and dry-run keep printing `CODE/rule/deny` from the details for their users.
10. **Post-state fact table (§5.10, bloxbean/yano-x#25).** Confirmed against each codec: the
    proposed `kv-registry` `ownerIsSender` is dropped because `decide` rejects a non-owner, so it
    would always be `true`; `valueLength` is declared for `put` only; the `approvals` facts are
    absent when the item does not exist after the command.
11. **View fields beyond the proposal (§5.4).** `approvals` adds `payloadHash`, which its stored
    item carries. It does not expose the deadline: rules have no timestamp to compare it with, and
    a stored `PENDING` item may already be past it (`EXPIRED` is written by the next vote). The
    map entry view adds `valueLength`, which §5.6 already assumed ("larger map values expose only
    `valueLength`").
12. **Characterization of ingress refusals (Phase 0).** §5.9 changes the ingress reason string by
    design, so the characterization pins what must not change — the refusal's code, rule and
    deny code — rather than the string. Phase 3 reads them from the details.
13. **Key expressions (§5.1, §5.8; Phase 0 review Blocker).** The first freeze let a read key or
    a lookup key be an expression that read another read or quantified, because key expressions
    reused the rule expression grammar. That is read chaining, which the ADR forbids. The CDDL now
    gives key expressions their own node grammar (`rule-key-node`: no read fields, no
    quantifiers), §5.8 says read fields and quantifiers appear only in rule expression clauses,
    and four negative cases cover both forms in both key positions.
14. **`hasValue` and `RESTORE` (§5.2, §5.4).** A restore installs a validated value
    (`valueBearing` includes `OP_RESTORE`), so `hasValue` is true for `PUT`, `PUT_IF_ABSENT`,
    `COMPARE_AND_SET` and `RESTORE`, by operation rather than by value length, and a restore
    exposes `value.<field>`. Otherwise a rule guarded by `!w.hasValue` could be bypassed by
    restoring an out-of-range value.
15. **Large map schemas (§5.4).** A schema may have 256 top-level members, a view at most 32 value
    fields. The first 32 eligible members in the schema's canonical member order are exposed.
    Integer members are exposed whatever their schema range; a stored value outside int64 fails
    closed with `ADMISSION_RULE_INPUT`.
16. **`index` is engine-defined (§5.2, §5.7).** The engine supplies every element's `index` from
    its position, so no kernel can misreport it; write content fields are never named `index`,
    `value`, or `present`.
17. **Coverage is unique (§5.4).** The ADR said a write covered by both kinds reports `direct`.
    After approval that cannot happen: each mutation has exactly one assignment whose kind equals the
    collection policy, and each evidence item covers exactly its assigned mutations. The ADR now
    says coverage follows the collection policy, and the actor fields are defined only for
    `direct`.
18. **Examples (§6.2).** `TRANSFER_CONTROLLER` is legal only in owner collections, where coverage
    is `none`, so the admin-only example now gates `REVOKE` and `RESTORE` in direct-role collections
    and notes that a transfer can only be forbidden outright.
19. **Phase ordering.** Phase 1 host work was drafted in the Yano working tree while the Phase 0
    review ran, as in ADR-031.3 deviation 16. The Phase 0 gate ran against the unchanged
    `0.1.0-pre18-f92d8b1-SNAPSHOT` in Maven Local, which has no `RuleValueView`.

## Phase 1 — Yano host contract and structured refusal reasons (Yano `feat/adr031-4-rule-views`)

    `MAX_FIELDS` 32 per list, `MAX_WRITES` 128), the namespace grammar, `present` reserved for

- Tests: `RuleValueViewTest` (3), two `TransitionKernelTest` cases, the #153 sanitization cases in
