# ADR-031.1: Declarative Event Bindings for Composite Workflows

## Status

Implemented — experimental; local qualification and release prerequisites are
tracked separately below.

Implementation and qualification evidence is tracked in
[the phase ledger](031.1-implementation-progress.md). Local implementation does
not by itself promote this experimental profile to a public release.

The number is local to the `adr/app-layer` series and marks this decision as a
sub-decision of [ADR-031](031-composable-state-machine-foundation-and-portable-proofs.md).
It supersedes the withdrawn root-level draft "ADR-054: Declarative Composition
of State Machines in Yano X" (2026-09-22), which described a runtime API that
does not exist and conflicted with accepted decisions listed in §4.

Classification: an experimental extension of the `BUNDLED` generic composite runtime
(ADR-022 §4.1). It is `EXPERIMENTAL` until every gate in §12 closes. No public
release has selected the profile schema or contracts defined here. It depends
on additive Yano kernel, descriptor, and event contracts (§9), published as a new Yano
version before a public Yano X preview can consume them. Coordinated local
qualification uses exact locally published Maven artifacts and their matching
ordinary JVM ZIP; it does not substitute for that release prerequisite.

Product intent: the customer of this feature is an external integrator who
assembles an app chain from stock machines without writing Java. The binding
language is therefore sized to real product flows (§12 gate 2), not to demos,
while remaining a closed, bounded, canonical IR rather than a scripting
language. Product-flow qualification below does not imply compatibility with
legacy product certificates or projections that require signed, finalized
command envelopes; see the reviewed boundary in §5.12.

## 1. Decision summary

1.1. Add one stock, generic `CompositeWorkflow`, the **event-binding
workflow**, to `composition/runtime`. Its behaviour is fully determined by a
canonical, bounded **binding table** committed in the composite profile bytes.
It contains no application-specific code.

1.2. Add a stock provider, `declarative-composite`, that assembles a composite
from a compiled binding IR: an ordered list of components, the event-binding
workflow, and typed limits. The resulting profile is canonicalized,
digest-pinned, and written to `~composite/profile/v1` at height 1 exactly as
every composite profile is today.

1.3. Introduce two additive host contracts in the Yano `core-api` transition
package. A **transition kernel**, `TransitionKernel<C,F>`, is the discoverable
form of a plan-form transition: a codec, a facts loader, an admission check,
`decide`, command descriptors, event descriptors, and a configuration
descriptor, exposed through an optional accessor on `AppStateMachine`.
**Transition events** are a bounded `events` list on `TransitionPlan`. A
machine declares events in the same plan that declares its writes. Events
are values inside one transition. They are never messages, never pooled,
never diffused, never signed, and never visible outside the cascade that
produced them. The engine also derives one **baseline event** for every
approving step, so any machine with a kernel is a source with no further
code. Events carry every field an author is likely to compare, including
hashes, lengths, revisions, and post-state values, so conditions rarely
need computation.

1.4. A **binding** maps one `(source component, event id)` pair, under a bounded
condition, to one derived command on a target component or one effect
intent. Bindings execute in declared order, which is committed in the profile
bytes, exactly as workflow order is today. Every component has its own
ingress topic, and the event-binding workflow owns the union of all component
topics through a multi-topic workflow descriptor, so global block order is
preserved across sources and two instances of one machine are distinct.

1.5. A source message and every command derived from it execute as one
**cascade** inside one `apply` call of the event-binding workflow. Each step is
decide-then-plan. Before anything is claimed or committed, the cascade
preflights the effect capacity that all of its plans need against the
workflow's remaining per-block quota. Plans are committed in step order only
after every step approves and the preflight passes. A rejected step, a limit
breach, an effect-capacity shortfall, or a conflicting consumption makes the
whole source message a deterministic per-message no-op with an authenticated
receipt. It never throws.

1.6. **Composability is generic.** Any machine that (a) exposes a transition
kernel, (b) declares events or relies on the baseline event, and
(c) whose command authority can be satisfied by the originator's principal
plus evidence carried in the event, can be a source or a target. This holds
for stock, host-owned, and third-party machines. §5.10 states the rules;
§5.11 states the authority model. The machines named for v1 are the order of
proof, not a boundary.

1.7. Derived commands carry the originator's sender and a distinct derived
message id. They are never re-signed and never re-admitted. Authority passes
through and is never amplified. Evidence such as an approval reference is
copied from the event and verified by the target exactly as for a direct
submission.

1.8. The binding language is a closed IR with bounded constructs:
**conditions** as conjunctions of clauses using equality,
integer comparison, set membership, exists, and absent; **lookup clauses**
that read one exact key from a declared participant's state and compare it;
**mappings** by identity, field copy, literal, or a call into a **versioned
stock function catalog** of pure, total functions such as hash and
concatenate; and **events** that already carry derivable fields. There is no
unrestricted scripting language or user-defined function. An optional
`yano-x-cel-v1` expression profile (§5.13) adds typed boolean expressions,
conditional values, and checked integer arithmetic to conditions and data
mappings. Loops and comprehensions remain excluded. Anything beyond the IR still requires a provider JAR
under ADR-022 §3.15, and v1 is gated on three real product flows needing
nothing beyond it (§12).

1.9. Limits (cascade depth, derived commands per source message, derived
commands per block, lookups per condition, function calls per mapping,
function input bytes, binding count, IR size) are typed fields inside the
canonical profile bytes. They are consensus values, not free configuration.
Attempted derivations are charged to a per-block authenticated counter
whether or not the cascade commits, so a block's work is bounded even when
every cascade fails late.

1.10. The binding graph is validated at profile construction, before a node
participates in consensus. Static cycles between components are rejected in
v1. A binding whose target declares evidence fields that the mapping does not
source from the event is rejected statically. Unknown catalogs, functions,
fields, or types are rejected statically.

1.11. The profile schema version becomes 2. Golden vectors are added. A v1
profile marker remains valid for chains that do not use bindings.

1.12. Binding changes on a running chain are ADR-015 profile-epoch transitions.
A local YAML edit cannot change bindings; the height-1 marker check fails
closed on divergence, as it does for every composite profile today.

1.13. Every cascade writes one authenticated **binding receipt** keyed by the
source message id. The receipt is the failure record, the audit trail, the
dry-run output, and the input for graph tooling. Nothing node-local enters
consensus state.

1.14. Module direction follows ADR-031 §8: the event value type lives in the
host so stock and third-party machines declare events against `core-api`
alone; the binding engine, provider, IR, function catalog, receipts, stdlib
event catalogs, and tooling live in Yano X.

1.15. The authenticated map is on the critical path. Its plan-form refactor,
under a frozen-contract gate, lands in Phase 2, and governed collections
become targets through evidence pass-through in Phase 3, because an
integrator's first binding will involve the map.

1.16. Component configuration is part of the IR. Each component carries a
canonical configuration map validated against the descriptor its kernel
publishes, with defaults normalized before hashing, and its configuration
id is computed from those bytes, never authored. Identical IR therefore
instantiates identical behaviour on every member.

## 2. Context

### 2.1 What exists today

Yano X already provides the non-declarative part of what the withdrawn draft
asked for. All of the following is implemented and frozen:

- `CompositeStateMachine` is an ordinary `AppStateMachine`. It routes messages
  by exact topic to components, then to workflows, all inside one block batch
  (`composition/runtime/.../CompositeStateMachine.java`, `apply`).
- A `CompositeWorkflow` already coordinates several members atomically. It
  reads declared participant views through `CompositeWorkflowContext`,
  synthesizes downstream commands, claims idempotency with `claim`, and
  commits. `ShowcaseReleaseWorkflow` and `DocumentReviewWorkflow` in
  `examples/showcase` are hand-coded instances of exactly the pattern this ADR
  makes declarative: read orders and approvals, compare a payload hash to an
  order hash, build a reference string by concatenation, append to doc-trail,
  emit an effect. Both clone the originator's envelope for the internal
  command. Every construct they use maps to one of the four in §1.8.
- The host publishes a pure decide-then-commit contract:
  `TransitionCapability.decide(command, context, facts)` returns a
  `TransitionDecision` that is either a rejection with a bounded code or an
  immutable `TransitionPlan` of mutations, effects, consumptions, and receipts.
  `kv-registry` and `doc-trail` already use it. The host's own `ordered-log`
  uses it too.
- The composite profile is canonical bytes, SHA-256 digested under a domain
  string, written to `~composite/profile/v1` at height 1, and byte-compared on
  every later transition and on retained-state startup. Governed evolution
  through append-only epochs is implemented (ADR-015).
- Per-component and per-workflow effect quotas, effect ownership records, and
  the CHAIN-result return path exist and are budget-checked at profile
  construction against `effects.max-per-block`.
- A precedent for bounded declarative logic in genesis exists:
  `AuthenticatedMapSchema` is a CDDL subset compiled offline into a capped,
  non-recursive, step-budgeted IR that stock code evaluates as a total
  predicate. Its constants (`MAX_SCHEMA_IR_BYTES`, `MAX_SCHEMA_NODES`,
  `MAX_EVALUATION_STEPS`) are the shape this ADR reuses.
- A precedent for a versioned, reviewed, named pure rule exists: the
  attestation feed's `feed-aggregation-v1` rule id. The function catalog in
  §5.3 generalizes that idea.
- A precedent for the host-versus-Yano-X line exists:
  `AppBlockExecutionContext.routeToMessageIndexes` is a host contract whose
  only consumer is the Yano X composite. Routing primitives live in the host;
  composition policy lives in Yano X.

### 2.2 What is missing

- **No event type exists anywhere.** `apply` returns void. `TransitionPlan`
  has no events list. Only `authenticated-map` writes a structured per-command
  receipt; `approvals`, `kv-registry`, `doc-trail`, and `balances` surface
  nothing a router could consume.
- **No discoverable transition.** `KvRegistryStateMachine` holds its
  `KvRegistryTransitions` as a private field, and `AppStateMachine` exposes
  no codec, facts loader, or `decide`. `TransitionCapability` defines only
  `decide`. A generic engine has nothing to call, and nothing tells it how
  mapped fields become a machine's wire command.
- **No data-driven composition.** Every profile is built in a Java preset and
  selected by one string such as `machines.composite.preset`. Nothing in
  configuration names components or wires them. Component settings such as
  the key/value registry's value format are read from the node's creation
  context, so nothing binds them to the committed profile.
- **No cascade.** Execution is one pass over components, then one pass over
  workflows. There is no depth or fan-out bound and no re-entrancy guard,
  because nothing today can re-enter.
- **No intra-block rollback.** `AppStateWriter` has no savepoint (ADR-031
  §4.3 D). The doctrine is validate everything, then commit; an exception
  aborts the block on every node.
- **No derived-command identity.** The existing helper clones the original
  envelope including the message id. Reusing the id collides with every
  machine that keys receipts or replay state by message id.
- **Three stock machines still write inline.** `approvals`, `balances`, and
  `authenticated-map` mutate the writer during apply instead of returning a
  plan. They cannot be cascade steps until they decide into plans.
- **The draft's machine inventory was partly fictional.** `Register`,
  `Counter`, and `RoleRegistry` do not exist as selectable machines.
  "Approval" names two unrelated implementations, `approvals` (member k-of-n)
  and `role-approvals` (actor-signed, policy clauses), that share no contract.

### 2.3 Why the draft was withdrawn

The draft proposed a "composition runtime" wrapping a `transition()` method
that returns a `TransitionResult`. Neither exists; the single entry point is
`apply(context, writer, effects)` (ADR-031 §6.6). It proposed a command queue
of synthesized internal commands, which ADR-013.1 §6 and ADR-031 §6.3 had
rejected. It failed transitions on downstream rejection, inverting the
per-message no-op rule that keeps admitted messages from poisoning proposer
selection. It re-opened questions that ADR-013.2 and ADR-015 already answer
(profile hashing, ordering, immutability). And it used "route" for an edge
type when "route" already means a topic-to-component binding in the profile.

The underlying goal stands. This ADR restates it inside the existing contract.

## 3. Goals and non-goals

### 3.1 Goals

- Let an external integrator assemble an application from existing machines
  plus a declared binding table, with no Java, for real product flows: gated
  approvals, registry-conditioned actions, audit trails, and effects.
- Make the composition rules generic, so any machine that exposes a
  transition kernel, including host-owned and third-party ones, can
  participate against `core-api` alone.
- Keep every deterministic guarantee of ADR-013.2 and ADR-031: one block, one
  atomic batch, one root; exclusive routes; namespaced views; effect ownership
  and quotas; committed profile identity; governed evolution.
- Never weaken an authorization check. A binding can only cause what the
  originator could do directly, or what a signer already authorized.
- Produce an authenticated, queryable explanation of every cascade, and let an
  integrator obtain the same explanation offline from a dry-run.
- Make the binding table a stable authoring format that a future graph editor
  can emit.

### 3.2 Non-goals

- A general workflow, BPMN, or scripting language. Expressions are restricted
  to the versioned CEL profile in §5.13; no arbitrary Java calls, user-defined
  functions, loops, comprehensions, or implicit access to state are available.
- Pub/sub, listeners, asynchronous delivery, or dynamic registration.
- Cross-chain routing. Bindings are intra-chain (root ADR-047 keeps chains
  independent).
- Result-triggered bindings (effect result to command). Results continue to
  reach the owning component generation through `onEffectResult` (ADR-013.1).
- Producing signatures. A derived command carries only evidence that already
  exists in the event or in declared participant state (§5.11).
- A delegation policy that lets the binding table itself authorize actions
  (§13.5). That is a separate authorization decision.
- Changes to standalone host state-transition semantics. The host additions
  in §9 expose pure kernels and events; the host commit path ignores events.

## 4. Amendment to prior decisions

This ADR changes the following clauses and nothing else. Each change is
narrow and reasoned.

**ADR-022 §17.3 "Allow arbitrary YAML composition — Rejected" and §3.15.**
The rejection targeted unreviewed logic and unordered discovery: "two members
discovering a different order would derive different roots". The binding IR
is not arbitrary YAML. It is a closed, bounded, canonical binary schema
(§5.3), interpreted by one reviewed stock workflow, committed into the
profile bytes, and byte-verified at height 1 and on every transition, so
divergence fails closed instead of forking. Components are named in
declaration order that is itself committed. Every computation available to
an author is a reviewed stock function referenced by id. ADR-025.1 Phase B
already applied this reasoning to value schemas. §3.15 continues to hold for
anything the IR cannot express.

**ADR-021 §12.4 (deferred action list) and §13 (risk).** This ADR is the
composite-profile decision that §13 required. ADR-021's single opaque effect
stays as is for the standalone `approvals` chain. Inside a
`declarative-composite`, effect bindings replace it and the two are mutually
exclusive at profile construction, as `ShowcaseCompositePreset` already
enforces for composite effect ownership.

**ADR-022 §5.3 (a hash is not an executable command).** Adopted. The
role-approvals to governed-map path in §5.11 requires the canonical action
bytes to be staged at propose time under a versioned contract addition,
exactly the "separate explicit contract/profile decision" §5.3 asked for.

**ADR-013.1 §6 and ADR-031 §6.3 (no internal continuation commands, no
synthetic blocks).** Unchanged. Derived commands here are not messages and
not blocks: they are in-memory step inputs inside one workflow `apply`, never
pooled, never certified, never re-entering a later block. The one feedback
loop across blocks remains the effect result callback.

**ADR-013.2 §12 and ADR-025.2 §1.3 (per-message no-ops; approve-then-act
hazard).** Unchanged and adopted (§5.6, §5.7). An approved event fires in the
same atomic transition as the terminal approval that produced it, including
staged-action cleanup and any target-native authorization consumption record.

**ADR-019 §14 (bounded AND clauses, no OR/NOT).** Role-policy clauses remain
unchanged. Binding conditions retain bounded conjunctions and may include a
typed CEL predicate under §5.13. Boolean composition in a binding never
replaces the target's role-policy evaluation or authorizes a command.

**ADR-031 §8 (stock transition capabilities must not depend on composite).**
Unchanged and the reason the event type lives in the host (§9).

## 5. Target architecture

### 5.1 The declarative composite provider

`declarative-composite` is a manifested `app-state-machine` contribution in
the `yano-x-composite` bundle. Its settings are:

| Setting | Meaning |
|---|---|
| `machines.composite.binding-ir` | hex of the compiled binding IR for the genesis profile |
| `machines.composite.binding-ir-catalog[n]` | optional dormant target IRs for ADR-015 governance |
| `machines.composite.profile-mode` | `fixed` or `governed`, unchanged from ADR-015 |

The provider decodes the IR, instantiates each declared component through
the plugin catalog (any manifested `app-state-machine` that satisfies §5.10;
stock machines are simply the ones already in the catalog), registers the
event-binding workflow with the declared bindings and limits, and builds the
profile through `ComposableAppStateMachine.builder`. The workflow's
participant set is every component a binding names as source, target, or
lookup. The profile is schema version 2. Its canonical bytes include the
component list, the workflow descriptor, and the complete IR. Nothing in the
IR is outside the digest.

Because the profile bytes are committed at height 1 and checked on every
transition, every member must hold byte-identical IR. A member with a
different local file fails at startup or at its first block, which is the
fail-closed behaviour ADR-013.2 §6.2 already provides. Chain state remains
the authority (ADR-015 §4.1).

### 5.2 Transition kernels and events

Two additive host contracts in `org.yanoproject.api.appchain.transition`
make a machine composable.

**The transition kernel** is the discoverable form of a plan-form
transition. Today `TransitionCapability` defines only `decide`, and a machine
such as `KvRegistryStateMachine` keeps its capability in a private field; a
generic engine has nothing to call. The kernel adds what the engine needs:

```java
public interface TransitionKernel<C, F> extends TransitionCapability<C, F> {
    MessageCodec<C> codec();                                    // existing host codec contract
    default AdmissionResult admit(C command) { return accept(); }
    default AdmissionResult admit(C command, TransitionContext context) { return admit(command); }
    F facts(C command, TransitionContext context, AppStateReader state);
    default List<String> readParticipants() { return List.of(); }
    // The default accepts an empty participant map and delegates to the local facts overload.
    default F facts(C command, TransitionContext context, AppStateReader state,
                    Map<String, AppStateReader> participants) { ... }
    List<CommandDescriptor> commands();                         // wire layout + field roles, §5.3
    List<EventDescriptor> events();                             // event ids + field schemas
    ConfigurationDescriptor configuration();                    // accepted settings + defaults, §5.3
}
```

`AppStateMachine` gains
`default Optional<TransitionKernel<?, ?>> transitionKernel()` returning empty.
A machine that can be composed overrides it. `MessageCodec` already exists in
the host and is what `TypedAppStateMachine` uses, so the codec half is reuse,
not new surface. `facts` reads through whatever `AppStateReader` the caller
supplies; in a cascade that is the overlay, so a later step sees earlier
steps' writes. `admit` is the per-command admission check the engine runs on
a derived command before `decide`. The engine never calls anything on a
machine except through its kernel, and a machine without a kernel cannot be
a component.

**Authorization fact reads are explicit.** A governed map or role-approval
kernel needs actor and approval records outside its own instance namespace.
Such a kernel declares `readParticipants()` from its committed configuration.
Construction rejects unknown, duplicate, or self participant ids. The engine
passes exactly those participants to the four-argument `facts` overload as
read-only cascade overlays; it never exposes a foreign writer or global key
space. All participants must already belong to the profile. This declaration
does not add command-derivation edges: reading authorization state is not a
command cycle. Kernel descriptors and both facts overloads cross the plugin
callback/TCCL boundary just like `decide`. Standalone adapters continue using
their existing declared views; they must not fall back to node-local caches.

**Participant-owned work accounting.** Independent authority and integration
reviews found that the governed approval-to-map path needs foreign reads and
a shared cryptographic-work reservation, not arbitrary foreign business writes.
Its proposal/index writes belong to approvals; its consumption records belong
to the map. Therefore business plans remain component-local. An owner kernel
declares bounded `TransitionWorkBudget(id, localKey, maximumUnits)` values;
callers declare exact `TransitionWorkReference(participantId, budgetId)` values
and return at most one cheap `workRequest(command, context)` before facts are
loaded or signatures verified. The engine validates all references at construction
and reserves against the owner's actual namespaced state, never a cascade-local
counter. Existing governed routes use the same helper and the same 12-byte
`[height:int64, used:int32]` state format.

Reservations survive business rejection of their source cascade, but roll back
with a failed host block transaction. They confer no general write authority.
Duplicate budget ids/keys, unknown references, and ordinary plan writes,
consumptions, or receipts targeting a reserved accounting key are rejected.
Corrupt counters or backwards heights are infrastructure failures, not business
rejections. A quota miss rejects before expensive work. Approval expiry remains
an owner-produced maintenance plan in the leaf machine's ordinary block `apply`,
including empty blocks, before the event-binding workflow executes. No new host
maintenance lifecycle is needed. General cross-participant business plans are
not introduced without an actual use case and a separate authority review.

**Leaf catalog contributions.** Existing `authenticated-map` and `role-approvals`
selectors construct complete presets; the generic engine must not unwrap or
special-case them. Explicit catalog-registered leaf selectors expose their
shared kernels and lifecycle. A leaf may publish a versioned scalar-map command
surface for bindings, whose codec/facts construct the existing nested action and
evidence contracts before invoking the same authorizer. This does not alter the
standalone selector's wire format or let mappings bypass evidence checks. In
particular, the map's `apply-action` takes canonical action bytes and an approval
proposal id; immutable proposal facts supply the exact policy revision, while
the existing authorizer verifies the full action commitment and consumption.

**Transition events** are a host value type:

```java
public record TransitionEvent(String eventId, byte[] payload) { ... }
```

`TransitionPlan` gains a fifth component, `List<TransitionEvent> events`,
bounded by `MAX_EVENTS_PER_PLAN` (256) and `MAX_EVENT_PAYLOAD_BYTES`
(65 536). The per-plan bound is set above the largest existing batch
command, the authenticated map's 128 mutations, so a maximum-size standalone
command still produces its plan with one event per result plus a batch
summary. The existing `empty()` and `mutations(...)` factories keep their
signatures.
`TransitionPlans.commit` ignores events: they are not written, not hashed by
the host, and not visible after the transition. The payload is a canonical
CBOR map whose top-level fields are scalars (integer, text, bytes, boolean);
a nested structure is exposed as its canonical CBOR bytes.

A machine declares events in the same `decide` that declares its writes:

```java
return TransitionDecision.approve(TransitionPlan.of(
        mutations, List.of(), List.of(), List.of(),
        List.of(new TransitionEvent("kv-registry.entry-put.v1", payload))));
```

Events are derived, not emitted. No generic adapter infers events from state
writes; that was considered and rejected (§13.2).

**Events carry every derivable field.** A source machine includes in its
event any value an author is likely to compare or copy: hashes of payloads
and values, byte lengths, revisions and counts, and post-state values such as
a balance after transfer. This is a design rule for every event catalog, so
that common bindings need only comparisons and field copies; richer data
calculations use the restricted expressions in §5.13.

The scalar integer contract is signed 64-bit, without numeric truncation.
In particular, balance event amounts and post-balances use integer minor
units in that range. A composed balance transition outside the range rejects
with `BALANCE_EVENT_RANGE` before commit. Standalone balances keep their
existing arbitrary-precision wire/state semantics; they execute the shared
pure decision without the composition event adapter. The same distinction
applies to composition event byte caps: adding event metadata must not narrow
previously valid standalone commands.

**Baseline event.** For every step whose decision is approved, the engine
derives the semantic `composite.command-accepted.v1` event. Its payload
`{topic, sender, messageId, body, bodyHash, bodyLength}` is materialized only
when a binding subscribes to that component's baseline event (§5.8); the event
ID remains in the receipt even without subscribers. Any machine with a
kernel is therefore a source with no code of its own. The baseline event's
`body` is opaque; the raw-body mapping in §5.3 forwards it unchanged as the
complete command for a second machine, which is the tee pattern, and a
function call may hash or measure it.

**Event catalog.** Event ids are stable logical identifiers versioned
independently of Java class names. Each machine's contracts module publishes
its catalog and the field schema of every event. The planned catalog:

| Source | Event | Payload fields | Phase |
|---|---|---|---|

### 5.3 The binding IR: bindings, conditions, lookups, mappings, functions

A binding is:

```text
BindingV1 = [
    bindingId,                      ; text id, unique, [a-z][a-z0-9-]{0,62}
    sourceComponentId,
    eventId,
    ConditionV1,
    target                          ; CommandTargetV1 / EffectTargetV1
]

CommandTargetV1 = [ 0, targetComponentId, commandName, MappingV1 ]
EffectTargetV1  = [ 1, effectType, gate, resultPolicy, expiryBlocks, MappingV1 ]
```

**Conditions** are conjunctions of at most 8 clauses. Every clause must hold.
The legacy field/lookup forms have no OR or NOT; a CEL clause may express
both under §5.13. Two bindings from the same `(source, event)` whose conditions both
hold both fire, which is fan-out, and `bindings validate` warns when two such
bindings target the same `(component, command)`.

```text
ConditionV1  = [ * clause ]                     ; 0..8, all must hold
clause       = FieldClauseV1 / LookupClauseV1 / ExpressionClauseV1
ExpressionClauseV1 = [ 2, ExpressionV1 ]         ; checked boolean result, §5.13

FieldClauseV1 = [ 0, fieldName, op, operand ]
op            = 0 eq / 1 ne / 2 lt / 3 le / 4 gt / 5 ge / 6 in / 7 exists / 8 absent
operand       = literal / [ * literal ]         ; list only for `in`, at most 64 entries / absent for exists, absent
```

Type rules, checked at construction against the event schema: integers
accept every operator; text and bytes accept `eq`, `ne`, `in`, `exists`,
`absent`, compared byte-wise; booleans accept `eq`, `ne`. A field absent
from the event fails every operator except `absent`.

**Lookup clauses** read one exact key from a declared participant's
namespaced state through the cascade overlay, so a lookup sees earlier
steps' writes, and compare the result:

```text
LookupClauseV1 = [ 1, participantComponentId, keySource, expectation ]
expectation    = [ 0 ]                ; key exists
               / [ 1 ]                ; key absent
               / [ 2, literal ]       ; value equals literal, byte-wise
               / [ 3, eventField ]    ; value equals event field, byte-wise
keySource      = source               ; see mappings: field, literal, or function call
```

At most 4 lookups per condition. A lookup names the participant's logical
key as the machine's contracts module documents it, for example a
`kv-registry` application key or an `authenticated-map`
`(collectionId, applicationKey)` pair; the engine derives the physical key
through the owner's pure `TransitionKernel.lookupKey` callback, using the same
helper the machine itself uses. The default copies an already-local key;
the map decodes a canonical `[collectionId, applicationKey]` tuple. Callback
inputs and outputs cross the plugin boundary defensively. A lookup never iterates and
never reads outside the declared participant.

**Mappings** build the target command or effect payload:

```text
MappingV1 = [ 0 ]                               ; identity: payload = canonical CBOR of the event payload
          / [ 1, * [ targetField, source ] ]    ; 1..16 field assignments, encoded per the command descriptor
          / [ 2, eventField ]                   ; raw body: the field's bytes are the complete command bytes
source    = [ 0, eventField ]
          / [ 1, literal ]
          / [ 2, functionId, [ * source ] ]     ; call into the stock function catalog
          / [ 3, ExpressionV1 ]                 ; typed data expression, §5.13
```

A call's arguments may be fields, literals, or one further call; nesting
depth is at most 2 and a mapping contains at most 16 calls in total.

The three mapping kinds differ in what static validation can promise.
Field assignment is validated against the target's command descriptor and
encoded by the engine into the descriptor's wire layout, so a mapped command
reaches the target exactly as a client-submitted one would. Identity is
allowed only for effect targets, whose payload is opaque to the chain; for a
command target it would deliver the event wrapper, not a command. Raw body
requires a bytes-typed event field, skips descriptor validation, and relies
on the target kernel's codec, `admit`, and `decide` at runtime; the receipt
records the step as raw. Raw body is rejected at construction for a target
kernel if any of its commands declares an evidence field, because opaque
bytes can select a different opcode from the command named in the binding
and the evidence rule below
cannot be checked through it. Raw body over the baseline event's `body` is
the "tee one command to a second machine" pattern.

**The stock function catalog** `yano-x-binding-functions-v1` is a closed set
of pure, bounded, reviewed Java functions referenced by id:

| Function | Inputs | Output | Bound |
|---|---|---|---|
| `blake2b-256` | bytes or text | bytes(32) | input ≤ `maxFunctionInputBytes` |
| `sha-256` | bytes or text | bytes(32) | input ≤ `maxFunctionInputBytes` |
| `concat` | 2..8 values, all text or all bytes | same kind | output ≤ `maxFunctionInputBytes` |
| `utf8-bytes` | text | bytes | |
| `hex` | bytes | text | |
| `byte-length` | bytes or text | integer | |
| `cbor-encode` | any event value | bytes, canonical | |
| `cbor-field` | bytes (canonical CBOR map), text key | the field's scalar value | one level, no recursion |

The catalog is versioned by its id. Adding a function means a new catalog
id, and a profile that names a catalog or function the node's stock code
does not have fails construction. Functions never read state, never allocate
beyond their bound. A statically knowable type error is a construction
error. Data-dependent failures (including invalid CBOR, missing fields,
and byte-limit breaches) are deterministic cascade rejections. Integer
arithmetic is available through §5.13; user-defined functions are excluded.

**Command descriptors.** To validate a binding statically and to encode a
mapped command, every kernel publishes one `CommandDescriptorV1` per command
name:

```text
CommandDescriptorV1 = [ commandName, layout, [ * FieldV1 ] ]
layout              = [ 0, opCode ]    ; positional CBOR array [opCode, field1, field2, ...] in declared order
                    / [ 1 ]            ; CBOR map keyed by fieldName
                    / [ 2 ]            ; opaque bytes; raw-body mapping only, no declared fields
                    / [ 3 ]            ; positional CBOR array without an opcode
FieldV1             = [ fieldName, type, required, role ]   ; role: 0 = data, 1 = evidence
```

The engine encodes assigned fields into the layout as canonical CBOR and
hands the bytes to the kernel's codec. Most stock commands are positional
arrays with a leading opcode. The document-trail append command is an
opcode-free array and the ordered log accepts opaque bytes; their descriptors
must preserve those existing wire formats. The keyed layout supports machines
whose commands are maps. A descriptor whose
layout cannot represent a declared field is a contracts-module test failure,
not a runtime condition.

`role = evidence` marks a field the target verifies against a signer's prior
statement (an actor signature, an approval reference). Profile construction
requires every `required` field to be mapped, every `evidence` field to be
mapped from an event field rather than a literal, function, or expression, and every
mapped field's type to match. A target with an unmapped evidence field fails
construction with `BINDING_EVIDENCE_UNSATISFIABLE`.

**Components and configuration.** A component names a machine from the
plugin catalog, its ingress topic, its configuration, and its effect quota:

```text
ComponentV1   = [ componentId, machineId, ingressTopic, configuration, maxEffectsPerBlock, fromHeight ]
configuration = canonical CBOR map of settingName -> scalar
```

Configuration is validated against the `ConfigurationDescriptorV1` the
machine's kernel publishes, which lists every accepted setting, its type,
and its default:

```text
ConfigurationDescriptorV1 = [ * [ settingName, type, default / null ] ]
```

Normalization fills every omitted setting with its default before encoding,
so two authors who omit and state the same default produce the same bytes.
The component's `configurationId` in the profile is
`hex(Blake2b-256("yano-x-component-config-v1\0" || canonical configuration bytes))`,
computed at construction and never authored. The provider builds each
component's `AppStateMachineContext` from its IR configuration, not from
node YAML, so `machines.<componentId>.*` keys in node configuration are
ignored for declarative components and rejected by `bindings validate` when
present. Two components may use the same machine with different
configuration; they are distinct generations with distinct ids, topics, and
namespaces. Where a machine reads a setting today from its creation context,
for example the key/value registry's value format, the descriptor names that
setting and the provider supplies it the same way, so standalone behaviour
is unchanged.

The ingress topic defaults to `<componentId>.command.v1` and must be unique
across the profile. It is a route in the ADR-013.2 sense and is committed
with the profile.

`fromHeight` defaults to 1 and identifies the component generation under
ADR-013.2; it is not inferred from local catalog order. Changed configuration
or quota for an existing instance requires a new generation height. Unchanged
generations across catalog entries reuse the same machine object and descriptor,
as `CompositeProfileCatalog` requires. Incompatible state/result contracts still
require a new component id; a new height does not waive compatibility checks.

**The complete IR** is one canonical CBOR array:

```text
BindingIrV1 = [
    1,                              ; IR version, catalog id "yano-x-binding-ir-v1"
    "yano-x-binding-functions-v1",  ; function catalog id
    "yano-x-cel-v1",                ; expression semantics profile, §5.13
    workflowFromHeight,              ; explicit workflow generation, genesis = 1
    [ * ComponentV1 ],              ; ordered components
    [ * BindingV1 ],                ; ordered bindings
    LimitsV1
]
LimitsV1    = [ maxCascadeDepth, maxDerivedPerSourceMessage, maxDerivedPerBlock,
                maxEventPayloadBytes, maxLookupsPerCondition,
                maxFunctionCallsPerMapping, maxFunctionInputBytes,
                maxExpressionNodes, maxExpressionDepth, maxExpressionValueBytes,
                maxExpressionWorkPerCascade, maxExpressionWorkPerBlock ]
```

Unknown fields, type mismatches, missing required fields, duplicate ids,
unknown catalogs, and unknown functions fail construction. The IR contains no
references, recursion beyond the stated nesting, host callbacks, or
implementation-defined nodes. Evaluation is total and bounded.

`workflowFromHeight` defaults to 1 for genesis and must not precede any
participant's `fromHeight`. A changed binding program requires a new workflow
generation height, even when its components are unchanged. Catalog entries
cannot redefine the same `(workflowId, fromHeight)` with different executable
behavior. Heights are committed in the IR and profile, not assigned from the
order in which dormant profiles happen to be configured. A generation height
is an earliest usable height, not authorization to activate a profile: ADR-015
proposal, readiness, and scheduled activation remain mandatory.

Authoring is off-chain. Devtools compiles a YAML binding document (§6) into
IR bytes. Nodes never parse YAML.

### 5.4 Cascade execution

The event-binding workflow owns the ingress topic of every declarative component,
including components without outgoing bindings. `WorkflowDescriptor` today has exactly one topic and the
composite routes by equality against it; schema v2 changes the descriptor to
a topic list of 1 to 64 entries, and `routeIndexes` matches by membership,
exactly as it already does for component topic lists. The workflow therefore
receives every source message in its original global block index order,
regardless of which source it belongs to. Ingress selects the source
component by the message topic. Declarative components own no topics of their
own, exactly as `approvals` and `authenticated-map` own none inside
`AuthenticatedMapPreset`. This preserves global command order and uniform
atomic planning/receipts. Components without outgoing bindings do not spend the
shared binding-work budget merely for ordinary source processing (§5.8).

One workflow per source topic was rejected (§13.13): workflows run in
declared order, so every message on a later workflow's topic would execute
after every message on an earlier one, breaking block order across sources.

For each routed source message, in block order, the workflow runs one
cascade:

```text
cascade(source):
    component = sourceComponentFor(source.topic)
    steps     = [ Step(component, component.kernel.codec.decode(source.body), originator, source.messageId) ]
    plans     = []
    overlay   = empty read overlay over the declared participant views
    produced  = 0
    charged   = readBlockWorkCounter()                        // ~composite/binding-work/v1/<height>
    if charged >= maxDerivedPerBlock and hasBindings(component): return noop(CAPACITY_EXCEEDED)

    while steps not empty:
        step   = steps.removeFirst()
        if depth(step) > maxCascadeDepth:                      return noop(LIMIT_DEPTH)
        if step.kernel.admit(step.command, step.context) rejects: return noop(step, ADMISSION)
        facts  = step.kernel.facts(step.command, step.context, overlay)   // read-your-writes
        result = step.kernel.decide(step.command, step.context, facts)
        if result is Rejected:                                  return noop(step, result.code)
        if conflictsWithEarlierConsumption(result.plan, plans): return noop(step, CONSUMPTION_CONFLICT)
        plans.add(result.plan); overlay.apply(result.plan)
        events = result.plan.events() + baseline(step, result.plan)
        for event in events:
            for binding in bindingsFor(step.component, event.id) in declared order:
                if !binding.condition.holds(event.payload, overlay): continue   // field + lookup clauses
                produced += 1
                if produced > maxDerivedPerSourceMessage:       return noop(LIMIT_FANOUT)
                if charged + produced > maxDerivedPerBlock:     return noop(CAPACITY_EXCEEDED)
                steps.addLast(derive(step, binding, event, produced))   // mapping + function catalog

    effectsNeeded = sum(plan.effects.size() for plan in plans)
    if effectsNeeded > remainingWorkflowQuota():               return noop(EFFECT_CAPACITY_EXCEEDED)
    if claim(operationId(source), commandHash(source)) != CLAIMED: return noop(REPLAY_OR_CONFLICT)
    writeBlockWorkCounter(charged + produced)
    for plan in plans:  commit(plan)                            // step order, one block batch
    write BindingReceiptV1(source, ACCEPTED, steps)

noop(...):
    writeBlockWorkCounter(charged + produced)                  // attempted derivations are charged
    write BindingReceiptV1(source, REJECTED, ...)
```

A `derive` for a command target evaluates the mapping, including function
calls, encodes the result into the target command descriptor's wire layout,
or forwards the raw body field unchanged, decodes it through the target
kernel's codec, and builds a `TransitionContext` with the same height,
timestamp, and original message index, the originator sender, the target's
ingress topic, and the derived message id (§5.5). The target kernel's
`admit` runs on the derived command before `decide`, as
`EvidenceReleaseWorkflow` does for its synthesized messages today; an
admission rejection is a step rejection. A `derive` for an effect target
produces an `EffectIntent` inside the current step's plan, attributed to the
source component generation through the workflow emitter, so ownership and
quotas apply unchanged.

**Effect preflight.** The existing workflow emitter throws when its per-block
quota is exhausted, and `TransitionPlans.commit` writes state before it
emits effects, so a cascade that discovered exhaustion while committing
would abort the block. The cascade therefore sums the effects of every plan
before claiming, reads the workflow's per-block quota counter, and rejects
the source message with `EFFECT_CAPACITY_EXCEEDED` when the sum exceeds the
remaining quota. Both inputs are deterministic, so exhaustion is a receipt
on every member and the emitter's exception path is never reached.

**Block work charging.** `charged` is read from and written to an
authenticated per-block counter, keyed like the quota counters and cleared
at the end of the block. Accepted and rejected cascades both add their
attempted derivations, so a block of cascades that fail late still performs
at most `maxDerivedPerBlock` derivations. Once the counter has reached the
limit, a later source message on a component that has bindings is rejected
before any binding is evaluated; a source message on a component with no
bindings is a single-step cascade and still executes.

Because every step is decide-then-plan and nothing is written until every
step approves, the cascade is atomic without a savepoint. Plans are committed
sequentially in step order; no merge is needed. Later steps and lookup
clauses see earlier steps' writes through the overlay, which is deterministic
because step order is deterministic.

### 5.5 Derived command identity

A derived command has:

- `sender`: the originator's sender. The originator's envelope signature was
  verified by the host before admission; derivation does not re-sign.
- `derivedMessageId`:
  `Blake2b-256("yano-x-derived-command-v1\0" || sourceMessageId || bindingId || be32(ordinal))`.
  It is distinct from the source id, so receipt and replay keys in target
  machines never collide with the source message.
- a `DerivationV1(sourceMessageId, bindingId, ordinal, depth)` record carried
  in the step context and written into the binding receipt.

A derived command never gains authority the originator did not have. Target
machines whose principal is the sender see the same principal they would see
for a direct submission.

### 5.6 Atomicity, failure semantics, and receipts

The unit of atomicity is one cascade inside one block batch. The unit of
failure is one source message.

- A rejected step, a limit breach, a conflicting consumption, or a replay makes
  the source message a deterministic no-op. No plan is committed. The cascade
  writes one `BindingReceiptV1` keyed by the source message id with the
  failing step and a stable code. This follows `CompositeWorkflow`'s contract:
  business failures are per-message no-ops and never throw.
- Exceptions remain reserved for invariant corruption and infrastructure
  failure. They discard the whole block batch, as today.
- The receipt is authenticated state under the workflow namespace, queryable
  at `composite/binding-receipt-v1/<messageId>`, and provable with the
  existing state-proof surface:

The physical key is discoverable with
`composite/binding-receipt-key-v1/<messageId>` (empty parameters, raw key bytes
in the generic query envelope's `payloadHex`) or offline with
`bindings receipt-key <messageId>`. It is
`CompositeStateKeys.workflowStateKey("event-bindings", sourceMessageId)`;
workflow version and generation height do not alter it. Key discovery does not
claim that a receipt exists or replace proof/finality verification.

```text
BindingReceiptV1 = [
    1, sourceMessageId, height, status, failedStepOrdinal / null, code,
    [ * StepReceiptV1 ]
]
StepReceiptV1 = [ ordinal, depth, bindingId / null, targetComponentId,
                  derivedMessageId, eventIdsProduced, conditionsEvaluated,
                  status, code, rawBody ]
```

`conditionsEvaluated` records, per binding considered at that step, whether
its condition held and which clause first failed or raised an evaluation error.
`rawBody` explicitly marks opaque command pass-through. That is what an integrator
needs to answer "why did my binding not fire", on chain and in dry-run.

The receipt is the trace the draft asked for in its §19. It is consensus data
because members must agree on it. Executor attempts and other node-local
observations stay node-local (ADR-013.1 §6).

### 5.7 Wait and effect boundaries

A cascade ends when no step produces a bound event. Multi-block business
processes arise naturally: an `approvals` PROPOSE derived from an order ends
its cascade at `item-proposed`; each later APPROVE is its own source message;
the threshold-reaching APPROVE produces `item-approved` and starts the next
cascade in that same transition. Its terminal approval state, staged-payload
cleanup, consequences, and any target-native authorization consumption records
commit atomically. A failed consequence rolls those business changes back, so a
later valid retry can still cross the threshold. A successful terminal approval
cannot emit the approved event again under a fresh message id; the member kernel
retains its terminal no-op semantics and the actor kernel retains its existing
terminal rejection. An exact source-message replay returns the original receipt
without executing a second cascade.

There is no framework-defined `(itemId, bindingId)` token or generic
`ALREADY_CONSUMED` code: arbitrary events have no universal item identity, and
ordinary repeated updates to a registry key must remain valid. One-use evidence
is verified and consumed by its owning target, such as the governed map's exact
action authorizer, in the same batch (ADR-025.2 §1.3). Overlapping one-use plan
keys within a cascade still reject with `CONSUMPTION_CONFLICT`.

Effect targets end a cascade branch. Emission is data; execution happens
after finality in the Effect Runtime. A CHAIN result returns to the owning
component generation through `onEffectResult` exactly as today. Bindings do
not observe results in v1.

### 5.8 Limits and cycle safety

All limits are fields of `LimitsV1` inside the profile bytes.

| Limit | Default | Maximum |
|---|---|---|
| `maxCascadeDepth` | 8 | 32 |
| `maxDerivedPerSourceMessage` | 32 | 256 |
| `maxDerivedPerBlock` | 4096 | 65536 |
| `maxEventPayloadBytes` | 65536 | 65536 |
| `maxLookupsPerCondition` | 2 | 4 |
| `maxFunctionCallsPerMapping` | 8 | 16 |
| `maxFunctionInputBytes` | 65536 | 65536 |
| `maxExpressionNodes` | 128 | 512 |
| `maxExpressionDepth` | 16 | 32 |
| `maxExpressionValueBytes` | 65536 | 65536 |
| `maxExpressionWorkPerCascade` | 1048576 | 4194304 |
| `maxExpressionWorkPerBlock` | 33554432 | 67108864 |
| bindings per profile | | 256 |
| clauses per condition | | 8 |
| `in` list entries | | 64 |
| fields per mapping | | 16 |
| IR bytes | | within the 64 KiB profile cap |

**Command admission versus execution rejection.** `maxEventPayloadBytes` bounds
the complete canonical event, not the raw command body. The baseline event's
semantic ID remains in the receipt, but its payload is materialized only when
this component has a binding subscribing to `composite.command-accepted.v1`.
Only then does it contain the body plus topic, sender, message ID, hash, and
length. Admission checks that exact encoded size before decoding the command
or pooling/relaying a local submission. A baseline subscriber therefore supports
slightly less than 65,536 body bytes, depending on metadata length. A component
without baseline subscribers has no such wrapper-induced command cap; the host's
message limit and the kernel's own command/native-event bounds still apply.
No bytes are truncated or silently omitted. Lower explicitly authored event
limits apply to events, not directly to raw command bodies. Native events may
have additional state-dependent overhead and remain execution-time validated.

After decoding, admission invokes the pure `TransitionKernel.admit(command)`
hook for command/configuration-only bounds (for example map schema and batch
limits). This additive host contract requires plugin API level **11**. The
contextual overload delegates to it by default and still runs during execution;
existing context-specific overrides are not invoked with fabricated block data.
Only codec runtime exceptions become `MALFORMED_SOURCE_COMMAND`. Unexpected
admission callback failures remain infrastructure errors, not business rejection.

Admission also rejects a source whose statically unavoidable work cannot fit its
per-cascade allowance, or whose binding-dependent work cannot fit a whole-block
allowance. Source-only fixed work does not consume the binding block allowance.
This is stateless feasibility,
not reservation against a node-local remaining budget. Local submission uses the
active candidate-height profile and a coherent committed-state snapshot, not the
genesis profile. A known-invalid submission returns HTTP 400 with a bounded safe
code (`COMMAND_PAYLOAD_TOO_LARGE` or `COMMAND_WORK_EXCEEDED`), is neither pooled
nor relayed, and has no finalized receipt. Block validation retains its independent
admission check; a successful submission is not a guarantee of future execution.

Execution repeats size and feasibility checks for source and derived commands.
It reserves command dispatch (`1 + body bytes`) and any required baseline
hashing/encoding before kernel facts/decision processing. Source fixed work is
charged only to its cascade. Selected-event decoding, conditions, lookups,
mappings, functions and expressions also charge the shared binding block budget.
Every derived dispatch and its event/preparation work charge both budgets, even
when its target has no outgoing bindings: host source-message bounds do not bound
internally derived commands. Unselected native events still undergo schema
validation; source-only validation is not binding-block work. Work is not charged
twice merely because a baseline payload was preflighted. State-dependent failure
or exhausted remaining block capacity produces a finalized rejection receipt,
rolls back the entire source cascade's business changes, and does not invalidate
the whole block. Such receipts are terminal for the source ID: a corrected or
later retry needs a fresh signed message ID and must still satisfy all business
authorization and consumption rules.

Work exhaustion remains deterministic, ordered, first-come accounting; failed
attempts are not refunded. A source with no bindings is not rejected merely
because earlier cascades exhausted the shared binding budget. Its fixed work is
already bounded by host message bytes/count plus per-cascade and kernel limits.
The next block starts with a fresh binding allowance. Ordinary source traffic
does not consume shared binding work. The authoring defaults are 1 Mi unit per
cascade and 32 Mi units per block so a near-64-KiB baseline raw-body tee fits:
the `source.v1` regression with 65,369 body bytes costs 392,650 cascade units
and 196,278 shared units, allowing 170 such cascades in an otherwise empty
default block allowance. Selected-event decoding remains byte-charged: a 60-KiB
native event alone uses at least 61,441 shared units, before conditions, mappings
and derived dispatch. Authors must select and test throughput and fan-out limits
together. Lazy baseline materialization and full-size event defaults remove the
incidental ~3.8 KiB ingress ceiling; they do not promise every maximal-payload,
maximal-fan-out cascade fits. Field-lazy decoding would change the consensus work
schedule and is not part of this version.

The changed pre-kernel reservation order is pinned by declarative profile and
workflow version **1.1.0**. Canonical IR layout is unchanged and explicit limits
are never rewritten on decode. Recompiling YAML with omitted limits selects new
defaults and changes its IR/profile identity. This is not an in-place upgrade of
a retained 1.0.0 chain; preserve its exact runtime or perform separately qualified
profile-generation migration.

`maxDerivedPerBlock` bounds the whole block, so the product of
`block.max-messages` and per-message fan-out cannot exhaust a proposer. The
counter `~composite/binding-work/v1/<height>` is charged with attempted
derivations by accepted and rejected cascades alike (§5.4). Breaching it
yields `CAPACITY_EXCEEDED` receipts for the remaining deriving source
messages in that block, mirroring ADR-025.2 Phase D, not a block abort.
Lookups and function calls are bounded per clause and per mapping, so the
work of one cascade is bounded by
`maxDerivedPerSourceMessage × (clauses × lookups + calls × maxFunctionInputBytes)`.

Effect capacity is checked before commit, never discovered during it
(§5.4, effect preflight). `EFFECT_CAPACITY_EXCEEDED` is a per-message
receipt code. `CompositeProfile.validateEffectBudget` remains the static
guarantee that the workflow's quota fits inside `effects.max-per-block`;
the preflight is the dynamic guarantee that successive cascades in one block
never exceed it.

Static cycles are rejected at profile construction: the directed graph whose
nodes are components and whose edges are command bindings must be acyclic in
v1. Effect targets are sinks. Bounded iteration is a possible future feature
and would require a new IR version.

Effect quotas compose with the existing budget check: the event-binding
workflow declares `maxEffectsPerBlock` like any workflow, and
`CompositeProfile.validateEffectBudget` continues to reject a profile whose
reserved quota exceeds `effects.max-per-block`.

### 5.9 Profile commitment, chain identity, and evolution

- `CompositeProfile.SCHEMA_VERSION` becomes 2. Version 2 adds the binding IR
  section and changes `WorkflowDescriptor.topic` to a topic list.
  `CompositeProfileCodec` encodes the list in place of the single topic and
  the IR after aggregate query limits. Version 1 bytes remain decodable and
  valid for chains without bindings; a v1 workflow decodes as a one-entry
  list.
- The digest domain string is unchanged; the schema version inside the bytes
  distinguishes the layouts. New golden vectors cover v2.
- The marker, the capability manifest's `composite-profile:<digest>`
  cross-cutting entry, and the DX lock's pinned profile digest all follow
  automatically.
- Evolution is ADR-015 unchanged. In governed mode, the provider builds its
  executable catalog from `binding-ir` plus `binding-ir-catalog[n]`; a
  proposal selects a target by digest; every member attests readiness; the
  epoch activates at the scheduled height. Consumption records and receipts
  written under a retired epoch remain valid state.
- A new function catalog id or IR version is a stock code change shipped in a
  Yano X release; a profile that uses it activates only through an ADR-015
  epoch once every member runs that release, which the readiness gate
  already enforces.
- Adding a component with a new id is a profile transition. Replacing a
  component's machine or configuration id follows ADR-013.2 generation rules.

### 5.10 Composability rules and the order of proof

Any machine can be a source, a target, or both, when it satisfies three
rules. The rules are generic; they do not name machines.

1. **A kernel.** The machine exposes a `TransitionKernel` through
   `transitionKernel()`: a codec, an admission check, a facts loader,
   `decide` into a `TransitionPlan` without writing, command descriptors
   with wire layouts, event descriptors, and a configuration descriptor.
   Atomicity comes from committing only after every step approves, so an
   inline-writing machine cannot be a step. Moving a machine to plan form
   and exposing its kernel is mechanical work, not a design barrier, but for
   a machine with frozen contracts it must be byte-identical and is gated by
   golden vectors.
2. **Events.** The machine declares events in its plan, or relies on the
   baseline event. Declared events make bindings precise; the baseline event
   makes every machine with a kernel a source with no further code.
3. **Authority.** Every command the machine accepts must be satisfiable by
   the originator's principal plus evidence carried in the source event. The
   machine's command descriptors mark evidence fields, and profile
   construction rejects a binding that cannot supply them (§5.3). §5.11
   defines how evidence travels.

Applied to today's machines, this gives the order of proof, not a boundary:

| Machine | Rule 1 today | Source | Target | Phase |
|---|---|---|---|---|
| `ordered-log` (host) | plan form | baseline and declared | yes, accepts anything | 0 |
| `kv-registry` | plan form | yes | yes | 1 |
| `doc-trail` | plan form | yes | yes | 1 |
| `approvals` (member k-of-n) | inline; refactor | yes | yes | 2 |
| `balances` | inline; refactor | yes | yes | 2 |
| `authenticated-map`, open/owner/member collections | inline; refactor under frozen-contract gate | yes, from `Receipt` | yes | 2 |
| `authenticated-map`, governed collections | same | yes | yes, with evidence from a `role-approvals` event | 3 |
| `role-approvals` | runs inside `RoleApprovalWorkflow`; needs a plan-form seam and staged action bytes | yes | no: every command needs a fresh actor signature | 3 (source only) |
| third-party manifested machine | as declared | if it exposes a kernel | if its kernel publishes command descriptors | any |

`role-approvals` as a target is the one durable "no": each of its commands is
a fresh actor-signed statement, and no event can carry a signature nobody
has made. That is rule 3 applied, not an exclusion of the machine. It is a
first-class source.

The authenticated map is on the critical path. It is the backbone of every
configuration-only product and the first machine an integrator will bind, so
its plan-form refactor is Phase 2 rather than a later option.

### 5.11 Authorization of derived commands

No step in a cascade produces a signature, and none needs to. Authorization
has three layers, and each has its own answer.

**Envelope.** The host verified the originator's member signature at
admission, before any machine saw the message. Derived commands are in-memory
step inputs that are never pooled and never re-admitted, so there is no
envelope to sign. The originator's verified envelope is the authority for the
whole cascade. `ShowcaseReleaseWorkflow` already relies on this today.

**Sender principal.** A derived command carries the originator's sender.
Machines whose principal is the sender (`kv-registry` ownership, `approvals`
approvers, `balances` accounts, `authenticated-map` owner and member
collections) evaluate the same principal they would for a direct submission.
Authority passes through and is never amplified. A binding can only make the
originator do what the originator could already do directly; if the
originator does not own the key the binding writes, the step rejects and the
cascade is a no-op.

**Evidence.** Actor-signed statements and approval references are data. They
are bound by their own hash to a policy, a revision, a deadline, and the
complete canonical action they authorize, and they are consumed once. If the
source event carries such evidence, the mapping copies it byte-for-byte into
the derived command's evidence field, and the target verifies it exactly as
it would for a direct submission through the same `RoleAuthorizationCapability`
path, writing the same one-use consumption record in the same batch. Nothing
is forged: the signer produced that statement in advance over precisely the
statement the target expects. If the mapping built a different action, the
target's hash check fails and the step rejects. The binding table cannot
weaken the check, because the check is the target's own. An evidence field
may only be sourced from an event field, never from a literal or a function,
and construction enforces that.

The first consumer is the governed `authenticated-map`:

```yaml
- id: approved-to-registry
  from: { component: reviews, event: role-approvals.proposal-approved.v1 }
  to:
    component: registry              # authenticated-map, AUTH_APPROVAL collection
    command: apply-action
    map:
      action:            { field: action }       # staged canonical MapActionV1 bytes
      approvalReference: { field: proposalId }   # evidence: verified and consumed by the map
```

Its prerequisite is a versioned addition to the role-workflow contract: today
`ApprovalProposalV1` stores only `payloadHash`, so the canonical action bytes
must be supplied at PROPOSE and staged under a bounded key, mirroring ADR-021's
`ae/p/<itemId>`, then carried by the approved event. ADR-022 §5.3 anticipated
exactly this addition. The map's existing authorizer recomputes the scoped
payload hash over the staged action and rejects any mismatch.

`StagedActorCommandV1` is a distinct canonical transport
`[1, signedActorCommandV1Bytes, actionBytes]`, with at most 32,768 action bytes.
Only PROPOSE carries nonempty action bytes. The product-neutral role component
does not interpret arbitrary product action schemas: the target codec checks
canonical action encoding, and its authorizer verifies the signed scoped hash.
Pending exact replay must carry identical staged bytes. Rejection, cancellation,
expiry (including empty-block expiry), or committed approval deletes staging.
A terminal PROPOSE replay cannot recreate staging and returns `CONFLICT`.
The frozen standalone signed-command and proposal encodings remain unchanged.

The first declarative actor leaf is explicitly a **genesis-fixed authority
participant** and shared budget owner. It rejects actor-governance command
derivations; fresh governance signatures and cross-participant governance
mutations are not made bindable by this ADR. Existing standalone governed
presets retain their governance routes. This limitation must appear in recipe
documentation rather than implying full preset or actor-rotation parity.

**What cannot be derived.** A target that requires a fresh signature over data
that only exists at cascade time. Profile construction rejects it statically
through the evidence-field rule in §5.3. There is no runtime path that could
reach such a target with unverified evidence.

**Events and receipts are not signed.** They are derived deterministically
inside consensus execution by every member. Their integrity is the block's
finality certificate and the state root. The receipt is authenticated state
and can be proven like any other entry.

**Deferred: delegation policy.** A genesis-committed policy stating that
actions derived through binding B on behalf of role R are authorized by the
originator's membership signature would let the binding table itself be
evidence. It is safe only under the governed-role framework with its own
consumption and revision rules, and belongs to a separate ADR in the ADR-019
and ADR-025.2 domain (§13.5).

### 5.12 Observability, dry-run, and tooling

- The capability manifest's `Workflow` entry for the event-binding workflow
  lists participant component ids, its topics, and its effect types as
  today. A `bindings` metadata entry lists `(bindingId, source, event,
  targetKind, target)` so explorers and Studio can draw the graph without
  decoding the IR.
- Devtools gains `appchain bindings compile|validate|graph|dry-run`, plus
  `receipt-key`, `recipe`, and `profile-check`.
  `compile` turns YAML into IR hex. `validate` runs the real profile
  constructor against the plugin catalog, kernels, event schemas, command
  descriptors, configuration descriptors, and function catalog, and reports
  every construction error with the binding, clause, field, or setting it
  concerns. `graph` renders the binding
  graph. `dry-run` executes one or more source messages through the real
  engine against a fixture state, without a node, and prints the
  `BindingReceiptV1` each would produce, including `conditionsEvaluated`.
  Blueprint `render` invokes `compile` and pins the profile digest in the
  lock.
- `recipe dpp|feed` builds chain-specific public genesis inputs from supplied
  actor/organization descriptors, verified chain-bound key proofs, and member
  configuration. It does not manufacture actor signatures or read private keys.
  The existing public-key/key-proof CLI supplies the required actor proof step.
  Starter generation also checks height-1 usability: active actors, organizations
  and keys must cover the fixed direct roles, proposer roles and approval quorum
  (including distinct organizations). This is not a general policy satisfiability
  proof or a guarantee about future state.
- `dry-run --prior-result` carries bounded complete physical post-state into the
  next consecutive fixture block. IR, explicit context and capability manifest
  identity must match; next timestamp, root and pending-effect assumptions stay
  explicit. `--continuation-only` emits a bounded state continuation artifact.
  Explicit empty-message fixtures execute the full block lifecycle; heights
  cannot be silently skipped. The CLI guide includes a proposal followed by two
  fresh approvals over carried state and a subsequent idle block.
  This is an unauthenticated local rehearsal, not a node snapshot export or a
  state-root computation.
- `profile-check` reconstructs supplied canonical retained profiles through the
  candidate plugin catalog before deployment. Application versions, query
  subjects and materialized defaults are committed inputs: an old IR alone
  cannot recreate a profile that the new binary no longer implements. The
  preflight is not migration, replay qualification or binary-semantic proof;
  see the [upgrade guide](../../docs/appchain/DECLARATIVE_BINDINGS_UPGRADES.md).
- Reference binding documents ship under `examples/bindings/` for the three
  product flows in §12 and the §7 procurement flow, so an integrator starts
  from a working recipe rather than a blank file.
- `operationalStatus` reports cascade counters per block. It is diagnostic
  only.

**Reviewed product boundary (2026-09-23).** Two independent reviewers checked
the accepted product ADRs and implementations. ADR-047's certificate verifier
requires an original signed `doc-trail` command in a finalized block. A derived
command has neither an independent envelope signature nor a finalized message
entry, by design. Therefore the attestation acceptance flow here is approval-gated
attestation recording with authenticated binding-receipt and trail-state proof
export, not a claim that `yano-x-attest-certificate-v1` accepts derived messages.
No synthetic signature or relaxed legacy verifier is introduced. A composite
certificate requires a separately versioned provenance contract.

DPP certification and feed closure qualification use the **existing product
value schemas and policies**: two auditors/publishers from distinct organizations,
the actual certification/round-close actions, and certified proofs of exact known
keys plus approval consumption. Existing product projections that enumerate by
replaying signed map envelopes do not discover internal commands automatically;
portal/list-projection compatibility is not claimed. Feed aggregation remains
the starter's off-chain recomputation at pinned observation height, not a new
on-chain aggregator or Cardano publication. These explicit boundaries replace
the draft's unsupported compatibility assumptions while preserving the core
acceptance goal: real application actions composed without Java orchestration.

### 5.13 Restricted CEL expressions

Use the official Java CEL implementation (`dev.cel:cel`) for parsing and
type checking during authoring. Pin the dependency to an exact version.
`yano-x-cel-v1` is a deliberately restricted CEL dialect, not a promise to
execute every CEL expression. The compiler lowers an allowlisted, checked
AST into a canonical Yano X expression IR; the runtime evaluates only that
IR with reviewed operations and deterministic accounting. This keeps parser
metadata, protobuf serialization choices, and evaluator optimizer changes
outside consensus. Unknown or unsupported AST nodes fail compilation and IR
decoding; runtime input is validated even when it did not come from devtools.

```text
ExpressionV1 = [ 1, resultType, node ]
node         = [ 0, scalar ]                         ; literal
             / [ 1, eventField ]                     ; typed event field
             / [ 2, operatorId, [ * node ] ]          ; allowlisted operator
```

Types are signed 64-bit integer, boolean, UTF-8 text, and bytes. Expressions
can read only declared event fields. State access remains an explicit lookup
clause through declared participants; expressions cannot obtain a reader,
writer, Java object, network client, clock, randomness, or environment.
The initial operator set is `==`, `!=`, integer `< <= > >=`, `&&`, `||`,
`!`, conditional `?:`, checked integer `+ - * / %` and unary minus, and
bounded text/byte concatenation. No floating point, dynamic dispatch,
comprehensions, regex, arbitrary methods, or user functions. Finance-like
amounts use explicit integer minor units; integer division truncates toward
zero and never silently rounds to a currency scale.

Operator ids, argument/result types, overflow rules, and evaluation order
have golden vectors. Arithmetic overflow, division by zero, absent referenced
fields, and output-size breaches are errors with stable codes. `&&` and `||`
use CEL's error-masking truth tables (`false && error` is false;
`true || error` is true); `?:` evaluates only its selected branch. Error
precedence and work charges must be pinned, independent of Java exception
messages. An unmasked expression error rejects the whole cascade and writes
a receipt, including the binding and expression location. A false condition
only skips that binding.

Each visited node costs one work unit; byte/text comparisons and concatenation
add the sum of operand byte lengths. Checked integer operations cost one node
unit, independent of operand value. Reserve this work and check output size
before allocating output. Enforce node/depth limits at construction and input
byte limits before evaluation. Charge per-cascade and per-block work even
when evaluation or a later step rejects. Exhaustion is
`EXPRESSION_CAPACITY_EXCEEDED`, never a wall-clock decision. These budgets
also bound expressions on conditions that do not produce any command.

The two historically expression-named work limits cover **all binding-language
evaluation**, not only CEL. The scalar operation charges are: one unit per visited
condition, mapping, source node, or candidate binding; equality costs one plus
both scalar sizes (UTF-8 bytes for text, byte length for bytes, nine for fixed
scalars), and `in` charges each attempted candidate in order. A lookup costs one
plus key bytes before reading and returned-value bytes before comparison.
Functions reserve their input sizes and output size before computation; CBOR
encoding reserves nine units per item/container header plus text/byte payload
sizes. Raw/identity copies reserve their byte length. Event processing reserves
one plus encoded event bytes before decode; baseline construction also charges
body hashing and encoding. Text sizing does not allocate an intermediate UTF-8
buffer. Execution version 1.1.0 separates host-bounded source preparation from
binding-dependent and derived work as specified in §5.8: source-only preparation
and unselected native-event validation charge the cascade budget, while selected
event decoding and all derived-command processing also charge the block budget.
Baseline payloads are lazy. Both counters retain the attempted charges assigned
to them even when one is exhausted.
This closes the otherwise unbounded aggregate-work gap in repeated nonmatching
non-CEL conditions. Signature verification uses the separate shared owner budget
above, never the binding-language work counter.

Field mappings accept `expr: '<CEL expression>'`; a condition accepts
`expr: '<boolean CEL expression>'`. Compilation verifies the result type
against the event schema and destination field. Evidence fields accept only
direct event-field copies: expressions cannot construct signatures or
approval references. Targets still verify action hashes and consume evidence.

Canonical expression bytes, dialect id, and limits are committed in the
binding IR. Any semantic change requires a new dialect id and governed profile
activation; a library upgrade must reproduce existing vectors and IR bytes.
The compiler must reject unsupported syntax instead of silently falling back
to full CEL evaluation. CEL adds no dependency to the Yano host API.

References: [CEL Java](https://github.com/cel-expr/cel-java) and
[CEL processing model](https://cel.dev/overview/cel-overview?hl=en).

## 6. Configuration and authoring

Authors write a binding document in the blueprint. Devtools compiles it; the
runtime configuration carries only the IR hex and the usual identity fields.

```yaml
# appchain.yaml (blueprint excerpt)
spec:
  chains:
    - id: procurement
      recipe: declarative-composite
      composite:
        components:
          - id: suppliers
            machine: kv-registry
            config: { value-format: utf8 }
          - id: orders
            machine: kv-registry
            topic: orders.command.v1          # default is <id>.command.v1
          - id: approvals
            machine: approvals
          - id: audit
            machine: doc-trail
            maxEffectsPerBlock: 1
        bindings:
          - id: order-to-approval
            from: { component: orders, event: kv-registry.entry-put.v1 }
            when:
              - { field: valueLength, le: 4096 }
              - lookup: { component: suppliers, key: { field: owner }, exists: true }
            to:
              component: approvals
              command: propose
              map:
                itemId:   { fn: hex, args: [ { field: key } ] }
                payload:  { field: value }
                required: { literal: 2 }
                deadlineMillis: { literal: 0 }
          - id: approved-to-audit
            from: { component: approvals, event: approvals.item-approved.v1 }
            when:
              - { field: approverCount, ge: 2 }
            to:
              component: audit
              command: append
              map:
                entityId:  { field: itemId }
                entryHash: { field: payloadHash }
                reference: { fn: concat, args: [ { literal: "procurement-approved:" }, { field: itemId } ] }
          - id: audit-to-outbox
            from: { component: audit, event: doc-trail.entry-appended.v1 }
            when:
              - { field: reference, in: [ "procurement-approved:po-123", "procurement-approved:po-124" ] }
            to:
              effect:
                type: webhook.post
                gate: app-final
                result: none
                map: identity
        limits:
          maxCascadeDepth: 8
          maxDerivedPerSourceMessage: 32
```

The first binding shows a bounded operator and a lookup: an order is only
proposed for approval when its value is within size and the originator is a
registered supplier. The second shows a function call building the audit
reference, which is what `ShowcaseReleaseWorkflow` does today by string
concatenation in Java. The third shows set membership.

Two key/value registries coexist because each has its own ingress topic,
configuration bytes, and namespace: `suppliers` states a value format,
`orders` takes the default, and both configuration ids are hashes the
compiler computes. A client submits an order to `orders.command.v1` with the
ordinary kv-registry command encoding.

Rendered runtime configuration:

```yaml
yano:
  app-chain:
    chains[0]:
      chain-id: procurement
      state-machine: declarative-composite
      state:
        commitment-profile: mpf-blake2b256-v1
        format-fingerprint: <generated>
        genesis-id: <generated>
      machines:
        composite:
          profile-mode: fixed
          binding-ir: <hex, generated by devtools>
```

The YAML is an authoring convenience. The IR is the contract. Two members
with different YAML that compiles to the same IR are identical; two members
with the same YAML but different compiler versions producing different IR
fail closed at height 1.

## 7. Worked example

Using the configuration above:

```text
block H, message m1 (sender = purchasing member, registered in suppliers)
  orders.put(key=po-123, value=<order cbor>)
    -> plan: mutation orders/po-123
    -> event kv-registry.entry-put.v1 {key: po-123, valueLength: 812, owner: …, …}
       -> binding order-to-approval: valueLength ≤ 4096 holds; lookup suppliers[owner] exists
          -> derived approvals.propose(itemId=po-123, payload=<order cbor>, required=2)
             -> plan: item po-123 PENDING, staged payload
             -> event approvals.item-proposed.v1 (no binding)
  commit plans in order; receipt(m1, ACCEPTED, 2 steps)

block H+1, message m2 (member A): approvals.approve(po-123)
  -> plan: approvers=[A], still PENDING; no event; receipt(m2, ACCEPTED, 1 step)

block H+3, message m3 (member B): approvals.approve(po-123)
  -> plan: approvers=[A,B], APPROVED
  -> event approvals.item-approved.v1 {itemId: po-123, approverCount: 2, payload: <order cbor>, …}
     -> binding approved-to-audit: approverCount ≥ 2 holds
        -> derived audit.append(entityId=po-123, entryHash=payloadHash,
                                reference=concat("procurement-approved:", "po-123"))
           -> plan: trail head
           -> event doc-trail.entry-appended.v1 {reference: "procurement-approved:po-123", …}
              -> binding audit-to-outbox: reference in [...] holds
                 -> effect intent webhook.post (owner = audit generation)
  terminal approval, staged-payload deletion, trail and effect commit atomically;
  receipt(m3, ACCEPTED, 3 steps); later terminal votes emit no approved event
```

If the originator of m1 were not in `suppliers`, the lookup clause would
fail, no approval would be proposed, the order put would still commit as a
single-step cascade, and the receipt for m1 would record that
`order-to-approval` was considered and which clause failed.

If `audit.append` were rejected at H+3, nothing from m3 would commit: the item
would remain PENDING with approvers [A], and the receipt for m3 would record
`failedStep=2, code=<doc-trail code>`. B may submit a fresh APPROVE later,
which runs a new cascade against the then-current state. That is the intended
behaviour: the approval and its consequence succeed or fail together, and no
partial outcome is ever committed.

## 8. Deterministic execution guarantees

Given identical committed state, block, profile bytes, and stock code, every
member derives identical:

- step sequence and derived message ids;
- events, clause outcomes, lookup results, and function outputs;
- plans, commit order, and state root;
- effect intents and ordinals;
- binding receipts.

The implementation must additionally define, and test, deterministic
canonical encoding of events and receipts, operator semantics per type
(byte-wise for text and bytes, exact for integers and booleans), overlay
read semantics for lookups, function outputs against pinned vectors, and
rejection codes. Wall clock, randomness, iteration over unordered
collections, and environment reads are forbidden as in every
`AppStateMachine`.

## 9. Module and dependency direction

The line between Yano and Yano X follows AGENTS.md ownership (host SPI in
Yano; composition in Yano X) and ADR-031 §8 (stock transition capabilities
must not depend on composite).

```text
Yano  core-api  transition package
      TransitionKernel, descriptors, AppStateMachine.transitionKernel()   (Phase 0, additive)
      TransitionEvent, events on TransitionPlan, bounds                    (Phase 0, additive)
      ordered-log exposes its kernel, declares message-finalized.v1        (Phase 0)
        |
        v
Yano X state-machines/stdlib-contracts, stdlib
      event catalogs, command descriptors, plan-form refactors
      depends on core-api only                                 (ADR-031 §8)
        |
        v
Yano X composition/contracts
      BindingIrV1, versioned function identifiers, binding wire contracts,
      BindingReceiptV1, CDDL, vectors
        |
        v
Yano X composition/runtime
      event-binding workflow, cascade engine, overlay, condition and lookup
      evaluator, function implementations, limits, cycle checks,
      profile schema v2, declarative-composite provider
        |
        v
Yano X tooling/devtools, tooling/studio, examples/bindings
      bindings compile | validate | graph | dry-run, blueprint schema, lock,
      graph view, reference recipes
```

What goes to the host, and why:

| Item | Home | Reason |
|---|---|---|
| `TransitionKernel`, `CommandDescriptor`, `EventDescriptor`, `ConfigurationDescriptor`, `AppStateMachine.transitionKernel()`, `TransitionEvent`, `events` on `TransitionPlan`, bounds | Yano `core-api` | Siblings of `TransitionPlan` and `TransitionCapability`, reusing the host `MessageCodec`; a third-party machine exposes its kernel and declares events against `core-api` alone; stdlib must not depend on composite. Additive: the accessor defaults to empty, the host commit path ignores events, and the existing plan factories keep their signatures. |
| `ordered-log` event | Yano | Host-owned machine, host-owned codec. |
| Derivation marker on `TransitionContext` | Yano, later | Optional. v1 keeps the derivation record in the Yano X receipt. |
| First-class `bindings` field on `AppCapabilityManifest` | Yano, later | v1 uses the existing cross-cutting metadata map; promote once the shape is stable. |
| Everything else, including the function catalog | Yano X | Depends on `CompositeWorkflow`, the profile codec, quotas, and governance, which live here under ADR-013.2, 015, and 031. The function catalog is composition policy, not host SPI. |

The host change is published as a new Yano version and pinned through
`yanoVersion` before Yano X Phase 1 starts. Building Phase 1 on a Yano X-side
event type and migrating later was considered and rejected (§13.3).

Promoting the whole composite runtime to Yano was considered and deferred
(§13.9).

- `authenticated-map` to plan form under a frozen-contract gate: existing

- Demonstrate `A -> B -> C` with a failing `C` and verify nothing from the

### Phase 3 — full condition and mapping language, effects, evidence pass-through

- Restricted CEL compiler, canonical expression IR, deterministic evaluator,

- Governed `authenticated-map` collections as targets through the evidence

## 11. Verification strategy

- **Determinism.** Multi-node cluster runs with identical height, root,
  profile digest, genesis, and capability-manifest digest across members for
  every example; replay from genesis reproduces roots; restart and catch-up.
- **Atomicity.** For every rejection code, a test asserts that no key written
  by an earlier step of the same cascade is present after the block.
- **Anti-poison.** A block containing a rejected cascade still finalizes and
  the proposer pool does not stall.
- **Identity.** Derived message ids never collide with source ids; target
  machine receipts keyed by derived ids are retrievable and provable.
- **Authority.** A binding that writes a key the originator does not own is
  rejected by the target with the same code as a direct submission. A
  governed-map binding with a mismatched staged action is rejected by the
  map's authorizer, and a matching one writes the same consumption record as
  a direct submission.
- **Evidence rule.** A binding whose target declares an evidence field the
  mapping sources from a literal, a function, or not at all, fails profile
  construction.
- **Language.** Every operator per type, every lookup expectation, and every
  function has pinned input and output vectors; a lookup sees an earlier
  step's write in the same cascade; a type error in any clause or mapping is
  a construction error.
- **Consumption.** Exact source-id replay preserves the original receipt and
  performs no work. A fresh-id vote on a terminal proposal cannot re-emit its
  approved event. Failed consequences roll terminal/staged business changes back;
  successful consequences commit those changes atomically. Governed map actions
  use the same exact-action one-use authorizer consumption as direct submission;
  repeated evidence cannot mutate the map twice. No universal item token is inferred.
- **Expressions.** CEL compilation and canonical IR vectors cover thresholds,
  OR/NOT, conditional approval counts, checked arithmetic, overflow, division
  by zero, missing fields, error masking, and forbidden syntax. Failed and
  nonmatching cascades consume expression work; replay and dry-run produce
  identical errors, receipts, charges, and roots. Evidence expressions fail
  construction. Dependency upgrades must reproduce the same IR vectors.
- **Limits.** Structural lookup counts, mapping function counts, IR size and
  invalid configured bounds reject construction/decoding before consensus
  participation. Data-dependent depth, per-message/per-block derivation, event
  payload, lookup/function input bytes, and evaluation-work breaches produce
  their documented per-cascade rejection codes, not block-aborting exceptions.
  Corrupt retained state and infrastructure failures remain exceptions handled
  by the enclosing host block transaction, not business rejection receipts.
- **Effect preflight.** A cascade whose plans need more effects than the
  workflow's remaining per-block quota is rejected with
  `EFFECT_CAPACITY_EXCEEDED`, writes no state, and the block finalizes; the
  emitter's exception path is never reached in any test.
- **Block charging.** A block of cascades that each fail at their last step
  performs no more than `maxDerivedPerBlock` derivations in total, later
  deriving messages short-circuit with `CAPACITY_EXCEEDED`, non-deriving
  messages still execute, and the counter is absent after the block.
- **Cross-source ordering.** Messages on two source topics interleaved in
  one block execute in global block index order, and the receipts' heights
  and ordinals prove it.
- **Configuration identity.** Two binding documents that state and omit the
  same default produce identical IR bytes and configuration ids; a
  node-level `machines.<componentId>.*` setting is ignored at runtime and
  rejected by `bindings validate`; two components of the same machine with
  different configuration have different ids and namespaces.
- **Raw body.** A baseline-event raw-body binding delivers the original
  command bytes to the target unchanged, the receipt marks the step as raw,
  and a raw-body binding to a target with an evidence field fails
  construction.
- **Cycle rejection.** A profile with `A -> B -> A` fails construction.
- **Profile identity.** Two members with differing IR fail closed at height 1
  or on retained-state startup with the existing marker error.
- **Governance.** A governed binding change activates at the scheduled height
  and old receipts remain provable.
- **Frozen contracts.** The `authenticated-map` plan-form refactor reproduces
  every existing golden vector, receipt, and proof byte-for-byte.
- **Dry-run parity.** For every reference flow, the receipt printed by
  `bindings dry-run` is byte-identical to the receipt committed on a cluster
  for the same fixture state and messages.
- **Golden vectors.** Canonical IR, event, and receipt bytes are pinned;
  decode-encode round-trips are byte-exact.

## 12. Acceptance criteria

This ADR is complete only when:

1. an application equivalent to §7 runs from configuration only, with no
   application-specific Java, on a three-member cluster with identical
   height, root, profile digest, and capability-manifest digest;
2. three real product flows are each expressed as a binding document with no
   Java, pass `bindings validate`, produce the expected receipts in
   `bindings dry-run`, and run on a cluster: approval-gated attestation recording
   and receipt/trail proof export (the reviewed ADR-047 boundary in §5.12),
   DPP claim certification using its existing schema and two-organization policy
   (root ADR-051), and feed round closure with independent publishers using its
   existing schema and policy (root ADR-052). The flow definitions are derived
   from the accepted product ADRs and independently reviewed; no unperformed
   product-owner approval or legacy client/portal compatibility is claimed;
3. every machine used as a component remains independently selectable and
   byte-for-byte unchanged in behaviour when used outside a composite,
   including `authenticated-map` after its plan-form refactor and at its
   maximum batch size;
4. every cascade rejection is a per-message no-op for business mutations and
   effects, retaining non-refundable work accounting and an authenticated,
   provable `BindingReceiptV1` that records which clause of which binding
   failed, and no cascade rejection, effect-capacity shortfall, or
   block-work exhaustion can abort a block;
5. derived commands carry distinct derived ids and the originator's sender,
   and a binding whose target declares evidence the mapping cannot supply
   fails profile construction;
6. an approved event's consequences, terminal approval, staged-action cleanup,
   and any target-native consumption record commit in the same batch; exact
   source replay does no work, fresh-id terminal votes cannot re-fire the event,
   and failed consequences leave approval/staged business state retryable;
7. a governed `authenticated-map` collection accepts a derived command only
   through the same authorizer path and consumption record as a direct
   submission, and rejects a mismatched staged action;
8. all limits are fields of the committed profile bytes; structural breaches
   reject profile construction, runtime breaches map to documented cascade
   codes, and attempted derivations of rejected cascades are charged to the block;
9. static cycles, unknown fields, types, catalogs, or functions, duplicate
   ids, unsatisfied evidence fields, and budget overruns fail profile
   construction before consensus participation;
10. identical IR instantiates identical component configuration on every
    member, every configuration id is derived from committed bytes, and
    node-level settings cannot alter a declarative component;
11. messages on different source topics execute in global block index order
    through one multi-topic workflow;
12. profile schema v2 golden vectors exist, v1 profiles still validate, and a
    governed v2-to-v2 epoch transition passes the cluster suite;
13. the host `TransitionKernel` and `TransitionEvent` contracts are published,
    consumed through `yanoVersion`, `ordered-log` exposes a kernel and is a
    working source, and a third-party machine in the conformance fixture
    composes through its kernel alone;
14. `bindings dry-run` reproduces cluster receipts byte-for-byte for every
    reference flow;
15. `verifyArtifactInventory`, `verifyJvmOnlyBuild`, `distributionCheck`, and
    the packaged smoke script pass with the new provider and examples; and
16. the documentation listed in §14 is updated and the open-item tracker
    carries the implementation rows.

## 13. Rejected alternatives

### 13.1 A separate "composition runtime" beside the composite

Rejected. It would duplicate routing, namespacing, quotas, ownership,
profile commitment, and governance that `CompositeStateMachine` already
provides, and would need a second entry point that ADR-031 §6.6 removed.

### 13.2 Generic event derivation from state writes

Rejected. Only `authenticated-map` writes a structured receipt; other
machines' state layouts are implementation details. Events must be declared
by the machine in its plan. The baseline event covers the "no codec" case
without inspecting state.

### 13.3 A Yano X-side event type instead of a host contract

Rejected. Stdlib event catalogs would then depend on composition contracts,
violating ADR-031 §8; third-party machines would depend on Yano X to declare
events; and `ordered-log` could only be a source through the baseline event.
The host change is an additive SPI extension, including kernel descriptors,
plugin lifecycle/class-loader facades, bounded events, logical lookup keys,
and owner-scoped work accounting. It ships before Phase 1; the implementation
is deliberately larger than the draft's original fifty-line estimate so that
these boundaries are explicit and tested.

### 13.4 Failing the transition on downstream rejection

Rejected. It inverts the per-message no-op rule and lets one admitted message
repeatedly abort block construction. The cascade is atomic per source
message; the block is not held hostage.

### 13.5 A synthetic system principal or delegation policy for derived commands

Rejected for v1. It would let the binding table grant authority no signer
holds. Derived commands inherit the originator's principal, and evidence
travels only when a signer already produced it. A governed delegation policy
is a possible later ADR in the ADR-019 and ADR-025.2 domain.

### 13.6 Unrestricted scripting or template evaluation

Rejected. Velocity's text rendering and Java object introspection are not
the required typed consensus contract. Unrestricted CEL evaluation is also
excluded. The restricted CEL compiler in §5.13 supports practical arithmetic
and boolean conditions while lowering only reviewed operations into bounded,
versioned IR. Its cost model, errors, and upgrades are part of this decision.
Application-defined Java functions remain provider code, not expressions.

### 13.7 Equality-only conditions and copy-only mappings

Rejected after the product intent was fixed on external integrators. That
language covers demonstration flows but fails on the first real
requirement, a threshold, an allowlist, a registry gate, or a computed
reference, and an integrator has no Java fallback. A no-code surface that
fails in the first pilot is worse than none.

### 13.8 Result-triggered bindings

Deferred. Effect results already reach the owning generation through
`onEffectResult`. Binding on results needs a decision about ownership
transfer across epochs and is not required by the acceptance scenario.

### 13.9 Promoting the composite runtime to Yano

Deferred. It would reverse the repository-split decision, move the
governance runtime, CDDL contracts, and cluster tests across, and place a
JVM-heavy engine under Yano's native-image target. Revisit after the
app-chain feature has a public release and the engine has proven itself.

### 13.10 A staged-writer adapter for inline-writing machines

Rejected. It would let an inline-writing machine act as a step without
refactoring, but ADR-031 §4.3 D chose decide-then-commit over helpers that
mutate opportunistically, and an adapter would have to infer rejection from
buffered writes. Plan form is the contract.

### 13.11 Bounded loops

Deferred. v1 requires an acyclic component graph. Iteration would need a new
IR version, a per-iteration budget, and termination proofs.

### 13.12 Deferring the authenticated-map refactor past the first release

Rejected. The map is the backbone of every configuration-only product and
the first target an integrator will bind. Shipping a no-code surface that
cannot bind it would not serve the stated customer. The refactor is gated by
byte-identical golden vectors instead of being postponed.

### 13.13 One event-binding workflow per source topic

Rejected. `WorkflowDescriptor` has one topic today, so the obvious fit was
one workflow per source. Workflows execute in declared order, so every
message on the second workflow's topic would run after every message on the
first, and a block's global order across sources would be lost. A
multi-topic descriptor in schema v2 keeps the routing helper and the order.

### 13.14 A single envelope ingress topic

Rejected. One composite-wide topic with an envelope naming the component
would also preserve order, but it forces every client to wrap commands in a
composite-specific encoding, hides the component from admission and from
existing clients, and gives the wrong topic to receipts and proofs.
Per-component ingress topics keep clients unchanged.

### 13.15 An authored configuration id

Rejected. A free-form `configurationId` string lets identical IR
instantiate different behaviour when members' node settings differ, which
is exactly the divergence the committed profile exists to prevent.
Configuration bytes live in the IR and the id is their hash.

### 13.16 Composition through `AppStateMachine` without a kernel

Rejected. Calling `apply` on a member machine cannot produce a plan, cannot
decode a mapped command, and cannot expose facts to a lookup clause. Adding
events alone would have enabled stdlib-only composition through private
knowledge of each machine, not third-party composition. The kernel is the
contract that makes the engine generic.

## 15. Resolved implementation choices and release boundary

The following choices were reconciled against the implementation and independent
reviews; they are no longer left for an integrator to guess:

1. `approvals.propose.required` is an ordinary integer command field and may
   be sourced from a literal, event, function, or restricted expression.
   Existing target admission/decision bounds remain authoritative.
2. Cross-cutting capability id `declarative-event-bindings` carries
   `schema=yano-x-binding-graph-v1` and `binding.<id>.*` attributes. Studio
   consumes this bounded metadata as an unauthenticated local preview.
3. Runtime configuration carries canonical IR hex. Blueprint locks pin the
   IR, profile, and exact plugin-catalog digests; the authoring plugins path
   is not a consensus setting or copied into node runtime configuration.
4. Staging is per proposal, at most 32,768 action bytes, with expiry/terminal
   cleanup and unchanged signed actor-command bytes inside the versioned wrapper.
5. `cbor-field` remains in v1 for one-level scalar maps, with strict canonical
   decoding, byte bounds, and explicit missing-field/type rejection. Authors
   are responsible for the value schema they choose to bind.
6. Product flows and their legacy interoperability boundaries are defined in
   §5.12 and §12. Independent review substitutes no claim of unperformed
   product-owner approval.
7. This work qualifies all phases together as an experimental implementation.
   It does not authorize a public release, production positioning, or publishing
   the required host Maven/ZIP inputs to a remote repository. Local exact-input
   publication is development evidence; release promotion is a separate decision.
8. `transitionKernel()` remains an `AppStateMachine` accessor. Validation
   instantiates through the catalog anyway, and needs no additional contribution
   kind. OrderedLog remains the sole host-owned built-in exception.
9. Identity mapping remains effect-only. Command targets use descriptor-checked
   fields or explicitly marked evidence-free raw-body pass-through.
10. Two independent reviews reconciled one-use actions with the generic-kernel
    boundary: the engine invents no universal item identity or per-binding token.
    Source terminal transitions, atomic staged-action cleanup, exact-id receipt
    replay, and target-native evidence consumption preserve the no-double-action
    invariant. This replaces the draft's unimplemented `(itemId, bindingId)` /
    `ALREADY_CONSUMED` proposal; §5.7, §11 and §12 require behavioral evidence.
11. Structural limits fail during authoring/profile construction; only executable,
    data-dependent limit breaches produce runtime rejection receipts. This preserves
    both fail-closed profile validation and per-message no-op block safety.
