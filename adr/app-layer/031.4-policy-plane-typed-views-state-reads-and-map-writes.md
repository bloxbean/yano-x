## 0. In plain words

ADR-031.3 gave the policy plane one policy point, admission, and a closed set of inputs. Two
blind spots remain, and they block most of the complex apps an integrator wants to build from
configuration:

1. **Rules cannot read values.** A lookup can only ask "does this key exist" or "are these
   bytes exactly equal". A rule cannot say "the amount must be at most this holder's tier
   limit", "the product must be ACTIVE", or "the limit stored in the settings collection".
   Every limit is a literal parameter, so changing one needs a profile epoch.
2. **Rules cannot see what a map write does.** The authenticated map is the machine every
   shipped starter uses (trust registry, product passport, data feed). Its commands are
   batches of up to 128 writes, and rules see none of their collections, keys, operations, or
   values. "A manufacturer writes only under its own products", "observations are
   insert-only", and "only an admin may revoke" are all impossible today.

This ADR adds two **typed views** to admission rules:

- **`reads`**: a rule declares up to four reads. Each read is one exact key in a declared
  component, decoded by that component's kernel into typed fields.
- **`writes`**: a kernel-provided list view of a map command's writes, checked with a
  bounded `all` or `exists` quantifier. In the verified-fact slot, each write also carries the
  actor who verifiably authorized it.

With reads, a limit or tier can live in a governed map collection. Changing it becomes an
ordinary role-governed write instead of a profile epoch. We call this pattern **governed
parameters**.

No new policy point is added. Rules stay forbid-only, read-only, bounded, and deterministic.

## 1. Decision summary

1.1. Add **state reads** to admission rules. A rule declares 0–4 named reads. Each read names
a component, an optional namespace (a map collection id), and a key source. At evaluation, the
engine reads the entry through the cascade overlay, and the owning kernel decodes it into
declared, typed fields. Expressions reference them as `reads.<name>.<field>`, or
`reads.<name>.value.<field>` for schema-typed map values. `reads.<name>.present` is always
defined.

1.2. Add a **map write view**. A kernel may declare a bounded list view of its command: one
element per write, with typed fields. In the admission slot, the elements carry decoded
content (collection, key, operation, value fields). In the verified-fact slot, the elements
also carry verified coverage (covering actor, organization, and roles). Expressions quantify
over it with `writes.all(w, …)` or `writes.exists(w, …)`. `writes` is the only list a rule may
quantify over, quantifiers do not nest, and evaluation short-circuits in index order.

1.3. **Governed parameters** are a pattern, not a new construct: a limit stored in a governed
map collection and read by a rule. Changing it is a governed write, authorized by the
collection's role or approval policy, and it takes effect at the next block. Literal
`params.*` and ADR-015 epochs remain for limits that must change only by profile governance.

1.4. Add two dialect operators needed by these views: `startsWith(text|bytes, prefix)` and
`size(text|bytes)`. The dialect otherwise keeps the ADR-031.1 §5.13 operator set.

1.5. The views are kernel-owned, like ADR-031.3 facts. The host carries the declarations and
bounded values across the plugin boundary; it neither evaluates rules nor interprets state.
The new `TransitionKernel` default methods are added to plugin API level 12, which is not
yet released, instead of creating level 13 (§5.7).

1.6. **Slots.** A rule that reads coverage fields (`w.actor*`, `w.coverage`) is a fact rule.
Otherwise the rule stays in the admission slot. Rules with reads are never static. Rules whose
clauses are all expressions and read only `writes` content, `command.*`, `params.*`, and
`config.*` are static, and also run at local ingress.

1.7. Receipts gain the failing write's index in `RuleFailureV1`. They never carry read values
or write contents.

1.8. The stock kernels declare value views: `balances`, `kv-registry`, `doc-trail`,
`approvals`, and `authenticated-map` per collection. `authenticated-map` also declares the
write view. The map authorizer retains which writes each verified actor covers.

1.9. All contracts are amended in place, with no new version identifiers:
- the IR, dialect, and receipt stay v1;
- `EXECUTION_VERSION` stays `1.2.0`;
- the plugin API level stays 12.

ADR-031.3 is unreleased, so there is nothing to stay compatible with. Pre-ADR-031.4 bytes fail
decode because of arity changes, and experimental chains and fixtures are regenerated.

## 2. Context

### 2.1 What exists after ADR-031.3

- Admission rules evaluate in two slots inside `EventBindingWorkflow.decide`, implemented in
  `composition/runtime/.../bindings/BindingRules.java`:
  - `admissionSlot`, after `admit`, before `workRequest`;
  - `factSlot`, after an approved `decide`.
- The inputs are `command.*`, `params.*`, `config.*`, `context.*`, and `facts.*`, plus lookup
  clauses.
- Lookups: `BindingProgram.lookup` derives the owner-local key via
  `TransitionKernel.lookupKey`, reads it through the overlay, and answers `EXISTS`, `ABSENT`,
  or byte equality (`EQUAL_LITERAL`, `EQUAL_FIELD`). The stored value is never decoded.
- Stored state is kernel-private encoding, not the application value:
  - `authenticated-map` stores `Entry(status, revision, controller, value, logicalValueHash,
    createdHeight, lastMutationHeight)` (`AuthenticatedMapContract.java:1259-1267`);
  - `kv-registry` stores `Entry(owner, value)` (`KvRegistryContract.java:73`);
  - `balances` stores a sign-padded integer.

  Byte equality over these records is rarely what an author means.
- Map values in collections with canonical-CBOR encoding are validated by a declarative schema
  (`yano-cbor-schema-ir-v1`, compiled from the `cddl-yano-subset-v1` CDDL subset, ADR-025.1
  Phase B). The subset supports exact text-keyed maps, so a collection's records can have
  named, typed top-level fields.
- A map command is one or more mutations (`AuthenticatedMapContract.Mutation`: operation,
  collection, application key, value, expected revision, expected value hash), at most
  `MAX_BATCH_ITEMS = 128`. The operations are `PUT`, `PUT_IF_ABSENT`, `COMPARE_AND_SET`,
  `TRANSFER_CONTROLLER`, `REVOKE`, and `RESTORE`. The map kernel publishes three `MAP`-layout
  commands and is not command-selectable (ADR-031.3 §5.4).
- The map's verified facts cover counts and, for a single direct actor, that actor's
  identity. `AuthenticatedMapDirectAuthorizer.AuthorizationResult` keeps `directFacts` and
  `governedMutationIndexes`, but not which writes each actor covered. That pairing is
  available on each `MapActorAuthorizationV1` evidence item while verifying.

### 2.2 What is missing

Taken from the product ADRs and the recipes in `examples/bindings/`:

| Application | Constraint | Blocked by |
|---|---|---|
| Tokenized asset | Per-holder tier limit; lock-up until `acquiredHeight + N`; limit changeable without an epoch | No value reads |
| Procurement | Order amount ≤ the supplier's credit limit | No value reads |
| Product passport (ADR-051 §8 defers lifecycle and sequence rules) | Writes only under the actor's own products; admin-only control operations; claims only on ACTIVE products | No write view; no value reads. The last one also needs per-write reads (§15 item 5) |
| Trust registry (ADR-049) | Issuer entry valid at this height; only admins transfer or revoke | No value reads; no write view |
| Data feed (ADR-052 §8 defers admission and equivocation) | A source writes only its own slot, insert-only; value within the feed's range; paused feeds refused | No write view; no value reads |
| Multi-tenant registry | Key prefix equals the tenant organization | No write view |

## 3. Goals and non-goals

### 3.1 Goals

1. Let rules compare command fields and context with typed values held in chain state.
2. Let integrators keep limits, tiers, and statuses in governed state and change them without
   profile epochs.
3. Make authenticated-map writes visible to rules, including per-write verified coverage.
4. Preserve every ADR-031.3 property:
   - forbid-only;
   - no bypass for derived commands;
   - kernel-owned facts;
   - dual-budget charging;
   - fail closed;
   - atomic denial with receipts;
   - committed and governed rules.
5. Keep the dialect small: one list, one quantifier level, two operators.

### 3.2 Non-goals

- Rules that write state, including counters. Quotas need a separate ADR (§16).
- Iterating state: prefix scans, ranges, or "count entries where". Reads are exact-key only.
- Read chaining, where one read's key is computed from another read. Denormalize records
  instead.
- General comprehensions, list literals, maps, nested quantifiers, or user functions.
- Exposing raw read values or write contents in receipts.
- Views for machines not listed in §5.4.
- Authority changes. Delegation, treasury accounts, and actor governance are separate
  enablers.

## 4. Terminology

| Term | Meaning |
|---|---|
| **Read** | A named, exact-key state read declared by a rule, decoded by the owner kernel's value view |
| **Value view** | A kernel's declaration of the typed fields it can decode from one namespace of its state |
| **Namespace** | `""` for single-namespace kernels; a collection id for `authenticated-map` |
| **Write view** | A kernel's bounded list view of its command, one element per write |
| **Coverage** | Verified facts attached to one write: who authorized it, and how |
| **Governed parameter** | A limit or setting stored in governed state and read by a rule |

## 5. Target architecture

### 5.1 Reads

```yaml
rules:
  - id: tier-limit
    command: transfer
    deny: TIER_LIMIT_EXCEEDED
    reads:                                   # 0..4
      holder:
        component: registry                  # an authenticated-map component
        namespace: holders                   # collection id; omit for single-namespace kernels
        key: { context: sender }             # any scoped source legal in this rule
    require:
      - expr: 'reads.holder.present && reads.holder.status == "ACTIVE"'
      - expr: 'command.amount <= reads.holder.value.maxTransfer'
```

Grammars (Phase 0):

- A read name is a CEL identifier, `[a-zA-Z][a-zA-Z0-9_]{0,62}`, not a CEL reserved word, unique
  within the rule. Reads are sorted by name, like parameters.
- A namespace is `""` or `[a-z0-9][a-z0-9._-]{0,63}` (the map's collection-id grammar). A kernel
  declares which namespaces exist (§5.7).
- View field names are CEL identifiers too. `present` is reserved for plain fields: no view
  declares a plain field named `present`. Value fields may use any name, including `present` and
  `value`, because the `value.` prefix keeps them apart. A view that declares value fields cannot
  also declare a plain field named `value`.

Semantics:

- The key source is evaluated like a lookup key source (ADR-031.3 §5.2): `context.*`,
  `command.*`, `params.*`, `config.*`, `facts.*` (fact rules only), literals, and `fn`. It must
  yield bytes or text; text is UTF-8 encoded.
- The engine asks the owner kernel for the owner-local state key with
  `ruleValueKey(namespace, key)`. It then reads through the cascade overlay, so earlier writes
  in the same cascade are visible, exactly as lookups do.
- If the entry exists, the kernel decodes it with `ruleValueFields(namespace, key, stored)`
  into the declared fields.
- `reads.<name>.present` is `true` or `false`. Reading any other field of an absent entry
  raises an absent-field error. Under the existing `&&`/`||` error masking,
  `!reads.x.present || …` is well defined. An unguarded read of a missing entry fails closed
  with `ADMISSION_RULE_ERROR`.
- Reads are evaluated once per rule evaluation, before its clauses, in declaration order.
- Reads are pure: no writes, no iteration, and no chaining. A key source cannot reference
  `reads.*`.
- A rule with reads is never static. It runs in the admission slot, unless it also reads
  facts or coverage, in which case it runs in the fact slot.
- Construction type-checks every `reads.<name>.<field>` against the owner kernel's declared
  view for that namespace. Diagnostics: `RULE_READ_UNKNOWN_COMPONENT`,
  `RULE_READ_UNKNOWN_NAMESPACE`, `RULE_READ_UNKNOWN_FIELD`, and `RULE_READ_KEY_TYPE`.

**Governed parameters.** Store limits in a governed collection whose schema is an exact
text-keyed map. The collection's own authorization policy — direct role or approval
(ADR-025.2) — governs who can change them, and an ADR-031.3 rule can add deployment
constraints on those writes (§6.3). A changed value applies from the next block that reads
it. Literal `params.*` remain for values that must change only through a profile epoch.

### 5.2 Map write view and quantifiers

```yaml
rules:
  - id: insert-only-observations           # static: content only, also refused at ingress
    deny: OBSERVATION_NOT_INSERT
    params: { collection: { type: text } }
    require:
      - expr: 'writes.all(w, w.collection != params.collection || w.op == "PUT_IF_ABSENT")'
  - id: own-namespace                      # fact rule: reads coverage
    deny: FOREIGN_NAMESPACE
    params: { collection: { type: text } }
    require:
      - expr: >
          writes.all(w, w.collection != params.collection
                        || (w.coverage == "direct"
                            && startsWith(w.keyText, w.actorOrganizationId + "/")))
```

Element fields:

| Field | Type | Slot | Meaning |
|---|---|---|---|
| `index` | integer | admission | Position in the batch, 0-based. Defined by the engine for every write view; no kernel declares it |
| `collection` | text | admission | Collection id |
| `key` | bytes | admission | Application key |
| `keyText` | text | admission | The key as UTF-8; absent when the key is not valid UTF-8 |
| `op` | text | admission | `PUT`, `PUT_IF_ABSENT`, `COMPARE_AND_SET`, `TRANSFER_CONTROLLER`, `REVOKE`, `RESTORE` |
| `hasValue` | boolean | admission | Whether the operation carries a value: `PUT`, `PUT_IF_ABSENT`, `COMPARE_AND_SET`, `RESTORE` |
| `valueLength` | integer | admission | Value byte length (0 when none) |
| `expectedRevision` | integer | admission | The write's revision precondition |
| `value.<field>` | per schema | admission | Top-level scalar fields of a schema-typed value (§5.4); absent otherwise. `value.<f>` is declared when some value view of the kernel declares value field `f`, and every view that declares it gives it the same type |
| `coverage` | text | fact | `direct`, `approval`, or `none` (open, owner, and member collections) |
| `actorId` | text | fact | Covering actor, when `coverage == "direct"` |
| `actorOrganizationId` | text | fact | Covering actor's organization, when `coverage == "direct"` |
| `actorRoles` | text set | fact | Covering actor's active roles, when `coverage == "direct"` |

Quantifier semantics:

- `writes.all(w, e)` evaluates `e` for each element in index order. It is `false` at the first
  `false`, raises the first unmasked error met before that, and is `true` if every element
  holds.
- `writes.exists(w, e)` is `true` at the first `true`, and otherwise `false` or the first
  error.
- The body may reference `w.*`, `params.*`, `config.*`, `context.*`, `command.*` (where legal),
  `reads.*`, and `facts.*` (fact rules). It may not contain another quantifier.
- The list is materialized once per step, lazily, only if an attached applicable rule — in
  either slot — references `writes`. The coverage fields are materialized once, in the fact
  slot, only if an applicable fact rule reads them.
- A component whose kernel declares no write view cannot attach a rule that references
  `writes` (`RULE_WRITES_UNSUPPORTED`).

`startsWith(a, b)` accepts two text or two bytes values and returns a boolean. `size(a)`
returns the UTF-8 byte length of text, or the length of bytes. Both are charged by operand
bytes, like equality. They are ordinary dialect operators, legal in binding conditions and
mappings as well as in rules (Phase 0). CEL's member form `a.startsWith(b)` lowers to the same
operator.

**Which write decided.** A quantifier *stops early* when `all` meets its first `false` element,
when `exists` meets its first `true` element, or when an element raises an error. The receipt's
`writeIndex` (§5.5) is the index at which the most recently completed quantifier of the failing
clause stopped early. It is `null` when that quantifier ran to completion, or when no quantifier
ran. So `writes.all(…)` false at element 3 reports 3, `!writes.exists(…)` that found element 2
reports 2, and `writes.exists(A) && writes.exists(B)` where `A` found element 1 and `B` found
nothing reports `null`.

### 5.3 Where the views are evaluated

```text
decide(step):
    decode; admit; admit(ctx)                                     // existing
    admission slot: for each rule → [writes = kernel.ruleWrites(command), once, at the first rule
                                     that references writes], reads, then clauses  // reads through overlay
    workRequest; facts; decision = decide(...)                    // existing
    if Approved and fact rules apply:
        values   = kernel.ruleFactValues(command, ctx, facts)     // existing (ADR-031.3)
        fact slot: for each rule → [writes, once, if not yet materialized],
                                   [coverage = kernel.ruleWriteCoverage(command, ctx, facts), once, at the
                                    first rule that reads coverage], reads, then clauses
```

The write view and coverage are materialized lazily, once per step, by the first applicable rule
that needs them, and their validation failures are attributed to that rule (clause `-1`). So a
step whose only write-view rules are fact rules does not materialize the view unless the kernel
approves, and a kernel rejection is then reported with the kernel's code. Every node follows the
same order, so the schedule and the work charged are deterministic (Phase 3 review).

Local ingress evaluates static rules, which may reference `writes` content. It calls
`kernel.ruleWrites(command)` after `admit`, without state, reads, or coverage.

### 5.4 Stock views

Phase 0 confirmed these fields against each kernel's stored record (§15 items 1 and 3).

| Kernel | Namespace | Stored record | Value view fields |
|---|---|---|---|
| `balances` | `""` (key: account id text) | sign-padded unsigned integer | `balance` integer |
| `kv-registry` | `""` (key: bytes) | `[owner, value]` | `owner` bytes; `value` bytes; `valueLength` integer; `valueText` text (declared only when `value-format: utf8`) |
| `doc-trail` | `""` (key: entity id text) | `[count, headHash]` | `count` integer; `headHash` bytes |
| `approvals` | `""` (key: item id text) | `Item(status, proposer, payloadHash, required, deadline, approvers, rejecter)` | `status` text (`PENDING`, `APPROVED`, `REJECTED`, `EXPIRED`); `required`, `approverCount` integers; `proposer`, `payloadHash` bytes |
| `authenticated-map` | each collection id | `Entry(status, revision, controller, value, logicalValueHash, createdHeight, lastMutationHeight)` | `status` text (`ACTIVE`, `REVOKED`); `revision`, `createdHeight`, `lastMutationHeight`, `valueLength` integers; `controller` bytes; `value.<field>` (below) |

Rules for every view:

- A value that cannot be represented in its declared type is never coerced. An integer outside
  int64 (a `balances` balance, a map integer) is reported unchanged, which violates the
  declaration, so the engine fails closed with `ADMISSION_RULE_INPUT`.
- A text or bytes value longer than `RuleFact.MAX_VALUE_BYTES` (4096) is absent; its length
  stays readable (`valueLength`). An absent field read unguarded fails closed with
  `ADMISSION_RULE_ERROR`.
- A stored record the kernel cannot decode yields no fields. `present` is still `true`, and any
  field read fails closed with `ADMISSION_RULE_ERROR`.
- `approvals` adds `payloadHash`, which the stored item carries. It does not expose the
  deadline: rules have no timestamp to compare it with. `EXPIRED` is written only by the first
  vote after the deadline, so a stored `PENDING` item may already be past it.
- `balances` deletes an account's key when its balance reaches zero, so an absent `balances`
  read means a zero balance.
- `kv-registry` `valueText` is absent when the stored value is not valid UTF-8 or longer than
  4096 bytes. `value-format` is matched case-insensitively.

**Map `value.<field>`.** The collection must use canonical-CBOR value encoding with a
declarative schema (`yano-cbor-schema-ir-v1`) whose root is an exact text-keyed map. The schema
IR retains member names (`AuthenticatedMapSchema.MapField.key`), so no genesis amendment is
needed. Each **top-level** member is exposed under its key when:

- the key is a CEL identifier (`[a-zA-Z][a-zA-Z0-9_]{0,62}`, not reserved); other keys are not
  addressable from CEL and are not exposed;
- its schema node is a single scalar kind: integer (`INTEGER`), text (`TEXT`), bytes (`BYTES`),
  or boolean (`BOOLEAN`). Choices, `null`, nested maps, and arrays are not exposed.

Optional members are absent when omitted. At most `RuleValueView.MAX_FIELDS` (32) members are
exposed: the first 32 eligible members in the schema's canonical member order. An integer member
is exposed whatever its schema range; a stored value outside int64 (possible under CDDL `uint`)
fails closed with `ADMISSION_RULE_INPUT` for every rule that reads that record or write.
Collections with opaque values or a plugin validator declare the entry fields only.

**Write view.** Only `authenticated-map` declares one in this ADR. Its content fields are the
§5.2 table's admission rows except `index`, which the engine defines. `hasValue` is true for
`PUT`, `PUT_IF_ABSENT`, `COMPARE_AND_SET`, and `RESTORE` (a restore installs a validated value),
whatever the value's length, and `keyText` is absent when the key is not valid UTF-8.
`value.<field>` is present only for a write that carries a value in a schema-typed collection,
decoded exactly as a stored value would be. Coverage requires
`AuthenticatedMapDirectAuthorizer` to retain, for each verified direct actor, the mutation
indexes it covered (`MapActorAuthorizationV1.coveredMutationIndexes()`), and for approval
evidence, its covered indexes. After approval, coverage is unique and follows the collection's
policy: each mutation has exactly one authorization assignment, whose kind must equal the
collection's policy, and each evidence item must cover exactly its assigned mutations. So a
write in a direct-role collection reports `direct` with its one actor, a write in an approval
collection reports `approval`, and a write in an open, owner, or member collection reports
`none`; its authority is the sender (see `facts.senderMember` and the map's own checks).

### 5.5 Receipts and codes

- `RuleFailureV1 = [ ruleId, failedClause, denyCode / null, writeIndex / null ]`. The array is
  4 elements (was 3). `writeIndex` (0..127) is the element at which the failing clause's most
  recently completed quantifier stopped early (§5.2), or `null`. A failure before any clause
  (`failedClause = -1`) always has a `null` index.
- Reads are evaluated before the clauses. A read that fails before any clause runs (a key that
  cannot be built or is rejected by `ruleValueKey`, a declaration violation, exhausted work)
  records `failedClause = -1`.
- Read failures reuse the existing codes:
  - an unguarded absent read, or an undecodable value, → `ADMISSION_RULE_ERROR`;
  - a kernel that returns values violating its declaration → `ADMISSION_RULE_INPUT`;
  - work exhaustion → `EXPRESSION_CAPACITY_EXCEEDED`.
- Receipts never include read values or write contents. The deny code and indexes are the
  whole disclosure.

### 5.6 Limits and work

| Bound | Value |
|---|---|
| Reads per rule | 4 (structural) |
| Declared value-view fields per namespace | 32 fields plus 32 value fields (`RuleValueView.MAX_FIELDS` each) |
| Entries in one decoded read or one write element | 64 (fields plus value fields) |
| Write value fields declared for typing | the union over the kernel's views, at most 64 × 32 names |
| Namespaces per kernel | 64 (the map's `MAX_COLLECTIONS`) |
| Write-view elements | the kernel's committed batch bound, at most `RuleValueView.MAX_WRITES` (128; map: 128) |
| Write-view element fields | 32 content fields plus the element's value fields |
| Text and bytes values | `RuleFact.MAX_VALUE_BYTES` (4096); larger map values expose only `valueLength` |

Work, charged on both counters at every depth and never refunded:

- **Read:** 1 + the rule key's bytes, then + the owner-local key's bytes, then + stored bytes,
  then + the encoded size of the decoded fields (9 per map, entry, and value, plus text and
  bytes lengths, as for fact values), before comparison. This matches how lookups charge both
  keys.
- **Write view:** 1 + encoded element bytes, once per step.
- **Coverage:** the same, once per step.
- **Quantifier:** node cost × evaluated elements.

A 128-write batch evaluated by one rule is bounded by these counters, and the map already
charges its own crypto work for such a batch.

### 5.7 Host contract (Yano `core-api`, additive, API level 12)

Frozen in Phase 0 (the Javadoc in `core-api` is normative):

```java
/**
 * One namespace of a kernel's state, with the typed fields its stored values decode to.
 * Value fields are read as reads.<name>.value.<field>; "present" is reserved.
 */
public record RuleValueView(String namespace, List<RuleFact> fields, List<RuleFact> valueFields) {
    public static final int MAX_VIEWS = 64;           // namespaces per kernel
    public static final int MAX_FIELDS = RuleFact.MAX_FACTS;  // per list
    public static final int MAX_WRITES = 128;         // write-view elements per command
    public static final String VALUE_PREFIX = "value.";
    // namespace: "" or [a-z0-9][a-z0-9._-]{0,63}; names unique per list; no field "present";
    // no plain field "value" when valueFields is non-empty. Lists are copied.
}

public interface TransitionKernel<C, F> ... {
    // State reads
    default List<RuleValueView> ruleValueViews() { return List.of(); }
    default byte[] ruleValueKey(String namespace, byte[] key) {           // owner-local key; pure
        if (!namespace.isEmpty()) throw new IllegalArgumentException("unknown rule value namespace");
        return lookupKey(key);
    }
    default Map<String, Object> ruleValueFields(String namespace, byte[] key, byte[] stored) {
        return Map.of();                                                    // pure, bounded
    }
    // Write view
    default List<RuleFact> ruleWriteFields() { return List.of(); }          // content fields
    default List<RuleFact> ruleWriteCoverageFields() { return List.of(); }  // fact-slot fields
    default List<Map<String, Object>> ruleWrites(C command) { return List.of(); }
    default List<Map<String, Object>> ruleWriteCoverage(C command, TransitionContext context, F facts) {
        return List.of();                                                   // only after Approved
    }
}
```

Key conventions:

- `ruleValueFields` returns a flat map: a declared field by its name, a value field as
  `value.<name>`. A declared name that is absent means "not established".
- `ruleValueKey` throws `IllegalArgumentException` for a namespace or key the kernel does not
  accept; the engine turns that into `ADMISSION_RULE_ERROR`, as it does for `lookupKey`.
- `ruleWrites` elements use the same flat convention: content fields by name, value fields as
  `value.<name>`. A kernel declares a write view by returning a non-empty `ruleWriteFields()`.
  Content fields are never named `index` (the engine defines it), `value`, or `present`.
- An element carries only value fields declared for the write view: `value.<f>` where some view
  declares value field `f` and every view that declares it agrees on its type. A kernel omits a
  conflicting member rather than returning it.
- Every other exception from these methods propagates like one from `decide`: a node-local
  plugin fault must not become a consensus outcome (ADR-031.3 deviation 12).

The contract:

- Every method is pure and depends only on committed configuration and its arguments. There
  is no state access, I/O, clock, or randomness.
- Values follow `RuleFact` types and bounds. The caller validates them against the
  declarations; a violation (a `null` result or value, an undeclared name, a wrong type, an
  exceeded bound, a list of the wrong length) is a deterministic `ADMISSION_RULE_INPUT`.
- `valueFields` are exposed under `value.<name>`.
- `ruleWrites` returns one element per write, in command order.
- `ruleWriteCoverage` returns a list of the same length and order, and is called only with
  the facts instance of an Approved decision.
- The runtime plugin facade forwards all of these methods (ADR-031.3 deviation 2) and
  snapshots values within the bounds, so no plugin object reaches the engine.
- Level 12 has not been released (ADR-031.3 RULE-007 open). These methods join level 12, so
  one host release carries both ADRs. If level 12 ships before this ADR, the methods move to
  level 13 unchanged.

### 5.8 Wire contracts (amended in place, v1)

```text
AdmissionRuleV1 = [ ruleId, denyCode, commandName / null, [ * ParameterV1 ],
                    [ * RuleReadV1 ], [ + RuleClauseV1 ] ]          ; 6 elements (was 5)
RuleReadV1      = [ name, componentId, namespace, keySource ]       ; 0..4, sorted by name
node            = …existing…
                / [ 3, quantifier, body ]                           ; quantifier: 0 all / 1 exists; list = writes
scope           = …existing (0..5)… / 6 reads / 7 write-element
field node      = [ 1, scope, name ] / [ 1, 6, readName, name ] / [ 1, 6, readName, "value", name ]
                / [ 1, 7, name ] / [ 1, 7, "value", name ]              ; write-element fields
operators       = existing + "startsWith" (TEXT,TEXT | BYTES,BYTES) -> BOOLEAN
                            + "size" (TEXT | BYTES) -> INTEGER
RuleFailureV1   = [ ruleId, failedClause, denyCode / null, writeIndex / null ]   ; 4 (was 3)
```

- Decode enforces the use-site table: `reads` and `write-element` only in rules, and
  `write-element` only inside a quantifier body. A quantifier body cannot contain a
  quantifier. Read fields and quantifiers appear only in rule expression clauses: never in read
  keys, lookup keys, lookup expectations, or binding sources, so no read is keyed by another
  read.
- Every amended structure changes arity, so pre-ADR-031.4 bytes fail with the explicit
  version error. Structures this ADR does not amend keep their bytes and their meaning: a
  document without rules, and a receipt whose steps record no rule failure, encode as before
  and decode identically. No byte string is read differently by the two layouts.
- **No new version identifiers.** ADR-031.3 is unreleased, so every identifier stays where
  ADR-031.3 left it:
  - `EXECUTION_VERSION` `1.2.0`;
  - IR version `1`, `yano-x-binding-ir-v1`, `yano-x-cel-v1`, and `BindingReceiptV1`;
  - the query subjects;
  - plugin API level 12.

  Changes are amended in place. Stale bytes fail decode because of the arity changes, not
  because of a version bump.
- The capability manifest adds `reads` and `writes` flags to each attachment's flat keys
  (ADR-031.3 deviation 21).

### 5.9 Structured refusal reasons (Yano host, bloxbean/yano#153)

A static-rule refusal at ingress reaches REST clients as more than `APPLICATION_REJECTED`. The
host keeps sanitization strict and adds allowlisted details:

- `AdmissionResult.reject(String reason, Map<String, ?> details)` is an explicit overload. The
  `CODE/detail/detail` string convention is not parsed. `details()` returns a bounded copy: at
  most 16 visited entries, keeping only text keys with `String`, `Long`, `Integer`, `Short` or
  `Byte` values, so no plugin-defined object crosses the plugin boundary. The copy is not yet
  checked against the allowlist or grammars. `reject(String)` has no details.
- `AppSubmissionRejectedException(String reason, Map<String, ?> details)` keeps `code` exactly
  as before (`[A-Z_]{1,32}`, otherwise `APPLICATION_REJECTED`). `details()` keeps only
  allowlisted keys whose values match their grammar:

  | Key | Grammar |
  |---|---|
  | `rule` | text `[a-z][a-z0-9-]{0,62}` |
  | `deny` | text `[A-Z][A-Z0-9_]{0,62}` |
  | `write` | integer 0..65535 |

  Unknown keys and invalid values are dropped, never echoed. When the code is replaced by
  `APPLICATION_REJECTED`, all details are dropped.
- The REST 400 body is `{"code": …}` as before, plus `"details": {…}` when any detail survived.
- This is advisory ingress only. Consensus, receipts, and block-time behaviour do not change.

Yano X ingress emits `rule` and `deny` for `ADMISSION_RULE_DENIED`, `rule` for
`ADMISSION_RULE_ERROR` and `ADMISSION_RULE_INPUT`, and `write` when a quantifier stopped early
(§5.2). The reason string is the bare code.

### 5.10 Post-state facts on the stock kernels (bloxbean/yano-x#25)

The stock kernels declare facts through the existing ADR-031.3 hook. Values are pure functions of
the command, its context (the sender, and the timestamp that decides expiry), and the approving
facts instance — the same computation the kernels use to build their events. Phase 0 confirmed
the table against each codec:

| Kernel | Fact | Type | Value |
|---|---|---|---|
| `balances` | `balanceAfter` | integer | `mint`: the account's balance after the mint |
| | `fromBalanceAfter`, `toBalanceAfter` | integer | `transfer`: sender and recipient balances after the transfer |
| `kv-registry` | `existed` | boolean | whether the key had an entry before the command |
| | `valueLength` | integer | `put`: the new value's length |
| `doc-trail` | `countAfter` | integer | the trail length after the append |
| | `first` | boolean | whether this append created the trail |
| `approvals` | `approverCountAfter`, `required` | integer | the item after the command |
| | `approvedNow` | boolean | whether this vote crossed the threshold |
| | `proposerIsSender` | boolean | whether the sender proposed the item |

- The proposed `ownerIsSender` is dropped: `decide` rejects a non-owner, so it would always be
  `true` after approval.
- A fact that does not apply to the command is absent: `balanceAfter` on a transfer,
  `valueLength` on a delete, and every `approvals` fact when the item does not exist after the
  command. An unguarded read of an absent fact fails closed (`ADMISSION_RULE_ERROR`).
- For a self-transfer, `fromBalanceAfter` and `toBalanceAfter` both equal the unchanged balance.
- A balance outside int64 is reported unchanged and fails closed with `ADMISSION_RULE_INPUT`.
  The composite adapter already rejects such commands with `BALANCE_EVENT_RANGE`.
- Profiles whose rules read none of these facts are unaffected.

## 6. Configuration examples

### 6.1 Tokenized asset: tier limit, lock-up, and a governed global limit

```yaml
composite:
  components:
    - id: actors
      machine: domain-actors-component
      config: { genesis-cbor-hex: "<actors>" }
    - id: registry                      # collections: holders, settings (schema-typed)
      machine: authenticated-map-component
      config: { actors: actors, approvals: reviews, genesis-cbor-hex: "<map genesis>" }
    - id: reviews
      machine: governed-role-approvals
      config: { actor-component: actors, genesis-cbor-hex: "<policies>" }
    - id: token
      machine: balances
      admission:
        - rule: governed-transfer-limit
        - rule: tier-limit
        - rule: lock-up
          params: { blocks: 1000 }
  rules:
    - id: governed-transfer-limit
      command: transfer
      deny: TRANSFER_LIMIT_EXCEEDED
      reads:
        limits: { component: registry, namespace: settings, key: { literal: "transfer" } }
      require:
        - expr: 'command.amount <= reads.limits.value.max'
    - id: tier-limit
      command: transfer
      deny: TIER_LIMIT_EXCEEDED
      reads:
        holder: { component: registry, namespace: holders, key: { context: sender } }
      require:
        - expr: 'reads.holder.present && reads.holder.status == "ACTIVE"'
        - expr: 'command.amount <= reads.holder.value.maxTransfer'
    - id: lock-up
      command: transfer
      deny: LOCKED
      params: { blocks: { type: integer } }
      reads:
        holder: { component: registry, namespace: holders, key: { context: sender } }
      require:
        - expr: 'context.height >= reads.holder.value.acquiredHeight + params.blocks'
  bindings: []
```

`settings/transfer` is a record `{ max: int }` in a collection governed by an approval policy.
Raising the limit is a proposal and approvals, not a profile epoch.

### 6.2 Product passport: namespace isolation and lifecycle

```yaml
  rules:
    - id: manufacturer-owns-product
      deny: FOREIGN_PRODUCT
      require:
        - expr: >
            writes.all(w, (w.collection != "product-versions" && w.collection != "events")
                          || (w.coverage == "direct"
                              && startsWith(w.keyText, w.actorOrganizationId + "/")))
    - id: admin-only-lifecycle-ops       # revocation and restoration in direct-role collections
      deny: ADMIN_ROLE_REQUIRED
      params: { role: { type: text } }
      require:
        - expr: >
            writes.all(w, (w.op != "REVOKE" && w.op != "RESTORE")
                          || (w.coverage == "direct" && params.role in w.actorRoles))
```

`TRANSFER_CONTROLLER` is legal only in owner collections, where coverage is `none`, so it cannot
be role-gated this way; a rule can still forbid it outright (`w.op != "TRANSFER_CONTROLLER"`).

This ADR does **not** cover "claims only on ACTIVE products" for arbitrary batches. Each
write would need its own read, keyed by that write's product, and per-write reads are
deferred (§13.3, §15 item 5). Until then, that ADR-051 lifecycle rule remains a kernel or
binding concern.

### 6.3 Data feed: own slot, insert-only, within range, and not paused

Key layout for observations: `<actorId>/<round>`. One feed per chain.

```yaml
  rules:
    - id: own-insert-only-slot          # fact rule (coverage)
      deny: OBSERVATION_REJECTED
      require:
        - expr: >
            writes.all(w, w.collection != "observations"
                          || (w.op == "PUT_IF_ABSENT" && w.coverage == "direct"
                              && startsWith(w.keyText, w.actorId + "/")))
    - id: feed-open-and-in-range        # admission slot (reads + write content)
      deny: OBSERVATION_OUT_OF_RANGE
      reads:
        feed: { component: registry, namespace: feeds, key: { literal: "main" } }
      require:
        - expr: 'reads.feed.present && reads.feed.value.status == "OPEN"'
        - expr: >
            writes.all(w, w.collection != "observations"
                          || (w.value.price >= reads.feed.value.min
                              && w.value.price <= reads.feed.value.max))
```

`PUT_IF_ABSENT` on `<actorId>/<round>` makes a second observation from the same source for
the same round impossible, which rules out equivocation. A chain carrying several feeds needs
the feed id in the key, and a per-write read of that feed's record, which is deferred (§13.3).
Alternatively, it keys observations as `<actorId>/<feed>/<round>` and reads one feed record
per chain.

## 7. Deterministic execution guarantees

- Reads observe only consensus state through the cascade overlay, and are decoded by pure
  kernel callbacks from committed configuration.
- Write views are pure functions of the decoded command. Coverage is a pure function of the
  facts instance that produced an Approved decision.
- Iteration is over one bounded, kernel-declared list, in index order, with short-circuit and
  per-element charging. There are no nested quantifiers.
- There are no state writes, so this ADR adds nothing to rollback.
- Advisory ingress evaluates only static rules, and cannot change any outcome.

## 10. Verification strategy

- **Determinism:** replay from genesis reproduces roots and receipts. The write order and
  element fields are identical across members.
- **Soundness:** coverage equals the authorizer's verified assignment. Values equal the
  kernel's decoding of stored entries. No read or write content appears in receipts.
- **Fail closed:** an absent read, an undecodable value, an oversized field, or a kernel
  declaration violation denies deterministically and never throws out of the cascade.
- **No bypass:** direct and derived map commands get identical rule outcomes.
- **Budgets:** both counters are charged for reads, views, and quantifiers, including on
  denial.
- **Governance:** governed parameters change behaviour without an epoch; literal parameters
  still need one.

---

## 11. Acceptance criteria

1. Recipes §6.1–§6.3 run from configuration only on a three-member cluster, with identical
   state and receipts.
2. Rules read typed values from `balances`, `kv-registry`, `doc-trail`, `approvals`, and map
   collections. Every read is type-checked at construction and fails closed at runtime.
3. Rules quantify over map writes. Content rules run at ingress when static, and coverage
   rules only after an approved decision.
4. A governed parameter changes the admitted behaviour without a profile epoch.
5. There are no rule-written state, state iteration, read chaining, or nested quantifiers,
   and construction and decode enforce this.
6. The amended v1 contracts are the only layouts; pre-ADR-031.4 bytes fail decode explicitly.
7. The host contract ships in the same Yano release as ADR-031.3's.

## 12. Consequences

**Positive**

- Most of the rules deferred in ADR-049, ADR-051, and ADR-052 become configuration.
- Limits and tiers become governed data.
- The map, the machine every starter uses, becomes visible to policy.

**Costs**

- One more in-place amendment and fixture regeneration.
- Seven host defaults, making API level 12 larger.
- A new list node and quantifier in the dialect.
- Rules with reads are not static, so their refusals come at block time.
- Governed parameters shift some change control from profile governance to collection
  governance, which operators must understand.

## 13. Rejected alternatives

### 13.1 Engine-side generic CBOR path extraction over raw state

Rejected. Stored bytes are kernel-private records (`Entry(status, revision, …, value, …)`),
not application values. Only the owner kernel can decode them soundly and keep that decoding
in step with its codec.

### 13.2 Value-returning lookup clauses instead of named reads

Rejected. Named reads decode once and are reused across clauses. They are type-checked by
name, and they compose with `present` and error masking. A per-clause lookup-value would
decode repeatedly and need its own absent semantics.

### 13.3 Per-element reads inside quantifiers

Deferred. A read per write multiplies state access by the batch size and needs a
dynamic-count budget. Denormalize, or use one exact read with an attachment parameter (§6.2).

### 13.4 General comprehensions and list literals

Rejected. One kernel-declared list, one quantifier level, and index order are enough for the
target rules, and keep cost static. ADR-031.1 §13.11 still defers general loops.

### 13.5 A new plugin API level 13 now

Rejected while level 12 is unreleased. One coordinated host release is cheaper.

### 13.6 Rule-owned counters for quotas in this ADR

Rejected here, because it would make the plane write state. Quotas need a separate ADR, with
engine-owned counters (§16).

- **Post-state facts** (bloxbean/yano-x#25, §5.10): `facts.balanceAfter`, `facts.existed`, and

## 15. Resolved questions (closed in Phase 0)

1. **Schema member names.** Yes: `yano-cbor-schema-ir-v1` keeps each exact text-keyed map
   member's key (`AuthenticatedMapSchema.MapField.key`). No genesis amendment is needed. Only
   keys that are CEL identifiers are exposed (§5.4).
2. **`endsWith`.** Not added. The ADR's goal is a two-operator extension, and every recipe here
   puts the scoping prefix first (`<organization>/…`, `<actorId>/<round>`). A later in-place
   amendment can add it before release if a key layout needs it.
3. **`approvals` and `doc-trail` fields.** Confirmed against `ApprovalsStateMachine.Item` and the
   document-trail head `[count, headHash]` (§5.4). `approvals` adds `payloadHash` and
   `deadlineMillis`, which the stored item carries.
4. **`kv-registry` `value-schema`.** No. Structured records belong in schema-typed map
   collections; `kv-registry` exposes raw `value`, `valueLength`, and `valueText` for UTF-8
   registries.
5. **Per-write reads.** Deferred (§13.3). The ADR-051 lifecycle rule and multi-feed range checks
   stay kernel or binding concerns until a separate decision.
