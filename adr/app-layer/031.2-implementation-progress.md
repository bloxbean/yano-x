# ADR-031.2 implementation plan, contracts and evidence

This ledger records the implementation plan, the M0 tooling contracts, the
review reconciliation and the executed evidence for
[ADR-031.2](031.2-guided-declarative-binding-editor.md). A row is marked
complete only after its tests ran and its independent reviews were reconciled.
Nothing here promotes the experimental binding profile, publishes a release or
changes ADR-031.1 semantics.

## 1. Boundaries restated

- Authoring client only. Studio stays a static page; files are exchanged with the
  version-matched CLI explicitly. No localhost probing, companion service,
  signing, deployment, plugin installation, live submission or effect delivery.
- The Java compiler, catalog-selected providers and the real composite engine
  remain authoritative. The browser has no transition engine, CEL evaluator,
  IR encoder or profile builder. It may parse YAML/JSON, decode a bounded binding
  receipt for display, and give advisory local diagnostics only.
- No host change, binding IR revision, consensus rule, receipt wire change,
  application-version bump or new runtime plugin. Any discovered need for one
  stops the work for an explicit decision.
- Imported catalogs and reports are unauthenticated. Matching digests establish
  that inputs correspond, never who produced a file.

## 2. Findings that shape the design (2026-09-25)

| Finding | Consequence |
|---|---|
| `BindingDocumentCompiler` lowers YAML into canonical IR: assignment and configuration maps are sorted, defaults are materialized, CEL source is replaced by lowered IR | The editor model must be the **authored document**, not IR. IR cannot be decompiled into an editable document without inventing text. |
| The capability-manifest `yano-x-binding-graph-v1` metadata only names edges | Retained as the read-only viewer input. Editing never reconstructs from it; the new authoring catalog is built first. |
| Java parses YAML with Jackson/SnakeYAML (YAML 1.1 resolution). Probed on 2.21.4: `017` → 15, `0x1F` → 31, `1_000` → 1000, `+5` → 5, `yes`/`on`/`True` → `true`, `~`/`Null` → null, `1.5` → double, raw U+0085 inside a quoted scalar folds to a space, `\/` is an invalid escape | A browser parser that guessed YAML types would silently change values. Studio accepts only an unambiguous subset (C4) and a differential test pins it against Jackson. |
| Existing CLI JSON contains Java longs as JSON numbers (for example fixture `expiresAt: 9223372036854775807`, receipt heights) | Studio parses every JSON input with a lossless parser; new tooling schemas carry int64 as decimal strings. |
| Descriptors are obtained by constructing a kernel with the component's configuration under a chain context (`BindingCatalogSession.kernel`) | Descriptor snapshots are keyed by machine, normalized configuration, context digest and catalog fingerprint (C1). |
| Profile-construction errors (`BindingProgram`) cross the plugin class-loader boundary only as message text; the CLI currently maps them to `$.bindings[i]` by searching the text for `binding '<id>'` | Structured diagnostics come from the same Java code linked into devtools, attached only when the authoritative catalog failure has the identical message (C3). The browser never parses messages. |
| The function catalog, limit maxima and baseline event schema are literals inside the compiler/runtime | They are exported from single Java definitions with conformance tests, not re-typed in JavaScript. |
| `BindingReceiptV1` records `(bindingId, failedClause)` per considered binding and a step status; a `PLANNED` step in a rejected receipt did not commit | Receipt display is derived from canonical bytes decoded by a bounded decoder and cross-checked against the Java decoded view (C6). |
| The plugin catalog fingerprint covers bundle ids, versions and complete-JAR digests | Replaced bundles change the catalog identity recorded in catalogs and reports. |

## 3. Milestone plan

Every milestone ends with focused tests, one independent architecture/security
review and one independent implementation review, reconciliation, re-validation
and an evidence entry below.

### M0 — tooling contracts (Java/devtools first)

1. `appchain bindings catalog [document] --plugins-directory --context`
   exporting `yano-x-binding-authoring-catalog-v1` (C1) from real kernels via
   `PluginProviderRegistry`/manifests; ordered-log through the existing builtin
   branch. Function, expression, limit, baseline-event and receipt-code tables
   come from single Java definitions.
2. `--report <file>` for `compile`, `validate` and `dry-run`, writing
   `yano-x-binding-report-v1` (C2) while stdout, stderr and exit codes stay
   byte-for-byte unchanged.
3. Structured diagnostics `BindingDiagnosticV1` (C3) for compiler, profile
   construction, JSON input and fixture failures, with stable codes.
4. Lossless int64 rules (C4), receipt/view consistency (C6), tooling limits (C7)
   and unsupported-import behaviour (C8) specified with golden files.
5. Representative corpus covering every ADR-031.1 construct, including a custom
   kernel and a configuration-dependent descriptor.

Gate: no handwritten duplicate machine/event/command inventory; golden and schema
tests for unknown versions, replaced bundles, malformed/oversized data and int64
extremes; existing CLI unit, integration and packaged tests still pass unchanged.

### M1 — guided static authoring (Studio)

Strict YAML subset parser/emitter with source spans, lossless JSON, draft model
and edit operations, catalog import and invalidation, component/binding forms,
typed mappings, advanced text inspectors, ordered lists, synchronized graph with
a textual equivalent, draft reset, safe document/blueprint import and export,
optional layout sidecar, registry-to-audit and approval-to-audit starters.

Gate: keyboard-only completion in a real browser; no silently dropped constructs
or unrelated blueprint changes; Java-compiled IR/profile identical for no-op round
trips; reordering changes identity; moving a node does not; unsupported imports
fail closed or open read-only.

### M2 — authoritative validation and explanation (Studio + CLI)

CLI handoff instructions with fixed safe filenames, report import, stale detection,
diagnostic navigation, receipt visualization, consecutive multi-block rehearsal
sequences including explicit empty blocks.

Gate: exported documents compared through the real compiler and engine; successful
cascades, false conditions, mapping/evidence errors, rollback, budget exhaustion,
replay, trace truncation, changed inputs/catalog, forged and mismatched reports;
no outcome implies an unobserved commit; no network submission, plugin install or
effect is triggered by file import/export.

### M3 — distribution, documentation, qualification

Package editor, starters and generated first-party catalog in the Studio ZIP, the
JVM distribution and the docsite; tutorials and reference pages in `docs/`;
regenerated site imports; aggregate Java/tooling, Studio unit and browser/a11y,
corpus, hostile-input, docsite/link and packaged-launcher gates against one exact
host/X identity; release smoke; fresh isolated three-node acceptance comparing an
editor-exported document with its CLI-authored equivalent.

## 4. M0 contracts (revision 3, after contract and implementation reviews)

Revision 1 was reviewed by an independent architecture/security reviewer and an
independent implementation-feasibility reviewer (§5). Revision 2 reconciled every
finding. Revision 3 records the refinements made after the two independent M0
implementation reviews (§5). All contracts are tooling contracts: none is consensus data, none
changes IR, profile, receipt, proof or wire bytes, and none adds authority.

### Common rules

- **Typed scalars.** `{type:"integer",value}` with canonical decimal text (no `+`,
  no leading zeros, no `-0`), `{type:"text",value}` (no Unicode normalization),
  `{type:"bytes",hex}` (lowercase), `{type:"boolean",value}`.
- **int64.** Every signed 64-bit domain value in a new schema is canonical decimal
  text. Only bounded ordinals, indexes and counts below 2^31 are JSON numbers.
- **Identity.** `producer {tool, version, jarSha256|null}` and
  `host {version, coreApiJarSha256|null, runtimeJarSha256|null}` identify the exact
  tool and host code, including SNAPSHOT/local builds; `catalog {fingerprint,
  pluginApi {major, level}, bundles [{id, version, digest, digestMode}]}` identifies
  the plugin bytes. Equal identities establish matching inputs, never provenance.
- **Authoring environment.** Descriptor construction uses the existing projection:
  state-identity settings plus `machines.<machine>.*` component settings, the
  explicit consensus profile, a membership view constant at every height,
  observation disabled and no child resolver. These fixed parameters are recorded
  as `authoringEnvironment: "yano-x-binding-authoring-environment-v1"`.

### C1. Authoring catalog `yano-x-binding-authoring-catalog-v1`

`appchain bindings catalog [document] --plugins-directory <dir> --context <ctx>
[--machine <selector>]... [--all]` writes JSON to stdout (at most 8 MiB; overflow
fails closed, never truncates).

- **Enumeration without construction:** every `AppStateMachineProvider` selector from
  `names(...)` plus the host builtin `ordered-log`, with bundle provenance.
- **Probing is explicit:** the components of a supplied document (with their exact
  authored configuration), each `--machine` selector (empty configuration), or every
  selector with `--all`. `declarative-composite` is never probed (nesting is
  rejected). A `--machine` value that is not a binding identifier
  (`[a-z][a-z0-9-]{0,62}`) is a usage error; any other selector that is not an
  identifier is listed with `composable: false` and never constructed. The 256-instance
  bound is checked before any provider is constructed. Construction and descriptor
  failures, including `LinkageError`, assertion and stack-overflow errors, are recorded
  per probe and never abort the export; only JVM resource exhaustion propagates.
- **Instances, not machines, carry schemas:** each probe records
  `authoredConfiguration` (exact typed map), `normalizedConfiguration`, its own
  `configurationDescriptor`, `events`, `commands`, `rawBodyTarget`,
  `readParticipants` (actual component ids), `applicationVersion` and a status:
  `available`, `requires-configuration` (constructed, but normalization of the
  authored map failed), `construction-failed`, `descriptor-failed` (constructed, but a
  kernel or descriptor callback failed) or `not-composable` (no kernel, nested
  composite or non-identifier selector). The configuration descriptor comes from the
  authored-configuration kernel, exactly as the compiler normalizes; every other
  descriptor comes from a kernel constructed with the normalized configuration, which
  is what compile-time typing and the profile use.
- **Studio performs no normalization.** A draft component uses an instance only when
  machine id and authored configuration are exactly equal as typed maps
  (order-insensitive). Anything else is "not described — export a catalog for this
  document". An empty-configuration descriptor may render a form, labelled as such.
- **Invalidation:** any machine/configuration edit, catalog switch or identity change
  marks affected descriptors unmatched and clears report associations. A draft binds to
  one catalog's `(context sha256, plugin-catalog fingerprint)`; lookups against any
  other catalog return nothing (`findInstance(..., expected)`).
- **Language tables** come from one Java tooling definition verified exhaustively
  against the unchanged runtime: functions (arity, per-position types, homogeneous
  arguments, `opaque` result for `cbor-field`), CEL operators, limits (wire order,
  defaults, maxima), structural bounds, baseline-event schema and receipt codes.
- **First-party snapshot:** generated by `regenerateStudioFixtures` from the
  first-party composable bundles with the shipped synthetic tutorial context through
  the packaged launcher; it carries the full identity of the build that produced it.
  Archives are reproducible, but that identity changes whenever devtools or bundle
  sources change and it covers only the three first-party bundles, so Studio labels
  it a reference catalog for the tutorial context only. Reports from a user's own CLI
  and plugin directory will not match it; authoritative matching needs the user's
  own `bindings catalog` export, which the handoff runs first. `StudioFixturesIT`
  drift-checks descriptor content and language tables with identity digests masked.
  The task refuses Maven Local, internal or custom Yano repositories and SNAPSHOT
  versions. The distribution test
  `shippedStudioCatalogIsWhatTheArchiveLauncherExports` (M3) requires the shipped
  snapshot, identity included, to equal what the final archive's launcher exports.

### C2. Report envelope `yano-x-binding-report-v1`

Written only with `--report <file>` on `compile`, `validate` or `dry-run`.

- Without `--report`, stdout, stderr and exit codes are unchanged. The usage text
  gains the `catalog` form, the `--report` option and one explanatory line (additive;
  every historical line is kept in order). `CliCompatibilityIT` enforces this against
  outputs captured from the committed pre-ADR-031.2 launcher. Report-only values
  (profile identity, prior post-state digest) are computed so that a failure yields
  `null` and never changes the outcome, and the profile-failure explanation runs only
  when `--report` is given.
- The report is written for exit 0 and exit 2 (never for usage 64 or unreadable
  input 74), **before** stdout is printed, to a same-directory temporary file with
  owner-only permissions where supported, then atomically moved into place. A report
  path that is the same file as an input, or inside the plugin directory, is a usage
  error. A write failure or a report above 16 MiB exits 74 with no stdout.
- `operationOutcome: "completed" | "failed"` describes the command, not cascades.
- `inputs` lists, in read order, `{role, state: read|not-read|oversized, bytes,
  sha256}` for `document`, `context`, `fixture`, `priorResult`. Digests cover the
  exact bytes that were strictly decoded and parsed. An absent digest never matches.
- `result` (success): `irHex`, `irSha256`, `profile {digestHex, executionVersion}`
  (digest from the catalog-created machine's `activeProfileDigest`, as project
  rendering does), `counts`.
- `rehearsal` (dry-run): `continuationOnly`, `assumptions {height, timestamp,
  stateRootHex, pendingEffects, fromPriorResult}`, `priorPostStateSha256`,
  `postStateSha256` (canonical digest over sorted physical entries), and per source
  message `{messageIndex, messageIdHex, topic, disposition, receiptHex, receipt}` where
  `disposition` is `executed`, `replay-existing-receipt` (receipt key present before
  execution; the receipt is **not** this block's outcome) or `duplicate-in-fixture`.
  Effects carry `expiryBlocks` as decimal text and are linked to steps by exact
  `scope == "binding/" + messageIdHex`. No physical post-state is included.
- `receiptCodes` travels in the report (from its producer), not from the catalog.
- Studio reports match a draft only when producer, host and catalog identities,
  context digest and the digest of the bytes Studio would export **now** are equal;
  rehearsal matching additionally needs fixture digests or the post-state chain.

### C3. Diagnostics `BindingDiagnosticV1`

`{code, severity:"error", message, detail?, detailMayContainInput, location}`

- `code` belongs to a closed documented catalog; `message` is controlled template
  text. Studio displays its own generated copy of the controlled text
  (`binding-diagnostic-codes.mjs`, drift-checked against Java) and shows a report's
  `message` only as reported text. `detail` is the bounded historical text with
  absolute paths redacted (paths under the user's home, working or temporary
  directory first, since they may contain spaces; then POSIX, drive-letter and UNC
  shapes). YAML, CEL, JSON, provider, kernel, context, fixture and profile texts set
  `detailMayContainInput`. Jackson JSON errors use a code plus structured path only.
- `location {input, pathSegments[], path, line, column, componentIndex, setting,
  bindingIndex, bindingId, clauseIndex, part, targetField, argumentPath[],
  expressionLine, expressionColumn}`; positions are one-based UTF-16 code units and
  are omitted when the source contains CR, NEL, LS or PS line breaks.
  The compiler tracks path segments, so names containing `.` are unambiguous.
  Indexes, `setting` and `part` are derived by position in the document shape, never
  from segment names elsewhere. `part` is one of `component`, `component-config`,
  `binding`, `source`, `source-event`, `condition`, `expression`, `lookup-key`,
  `lookup-operand`, `target`, `target-command`, `target-field`, `mapping`,
  `raw-body`, `effect`, `limits`; `BindingValidationException` uses the same names.
  IR input (`--ir`) has no authored document, so its locations carry only IR indexes,
  names and parts.
- Compiler failures carry code and segments as exception fields; historical messages
  are byte-identical.
- Profile construction: `BindingProgram` throws an `IllegalArgumentException`
  subclass carrying code and location with **byte-identical messages** (decision D6).
  Only after the authoritative provider fails, devtools reconstructs with its linked
  `DeclarativeCompositeProvider.entry` under the same context; the structured
  location is attached only if its message equals a message in the provider's bounded
  cause chain (after known host activation wrappers) and the catalog's composite
  bundle version equals the linked version. Otherwise `PROFILE_CONSTRUCTION_FAILED`
  without location. The explanation runs only for report requests and is contained
  (only JVM resource exhaustion escapes). A plain `IllegalArgumentException` raised by
  a selected kernel's descriptor callbacks is classified `KERNEL_CONTRACT_INVALID`
  without a part, and the original exception is kept as suppressed.

### C4. Lossless int64 and YAML typing

- Studio parses every JSON input with the lossless parser (BigInt integers, no
  fractions/exponents, duplicate names rejected) using per-input limit profiles equal
  to the CLI's (depth 48, 2,097,152-character strings, 32-character numbers).
- Studio YAML profile `yano-x-studio-yaml-v1` (implemented, see evidence): block and
  flow collections (multi-line flow allowed with deeper continuation lines), single-line
  scalars, comments, one optional bare leading `---`. Plain scalars: canonical decimal
  int64, exactly `true`/`false`, or ASCII text matching `[A-Za-z_][A-Za-z0-9_./-]*` that
  is not a YAML 1.1 reserved word; everything else must be quoted. Plain keys match
  `[A-Za-z_][A-Za-z0-9_.-]*` and are not reserved words or `<<`. Refused: empty values
  (Java reads them as empty text), anchors, aliases, tags, directives, `...`, complex
  keys, block scalars, multi-line scalars, trailing commas, single-pair flow entries,
  tabs anywhere, raw C0/C1/DEL, U+2028/2029, U+FEFF after the start, U+FFFE/FFFF, lone
  CR, lone surrogates, duplicate keys, multiple documents. Limits equal Jackson's
  token (32,768) and depth (48) semantics.
- The differential oracle runs the exact compiler parser and the blueprint parser
  configuration; every document Studio accepts must yield identical typed trees.

### C5. Draft model and layout sidecar

- Draft mirrors authored YAML exactly; no defaults, IR or normalized configuration.
- Round-trip equivalence is identical canonical IR and profile digest from the Java
  compiler under the same identities and context.
- Layout sidecar `yano-x-binding-layout-v1` (bounded integers, unknown ids ignored)
  never enters YAML, IR, profile, lock, URL or browser storage.
- Deep links never carry draft, catalog, report, fixture or layout data (tested).

### C6. Receipt consistency and explanation

- Studio renders only from canonical bytes decoded by its bounded strict decoder. The
  report's `receipt` view must equal the decoded bytes field by field or the report
  is rejected. A shared valid-plus-mutation corpus pins JS/Java decoder parity.
- The receipt-code table has `origin (engine|kernel|either)`, `levels` (a non-empty
  set of `source|step|condition|mapping|effect`), `locatesLastCondition
  (always|never|ambiguous)` and `category`. Kernel rejection codes are recorded
  verbatim and may equal any framework code, so every framework entry is
  `origin: either`. Codes outside the table read "rejected (unclassified; may be the
  target kernel)".
- Studio distinguishes five assurance states: draft with local checks, matching
  report (completed), matching report that the CLI rejected, stale or unverifiable
  report, and rehearsed outcome. A rehearsal is verified only when its own inputs
  match, its fixture digest was imported, and every block it continues is verified;
  sequences are grouped by execution identity and a sequence missing its first block
  is incomplete.
- A clause location is claimed only for an `always` code on a `REJECTED` step with at
  least one condition record: the engine appends the failing `(binding, clause)` as the
  last record (the 256-record cap is checked before evaluation), while a kernel
  rejection is decided before any condition of its step is evaluated, so a
  kernel-originated rejection's step has none (`clauseLocation`).
- Display rules: `PLANNED` in a `REJECTED` receipt is "planned, not committed";
  bindings after the failure point are "not evaluated (cascade stopped)"; "not
  visited" is claimed only for accepted receipts; receipt code different from the
  failed step's code means "history truncated"; `REPLAY_OR_CONFLICT` is a
  source-level outcome; mapping failures cannot name the failing field. All
  kernel-supplied text is rendered as text with control and bidi characters escaped.

### C7. Tooling limits

| Input | Studio bound | Java bound |
|---|---|---|
| Binding YAML | 262,144 UTF-16 units, 32,768 tokens, depth 48, 131,072-unit scalars, keys of 256 units and 512 source characters (emitter and parser) | compiler (no separate scalar bound at parse); SnakeYAML implicit keys ≤ 1,024 source characters |
| Blueprint YAML | 1 MiB | renderer 1 MiB |
| Authoring catalog | 8 MiB; 512 selectors; 256 instances | exporter fails closed above 8 MiB |
| Report | 16 MiB; 4,096 messages | writer fails closed above 16 MiB (exit 74) |
| Context / fixture / continuation | 1 / 32 / 64 MiB | same as CLI |
| Layout sidecar | 256 KiB; 1,024 nodes; coordinates within ±1,000,000 | n/a |
| Rendering | 256 diagnostics; 257 steps; 256 conditions per step | contract bounds |

### C8. Unsupported and invalid imports

- Syntax-invalid YAML stays editable; the draft keeps its last valid state, is labelled
  out of date and cannot be exported as the text.
- Unsupported constructs or unknown keys open read-only with an exact location; only the
  original bytes can be downloaded.
- Catalogs/reports/layouts with an unknown schema, or a catalog whose IR version,
  function catalog or dialect differs from Studio's emitter, are rejected.
- Blueprint splicing requires the entire blueprint inside the YAML profile, unique chain
  ids, and a re-parse proving every other node unchanged; otherwise Studio offers the
  composite document alone. Studio never labels a blueprint-embedded composite
  "validated"; project rendering derives its own context and stays authoritative.

## 5. Review reconciliation and decisions

### M0 contract review (2026-09-25)

Reviewers: one independent architecture/security review and one independent
implementation-feasibility review (a separate model). Both were read-only.

| Finding | Resolution |
|---|---|
| Eager construction of every provider is broader than today's compiler path (heavy EUTxO/ZK constructors, file-reading configuration) | Enumerate without construction; probe only document components, explicit selectors or `--all`; keep the existing context projection |
| Studio-side normalization can false-match configuration-dependent descriptors (blocker) | Instance-scoped descriptors; exact typed equality of authored configuration; Studio never normalizes |
| Replayed messages show an old receipt as this block's result (blocker) | Per-message `disposition` computed in Java before execution; report-only |
| Host activation facade wraps provider failures | Compare against the bounded cause chain after known wrappers |
| Reports could be partial, unsafe to write, oversized or leak paths | Input states, atomic owner-only writes, collision checks, 16 MiB bound, redaction |
| Identity omits host implementation and devtools build | `producer.jarSha256`, `host` jar digests and version, authoring-environment id |
| Blueprint-derived context differs from explicit context files | Studio never marks blueprint composites validated; `--blueprint` context derivation deferred |
| YAML subset gaps (empty values, keys, negative text rule, characters, name length, blueprint parser) | Positive whitelists, refused empty values, character list, blueprint-parser oracle; the Java blueprint parser's missing alias pre-scan is recorded as pre-existing and unchanged |
| Structured profile locations need a runtime change; dotted names make path strings ambiguous | Decision D6; compiler path segments |
| Receipt codes cannot distinguish origin and clause certainty | Table columns and display rules in C6 |
| Tables replacing runtime switches could change consensus behavior | Tooling-only tables with exhaustive conformance tests; runtime switches untouched |
| `detail` text may contain values or paths | Controlled messages, redaction, `detailMayContainInput` |

| # | Decision | Reason |
|---|---|---|
| D1 | Report as a side file (`--report`) | Keeps every existing stdout/stderr/exit consumer and `--prior-result` chaining unchanged |
| D2 | Exact-byte SHA-256 input digests plus a canonical post-state chain | Unambiguous and computable in the browser without canonical JSON |
| D3 | Conservative YAML whitelist with a Java differential oracle | Avoids YAML 1.1/1.2 typing divergence and a vendored parser |
| D4 | No `--blueprint` context mode in this ADR | Keeps one context basis; project rendering stays authoritative for blueprints |
| D5 | Catalog probing is explicit (`--all` is opt-in) | Avoids running unrelated plugin constructors by default |
| D6 | `BindingProgram` failures become an `IllegalArgumentException` subclass with structured fields | Needed for exact clause/field locations; gates: identical messages, unchanged IR/profile/receipt goldens, no execution-version change, no acceptance change |
| D7 | Report-write failures, including oversize, exit 74 only when `--report` is used | New option's failure mode; existing invocations are unaffected |
| D8 | A pure-JavaScript SHA-256 in Studio | WebCrypto is unavailable on insecure origins such as `http://<LAN address>`; results are tested against Node crypto |

None of these changes ADR-031.1 semantics, expands authority or adds a privileged
service; D6 changes only the exception type thrown by existing validation.

### M1 reviews (2026-09-25)

Two independent read-only reviews: an implementation review (a separate model, 3 major and 2 minor) and an
architecture/security/accessibility review (1 major, 10 minor, suggestions). Neither found a blocker or a
boundary violation (no DOM sinks, CSP respected, no network or storage, BigInt throughout).

| Review | Finding | Resolution |
|---|---|---|
