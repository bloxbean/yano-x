# ADR-031.2: Guided Declarative Binding Editor in Studio

- **Status:** Implemented — experimental and unreleased; not a release claim. Plan, contracts, review
  reconciliation, executed evidence and remaining gaps are in the
  [implementation ledger](031.2-implementation-progress.md)
- **Date:** 2026-09-25
- **Scope:** Yano X Studio, binding authoring tools, documentation and release packaging
- **Extends:** [ADR-031.1](031.1-declarative-event-bindings-for-composite-workflows.md)
- **Related:** [ADR-031](031-composable-state-machine-foundation-and-portable-proofs.md),
  [composite profile governance](015-governed-composite-profile-evolution.md),
  [cohesive application deployment](../047-cohesive-application-deployment.md),
  [documentation site](../038-yano-x-documentation-site.md)

## 1. Context

ADR-031.1 lets application authors connect existing kernel-enabled state machines
through bounded event-to-command and event-to-effect bindings. The compiler
lowers YAML and restricted CEL into canonical IR; the existing composite engine
executes that IR with deterministic ordering, authorization, resource accounting,
atomic business changes and authenticated receipts.

This removes application-specific Java coordination, but authors still need to
discover machine selectors, event names, command fields, types, configuration,
evidence restrictions and limits. Correct YAML is not necessarily a valid profile,
and a valid profile does not guarantee a particular command will succeed.

Studio currently generates guided application blueprints and contains a
read-only binding graph viewer. The viewer imports capability metadata with
schema `yano-x-binding-graph-v1`. That metadata identifies edges; it does **not**
contain enough information to reconstruct conditions, mappings or a complete
editable program. Studio currently has no backend, secret inputs or persistent
workspace. The version-matched Java CLI remains authoritative.

The developer path should therefore become **design, validate, rehearse, explain**,
not merely “draw a graph.” A graph helps users understand their authored program;
the compiler and real execution receipts establish what it means.

## 2. Decision

Extend the existing Studio with a **guided, catalog-driven binding editor**.
Begin with accessible component and binding forms plus a synchronized graph.
Do not require a free-form canvas to complete an authoring task.

The editor is an authoring client for ADR-031.1, not a second workflow engine.
It exports the existing composite document and integrates it into the existing
application blueprint. Authoritative validation and rehearsal reuse the Java
compiler, catalog-selected providers and composite engine.

The first release remains a static application. It exchanges files with the
local CLI; it does not automatically connect to localhost, execute Java, install
plugins, hold keys, submit messages or deploy a profile. A connected local
companion is a possible later decision, not a prerequisite or an implicit part
of this ADR.

No host change, binding IR revision, consensus rule, proof format, application
version bump or new runtime plugin is required solely to provide this editor.
If implementation uncovers such a requirement, decide it explicitly rather than
burying it in tooling work.

## 3. Goals and non-goals

### Goals

1. Let a beginner build registry-to-audit and approval-to-audit flows without
   memorizing event names or manually constructing target CBOR.
2. Keep YAML and visual authoring equally usable, with safe semantic round trips.
3. Make invalid mappings, evidence restrictions, ordering and resource bounds
   visible before deployment.
4. Use the actual matching Java implementation for authoritative validation and
   rehearsal; show diagnostic locations and receipt outcomes in the editor.
5. Explain the difference between a skipped binding, a rejected cascade, a
   pending human approval and an external effect intent.
6. Preserve the existing catalog, chain identity, profile-governance and
   deployment boundaries.

### Non-goals

- BPMN compatibility, arbitrary scripts, loops or additional expression features.
- New authorization rules, synthetic signatures or a system principal.
- A browser-side consensus interpreter, CEL evaluator or independent IR encoder.
- Runtime YAML hot reload, one-click chain upgrades or migration automation.
- Node administration, deployment, wallet/signing flows, external effect delivery
  or remote plugin installation.
- Browser execution of arbitrary Java plugins or an internet-hosted compilation
  service. Public-key descriptors are data; private keys remain outside Studio.
- Reconstructing an editable workflow from the existing graph manifest alone.
- Collaborative editing, accounts, cloud storage and automatic draft persistence.

## 4. User experience

### 4.1 Guided workflow

1. Choose a release-matched authoring catalog and create a document, import an
   existing binding document, or select a composite in an application blueprint.
2. Add named component instances, select their machines and configure settings.
3. Add a binding by selecting a source instance and one of its declared events.
4. Select a target command or declared effect, then map each required field.
5. Add optional conditions, participant lookups and bounded expressions.
6. Inspect YAML and the dependency graph; export a draft for CLI validation.
7. Import a matching validation report or rehearsal result and inspect its
   diagnostics, source-message outcomes and visited steps.
8. Export reviewed YAML or an updated blueprint for the existing project workflow.

Registry-to-audit is the initial tutorial. A proposal followed by two distinct
votes and an empty block is the second. Neither tutorial manufactures real keys
or suggests that two browser users represent two consensus members.

### 4.2 Components, bindings and mappings

Use separate component and binding lists with explicit execution order. Multiple
instances of one machine remain distinct. The graph shows native event names,
target commands and effect boundaries, and selects the corresponding form.

Mapping controls offer direct fields, typed literals, documented functions and
restricted CEL text. Display source and target types, required/optional fields,
and direct-copy evidence requirements. Distinguish bytes from text; hexadecimal
bytes require an explicit bytes control. Raw-body forwarding is an advanced
option with its codec/evidence restrictions displayed, not a universal shortcut.

Display all committed limits and whether each was authored or omitted. Showing
a catalog default must not silently materialize it into the authored document.
Changing release/catalog invalidates validation and requires review of defaults.
The editor may offer conservative local diagnostics, but they are advisory;
Java remains the authority for type checking, cycles, evidence and profile construction.

Human waiting is represented by persisted component state and later source
messages, not by a synchronous “wait” edge. Effects are visibly outbox intents;
they are not atomic remote calls or an exactly-once delivery promise.

### 4.3 Accessible graph, not graph-only editing

Every action must be available through keyboard-operable forms and ordered lists.
Provide readable labels, focus management and a textual equivalent of the graph.
Do not communicate outcomes only through color. A later drag-to-connect gesture
must invoke the same edit operation as the form, not maintain a second program.

Canvas coordinates, selection and collapsed panels are presentation state only.
Keep them in an optional separately versioned layout sidecar, never in binding
YAML, IR, profile commitments or `appchain.lock`. Layout loss must not change
the workflow. No telemetry or browser persistence is enabled by default.

## 5. Authoring and catalog contracts

### 5.1 One document model; no silent semantic changes

Use one structured draft model behind forms, graph and YAML view. Preserve
component, binding, clause and function-argument order. Preserve identifiers,
explicit topics, configuration, quotas, generation heights and explicit limits.
Renaming an instance is a deliberate operation with a reference-change preview,
not an automatic correction or a layout action.

Graph layout must never topologically reorder the authored component/binding
lists. YAML assignment-key ordering is not target codec-field ordering.
No implicit conversions, inserted defaults, invented evidence or rewritten CEL
expressions are permitted. Handle signed int64 losslessly; do not pass such
values through JavaScript `Number`. This applies to JSON catalogs, reports,
fixtures, continuation files and blueprints as well as YAML. Existing CLI JSON
can contain numeric Java longs: ordinary `JSON.parse()` followed by conversion
is too late to recover rounded values. Use lossless parsing/serialization or an
explicitly versioned tooling representation at those boundaries. This is an
editor representation concern, not permission to change existing YAML, IR or
receipt scalar types.

The first release must retain all currently supported ADR-031.1 constructs.
Advanced constructs may use a text-backed inspector instead of visual controls.
If an import contains an unknown schema or unsupported construct that cannot be
preserved safely, keep the original available for download and open read-only
with a precise diagnostic. Never silently drop a field and export a partial program.

YAML parsing must reject the same forbidden constructs as the authoring contract,
including duplicate keys, aliases and multiple documents. Syntax-invalid text
remains editable but must not silently update the last valid structured draft.
Label that state clearly and do not export the older model as if it were the text.

Round-trip compatibility means equivalent canonical IR under the **same exact
compiler, catalog and context**, not identical whitespace or comments. Warn that
structured edits may reformat YAML and lose comments before the first such edit;
retain the original for explicit download. Preserve unrelated blueprint fields
and chains; if full-blueprint preservation cannot be guaranteed, export only the
selected composite document instead of rewriting the application.

### 5.2 Full authoring catalog, distinct from graph metadata

Add a versioned, data-only authoring catalog export to devtools. Its concrete
schema and CLI syntax are implementation deliverables; this ADR does not claim
that a catalog-export command exists today.

Generate it from the existing catalog-selected kernel descriptors and the
compiler's function/expression definitions. Include:

- Schema version, exact host/X build identities and relevant plugin/catalog
  fingerprints, with installed bundle identity sufficient to detect replacements.
- Selectable composable machines and their configuration descriptors/defaults.
- Event IDs and field names/types/optionality; command IDs, layouts, required
  fields, evidence classifications and raw-forwarding restrictions.
- Function signatures, applicable bounds, expression profile version and limits.
- Effect authoring descriptors from their authoritative catalogs where available;
  do not invent an effect field schema merely because a type name is advertised.

Descriptor validity must bind the normalized component configuration as well as
the chain context and exact build/catalog identity. The current descriptor bridge
constructs kernels using supplied configuration; a machine selector alone is
not a sufficient cache key. Configuration or context edits mark affected
descriptors stale/unavailable until a matching snapshot is supplied. A bundled
default snapshot does not describe arbitrary custom genesis/configuration.
Any required context-dependent descriptor must identify the context used, or be
marked unavailable until such a catalog is exported. Do not synthesize descriptors
by guessing from a capability name. Keep runtime graph metadata backward-compatible
and separate: it remains sufficient for viewing, not for authoring.

Ship a generated first-party snapshot with the matching Studio distribution and
docsite build. Permit explicit imports for a locally installed custom catalog.
Snapshots supply editing assistance, not plugin trust or runtime availability.
Fingerprint equality establishes matching inputs, not provenance. An imported
catalog is untrusted data and cannot load executable code or install a bundle.

The exporting Java process loads trusted plugins through `PluginProviderRegistry`
and manifests, exactly as existing authoring tools do. Java plugins are not
sandboxed: exporting descriptors must not be marketed as safe inspection of an
untrusted JAR. No raw provider construction or optional classpath fallback is added.

## 6. Validation and rehearsal handoff

### 6.1 Static-first operation

The editor exports the binding document and, when supplied explicitly, context
and fixture files. It shows commands for the matching local distribution's
existing `compile`, `validate` and `dry-run` paths. Do not derive local file paths
from uploaded metadata or turn document text into shell fragments. Use fixed
safe filenames in downloadable handoff instructions, with paths chosen by the user.

Add a versioned report envelope for editor consumption around the existing
results. Reuse compiler/engine APIs; do not scrape human stderr or reinterpret
execution in JavaScript. Existing CLI output consumers must either remain
supported or migrate through an explicit output-format/version option.
Preserve existing exit codes. The current CLI reports textual diagnostics;
stable codes and structured locations are new Java tooling infrastructure to
extract and qualify, not a pre-existing JSON contract to wrap.

The envelope records operation, schema, compiler/build/catalog identities,
digests of exact authoring inputs and context, and diagnostics or execution
results. Successful compilation adds canonical IR/profile identities where
available. Failure reports still identify the attempted inputs. Rehearsal
reports additionally bind fixtures, continuation inputs and execution identity.
Specify canonical digest inputs and encoding in the report contract and tests.

Show these distinct states:

| UI state | Assurance |
|---|---|
| Draft / local checks | Editor assistance only; no Java validation |
| Imported matching CLI report | Report says the exact inputs validated under the named catalog |
| Stale report | Document, context, catalog or relevant fixture changed; previous result does not validate this draft |
| Rehearsed source outcome | Real engine result reported for the identified, assumed fixture inputs |

Imported reports can be forged. Label them as imported, unauthenticated artifacts,
not trusted compiler attestations, finality certificates or deployment approval.
Byte matching prevents accidental stale association; it does not authenticate
the report producer. Project rendering must independently revalidate regardless
of Studio's badges. A mismatch may be viewed as historical evidence but must not
decorate the current graph as its validation result.

### 6.2 Diagnostics and execution explanation

Diagnostics include stable machine-readable codes and structured locations:
component setting, binding ID/index, clause, target field or expression position
where known. Reuse a shared Java diagnostic contract for CLI and Studio; do not
make the browser infer locations by parsing exception strings. Missing location
information is shown honestly rather than pointing at a guessed field.

Imported dry-run results retain canonical receipt bytes alongside decoded views.
The report contract must define consistency checks between those representations.
Derive the display from the canonical bytes through a bounded, version-aware
receipt decoder, or verify that every decoded field matches before rendering.
Reject contradictions and unsupported receipt versions rather than choosing a
convenient copy. Decoding an untrusted receipt does not authenticate it and must
not introduce browser transition execution or change the receipt wire format.
Render source messages individually and steps in receipt ordinal order, including
derived depth, target, binding, events, condition results and failure codes.
An overall rejected receipt means planned business changes did not commit; do not
color a `PLANNED` step as committed without considering the overall result.

Distinguish false-condition skips, evaluation errors, target rejection, resource
exhaustion and unvisited edges. Receipt-capacity fallback can omit history: display
“not recorded” rather than inventing an execution trace. The existing receipt does
not contain every intermediate value; full value tracing is not assumed or added
to consensus receipts by this ADR.

Multi-block rehearsal uses the current consecutive-height continuation contract.
Show the complete scenario sequence, including empty blocks and separate voters.
Keep timestamp, assumed predecessor root and pending effects explicit. Never
present continuation state as an authenticated node export or calculate a root
using a new browser implementation.

Typed fixture assistance may be added through Java codec-backed tooling, not a
second collection of browser CBOR encoders. Initially ship public, synthetic
fixture templates and allow raw body bytes with explicit encoding guidance.
No rehearsal action submits to a node or delivers an effect.

### 6.3 No implicit local execution bridge

Initial Studio has no localhost probing, WebSocket companion or compilation API.
If a later release introduces one, it requires a separate security decision:
loopback binding alone is insufficient. Origin/Host validation, capability tokens,
CSRF/DNS-rebinding protection, bounded execution, cancellation, plugin trust,
allowed filesystem roots and secret/log handling must be resolved first.
There is no generic shell endpoint or browser-supplied plugin path in this ADR.

## 7. Blueprint and deployment boundaries

Support exporting a standalone composite document under any filename and inserting
its body into the selected `declarative-composite` chain in `appchain.yaml`.
Explain the existing lifecycle:

`bindings.yml → copied blueprint definition → Java rendering → committed IR in node configuration`

The source file is not a live include; the node does not watch it. Studio exports
intent, not authoritative lock files or validated node properties. Existing Java
project rendering creates/checks the IR/profile/catalog pins in `appchain.lock`.

Every substantive edit clears the current validation status. Comparison views
show component/binding ordering, configuration, generation heights, limits and
catalog identity changes, not only a YAML textual diff. Do not describe layout
changes as profile changes or claim semantic equivalence without compiler evidence.

A changed profile is not a deployable upgrade merely because it compiles. Existing
retained-chain reconstruction, historical executable catalog, generation and
governed-activation requirements remain. `profile-check` establishes exact profile
reconstruction only, not migration or replay safety. Studio must not offer a
button that resets retained state or regenerates genesis to overcome a mismatch.

## 8. Ownership and security

- `tooling/studio`: static editor, draft model, import/export, forms, graph,
  accessibility and report presentation.
- `tooling/devtools`: generated authoring catalog, compiler-backed diagnostics,
  report envelopes and existing CLI/project integration.
- Existing contracts/runtime modules: reused without a parallel engine; any
  additive non-consensus DTO belongs in an appropriate tooling/library boundary.
- `docs/`: tutorials and reference truth; `www/` imports them and packages Studio
  through the existing process. No hand-maintained second catalog in the site.

No new application-server product or host REST endpoint is introduced. Pure
authoring tools do not require runtime-plugin activation, while machines used
for compilation still cross the normal plugin catalog boundary.

Treat YAML, JSON, labels, expressions, reports and layout files as untrusted.
Use bounded files, nesting, strings, collections and trace rendering. Define
these numeric tooling bounds before implementation and test both edges; they
must not masquerade as new consensus limits. Render text without HTML injection;
do not execute imported markup, links, templates or expressions. Bundle assets
locally with a restrictive content policy and no runtime CDN dependency.

Do not store secrets, private keys, API credentials or context files in URLs,
analytics, browser storage or logs. Business payloads may be sensitive even when
they are not keys: imports stay in memory unless the user explicitly downloads
them. Warn before exporting context, fixture state or receipts. Provide clear
discard/reset-draft controls that affect editor memory only, never node state.

## 9. Implementation milestones and acceptance gates

Each milestone requires implementation, independent review, focused tests and
iteration before its acceptance criteria are declared complete.

### M0 — Freeze tooling contracts

Define bounded versioned authoring catalog, report envelope, structured diagnostics
and draft/layout contracts. Generate catalog data from real descriptors. Establish
representative fixtures for all current language constructs and exact build/input
identity matching, including a custom kernel and configuration/context-dependent
descriptors. Specify lossless JSON boundaries and receipt/view consistency checks.

**Gate:** no handwritten duplicate command/event inventory; schema and golden
tests cover unknown versions, replaced bundles, malformed/oversized data and
int64 extremes. Existing CLI consumers remain qualified.

### M1 — Guided static authoring

Implement component/binding forms, typed mappings, advanced text inspectors,
ordered lists, graph selection, draft reset, safe YAML/blueprint import/export and
optional layout sidecars. Ship registry-to-audit and approval-to-audit starters.

**Gate:** keyboard-only completion; no silently dropped constructs or unrelated
blueprint changes. Import/edit/export/recompile tests prove identical IR and
profile for no-op semantic round trips under matching inputs. Reordering a
binding changes identity as expected; moving a graph node does not. Unsupported
imports fail closed or remain explicitly read-only.

### M2 — Authoritative validation and explanation

Add CLI file handoff, report import, stale-result detection, diagnostic navigation
and receipt visualization. Support consecutive multi-block approval rehearsals
and explicit empty blocks. Keep all offline-assurance limitations visible.

**Gate:** compare exported documents through the real compiler and engine.
Cover successful cascades, false conditions, mapping/evidence errors, rollback,
budget exhaustion, replay, trace truncation, changed inputs/catalog and forged
or mismatched reports. UI outcomes must not imply unobserved steps committed.
Prove file import/export triggers no network submission, plugin install or effect.

### M3 — Distribution, documentation and qualification

Package the editor/catalog in the normal Studio/JVM distribution and docsite.
Publish beginner-to-advanced tutorials including separate-file versus inline
blueprint lifecycle, real actor-proof prerequisites and upgrade limitations.

**Gate:** Java/tooling tests, Studio unit and browser/accessibility tests,
import/round-trip corpus, hostile-input tests, docsite/link checks and packaged
launcher contracts pass against one exact host/X build identity. Complete the
normal distribution/release smoke gates before release. Run a fresh isolated
multi-node workflow acceptance scenario showing that an editor-exported document
has the same profile, receipts and finalized state as its CLI-authored equivalent;
no retained deployment or preprod transaction is required for this test.

All milestones are **not started** at proposal time. This ADR authorizes no claim
that the editor, new catalog export or report schema already ships. A free-form
canvas and connected companion are not required to finish these milestones.

## 10. Alternatives considered

| Alternative | Decision |
|---|---|
| Keep only YAML plus a read-only graph | Retain as a supported path, but it leaves field discovery and failure explanation difficult for beginners |
| Start with a full drag-and-drop BPMN designer | Reject: adds scope and suggests unsupported waits, loops or transactional boundaries |
| Implement compilation and execution again in JavaScript/WASM | Reject for this scope: creates consensus-semantic duplication and a second compatibility burden |
| Embed a raw YAML editor and call it graphical authoring | Insufficient: does not address typed mapping or catalog discovery |
| Require a backend or localhost service from the first release | Defer: expands installation and security scope unnecessarily; explicit file handoff preserves static Studio |
| Make the graph the persisted executable format | Reject: existing composite YAML/IR remains authoritative; layout is nonsemantic |

## 11. Consequences

Developers gain discoverable, guided composition while retaining portable YAML,
reviewable source control and the existing compiler/runtime authority. The most
valuable capability is explaining a real rehearsal outcome in its authored graph,
not the graph itself.

The costs are maintaining a lossless editor model, release-matched descriptor
exports, structured tooling diagnostics and a substantial round-trip/security
test corpus. File handoff is less seamless than a connected IDE, but it avoids
shipping a privileged local service before its trust boundary is designed.

This decision improves authoring ergonomics, not the execution language's power
or production-readiness guarantees. New domain rules still require appropriate
plugins; authorizations, consensus limits, proofs and governed upgrades are not
replaced by a visual workflow.
