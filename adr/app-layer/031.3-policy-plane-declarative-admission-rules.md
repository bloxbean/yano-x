## 0. In plain words

An integrator who builds an app chain from stock machines through configuration can already
say *what happens next* (bindings, ADR-031.1). They cannot yet say *what is not allowed here*:
"transfers above 10,000 are refused", "only registered suppliers may place orders", "the audit
trail accepts entries only from the approval workflow", "only actors holding the `operator`
role may write this collection". Today each of those needs a forked machine or a provider JAR.

This ADR adds the **policy plane**: named, parameterized **admission rules**, written in the
same restricted CEL as bindings, compiled into the same committed IR, and evaluated by the
same cascade engine. A rule can only **deny**. It never grants authority, never rewrites a
command, and never replaces the machine's own validation. Every command that enters a
component, whether a client submitted it or a binding derived it, passes the rules attached
to that component. Rules may also read **verified facts** — actor, organization, and roles
that the target kernel itself established by verifying signed evidence. A denial makes the
whole source message a no-op with an authenticated receipt, exactly like every other
cascade rejection.

The same change gives binding conditions and mappings the `context.*` inputs.

**Scope: admission only.** This ADR introduces one policy point. Other candidate policy
points are either binding features that already exist or separate future decisions (§16).

## 1. Decision summary

1.1. Establish the **policy plane** as a distinct layer of a declarative composite, between
authority (host envelope verification, the sender principal, and evidence verified by
kernels) and the transition kernel's decision. Its first and only policy point is
**admission**. The plane is a contract over the existing engine, not a new runtime, engine
SPI, or language host.

1.2. An **admission rule** is defined once, by id, in the composite's `rules` section. It
has a deny code, an optional command selector, typed parameters, and 1–8 clauses that must
all hold. Rules are **attached** to components with concrete parameters. One rule can be
attached to many components, and one component can carry several rules.

1.3. Rules are **forbid-only** and combine by conjunction. The kernel's own `admit` and
`decide` remain the permit. There are no allow rules, priorities, overrides, or exemptions.

1.4. Rules read a **closed input view** through scoped fields:

- `command.*`: the data fields of the selected command, decoded through its descriptor.
- `params.*`: the attachment's parameters.
- `config.*`: the component's normalized configuration.
- `context.*`: `height`, `sender`, `derived`, `depth`, and `binding`.
- `facts.*`: scalar facts that the component's kernel declares and establishes by its own
  verification.

Rules may also use lookup clauses against declared components through the cascade overlay.
Rules cannot read evidence fields, the block timestamp, event payloads, or anything
node-local.

1.5. Rules are evaluated inside `EventBindingWorkflow.decide`, for every step at every
depth, in two slots:

- **Admission slot.** Rules that do not read `facts.*` run after codec decode and the
  kernel's two `admit` hooks, and before `workRequest`. A command denied here reserves no
  crypto work.
- **Verified-fact slot.** Rules that read `facts.*` run after `kernel.decide` has
  **approved**, and before the plan joins the cascade. Every kernel has finished
  verification at that point, including kernels that verify signatures inside `decide`.

Derived commands therefore cannot bypass a target's rules.

1.6. A denial is a step rejection with code `ADMISSION_RULE_DENIED`. The cascade is a
per-source-message no-op (ADR-031.1 §5.6): no plan commits, no effect is emitted, and work
already charged stays charged. The receipt records every rule evaluated at every step, the
failing clause, and the rule's deny code.

1.7. A new additive Yano host contract lets a kernel declare and supply verified facts:
`RuleFact` and two `TransitionKernel` default methods (§5.5). This raises the plugin API
level to 12. In the first release, the governed `authenticated-map` kernel and the
`governed-role-approvals` kernel implement it. Facts are kernel-owned outputs of
verification. Nothing else — not bindings, commands, configuration, or other plugins —
can produce them.

1.8. **Static rules** are those that read only `command.*`, `params.*`, and `config.*`, with
no lookups. They also run at local ingress, before pooling, as an advisory rejection.
Block-time evaluation is authoritative for all rules.

1.9. Rules, attachments, and parameters are part of the committed binding IR, and therefore
of the composite profile bytes and the `~composite/profile/v1` digest. A rule change on a
running chain is an ADR-015 profile-epoch transition. No node configuration can add,
remove, or alter a rule.

1.10. Authority is unchanged from ADR-031.1 §5.11. `context.sender` is always the
originator. Rules can distinguish direct from derived arrivals, and can require verified
roles where a kernel verified them. They cannot create, widen, or delegate authority.

1.11. Binding conditions and mappings gain `context.*`, which describes the step that
produced the event. Evidence fields still accept only direct event-field copies.

1.12. **Versioning.** All identifiers stay at v1: `yano-x-binding-ir-v1`, `yano-x-cel-v1`,
`BindingReceiptV1`, and the query subjects. Their layouts are amended in place (§5.14). Every
amended structure changes its array arity, so bytes that contain one fail decode instead of
being misread. Every IR document and every receipt contains an amended structure (a receipt
always records at least its source step). `EXECUTION_VERSION` moves to `1.2.0`. Experimental declarative
chains and fixtures are re-created; no migration is offered.

1.13. During development, Yano X consumes the host change from a local Maven publication of
Yano (`0.1.0-pre18-SNAPSHOT`, `-PuseMavenLocal=true`). A published Yano release must replace
it before any Yano X release that includes this ADR.

## 2. Context

### 2.1 What exists today

- ADR-031.1 is implemented as an experimental profile. A `declarative-composite` provider's
  single event-binding workflow executes a canonical, committed `BindingIrV1`.
- CEL is an **authoring** language. `dev.cel:compiler` is a dependency of `tooling/devtools`
  only. `gradle/libs.versions.toml:21` records "Authoring parses/type-checks CEL; consensus
  uses our versioned IR interpreter, not CEL runtime". `BindingExpressionCompiler` lowers an
  allowlisted, type-checked AST into `BindingExpressionV1`. Consensus evaluates only that IR
  in `BindingExpressionEvaluator`, with checked int64 arithmetic and per-cascade and
  per-block work budgets.
- Expressions can reference only `event.<field>`. The compiler declares only `event.*`
  variables, and lowering rejects any other identifier.
- Every cascade step, source or derived, goes through `EventBindingWorkflow.decide`
  (`EventBindingWorkflow.java:396-419`), in this order:
  1. codec decode;
  2. `kernel.admit(command)` and `kernel.admit(command, context)` (L407);
  3. `workRequest` reservation (L410);
  4. `facts` and `decide` (L418).

  A failure becomes a `BindingFailure`, the cascade is a no-op, and a `BindingReceiptV1` is
  written.
- Local ingress runs `EventBindingWorkflow.validate` (L86): route, work estimate, codec
  decode, and the stateless `kernel.admit(command)`. It is advisory; followers do not run it.
- Kernels publish `CommandDescriptor`s (layout, opcode, and typed fields with a DATA or
  EVIDENCE role) and a `ConfigurationDescriptor`. The engine already encodes mapped commands
  from these descriptors.
- Lookup clauses support `EXISTS`, `ABSENT`, `EQUAL_LITERAL`, and `EQUAL_EVENT` only
  (`BindingIrV1.java:124`). They cannot yield a value for comparison.
- Role verification is kernel-internal, and kernels place it differently:
  - The governed map verifies actor evidence while building facts, in
    `AuthenticatedMapTransitionKernel.facts` → `AuthenticatedMapDirectAuthorizer.authorizeReserved`
    → `RoleAuthorizationCapability.verifyDirect`.
  - `governed-role-approvals` snapshots actor eligibility in `facts` and verifies the actor
    signature inside `decide` (`ActorApprovalProcessor.java:217`).

  Neither exposes its verified actor, organization, or roles to anything outside the kernel.

### 2.2 What is missing

A configuration-only integrator has no way to constrain a stock machine per deployment. The
same `balances` machine should be usable with a 10,000 transfer limit in one product and none
in another. The same `doc-trail` should be usable as an audit log that accepts entries only
from an approval binding. A governed collection should be able to require a deployment role
beyond the one its genesis policy names. Today these need a provider JAR (ADR-022 §3.15).

The binding language cannot do this. A binding condition decides whether a binding *fires*.
It cannot stop a command that a client submits directly, or one that a different binding
derives.

### 2.3 What changed from the withdrawn draft

The Yano draft described the right problem and separation of concerns. It was written as
instructions to a coding agent and conflicted with accepted decisions. This ADR keeps its
intent and replaces its mechanisms:

| Draft proposal | This ADR | Reason |
|---|---|---|
| A CEL runtime behind a language-neutral `PolicyEngine`; WASM or other engines later | Rules compile to the same canonical IR and run in the existing interpreter | CEL does not run in consensus (§2.1); ADR-031.1 §5.13 and §13.6 |
| Policy inserted into the Yano host execution path | Evaluated in `EventBindingWorkflow.decide`; the host contributes only a kernel fact accessor | The host treats `apply` as opaque; ADR-031 §5.3 and §13.4 reject a runtime authorization hook |
| `TrustedFact` model with an open `TrustedFactProvider` SPI | Closed, kernel-declared `facts.*`, established by the kernel's own verification (§5.5) | No provider registry; ADR-031 §6.4 defers an open policy SPI |
| `originalPrincipal`, `delegatedAuthority`, `systemAuthority` | `context.sender` is the originator; `derived`, `depth`, and `binding` describe arrival | ADR-031.1 §13.5 rejected synthetic principals and delegation for v1 |
| Admission, permission, filtering, guards, derived values, postconditions | Admission only (§3.2, §16) | Permission is admission with verified facts; filtering, guards, and derived values are binding constructs; postconditions need their own decision |
| `stateMachines.<id>.policies` node configuration | Committed IR section, ADR-015 governed | ADR-031.1 §1.12: local configuration cannot change consensus behaviour |
| Example `auth.approvals.exists(a, ...)` | Not expressible; approvals stay evidence verified by the target; verified actor facts are scalars and a role set | The dialect excludes comprehensions; approval verification belongs to the kernel (ADR-031.1 §5.11) |

## 3. Goals and non-goals

### 3.1 Goals

1. Let a configuration-only integrator deny commands to any component of a declarative
   composite by deployment-specific rules, without changing or forking the machine.
2. Make rules reusable: define once, attach to several components with different parameters.
3. Guarantee that every command entering a component, direct or derived, passes that
   component's rules.
4. Allow rules over **verified** actor identity, organization, and roles where a kernel
   verifies them, without letting anything but that kernel establish those facts.
5. Keep rules deterministic, bounded, statically type-checked, committed, and governed.
6. Make every denial explainable from the authenticated receipt and reproducible in
   `bindings dry-run`.
7. Reuse the existing compiler, IR, interpreter, budgets, receipts, and governance. Add no
   runtime dependency.

### 3.2 Non-goals

- Any policy point other than admission (§16).
- Replacing kernel admission, validation, invariants, or authorization.
- Verifying signatures, approvals, credentials, or proofs in rules.
- Granting, widening, or delegating authority, and allow rules or exemptions.
- Transforming, rewriting, or routing commands. That is the binding plane.
- Rules on effect targets, events, or query responses.
- A pluggable policy engine, fact-provider SPI, or second language.
- Policy for standalone (non-composite) machines selected with `state-machine=<id>`.
- Compatibility with binding IR, expression, or receipt bytes produced before this ADR.

## 5. Target architecture

### 5.1 Layering on the real components

```text
Client command
   │  host: envelope signature + membership              (authority, Yano host)
   ▼
EventBindingWorkflow.validate                             (advisory, local ingress)
   │  decode → kernel.admit(command) → static admission rules
   ▼
pool → block → EventBindingWorkflow.apply → cascade(source)
   │
   │  for every step, depth 0 and derived:
   │    decode                          → MALFORMED_*
   │    kernel.admit(command)           → ADMISSION              (machine bounds)
   │    kernel.admit(command, context)  → ADMISSION
   │    ► admission slot: rules without facts.*  → ADMISSION_RULE_*   (policy plane)
   │    workRequest reservation         → CRYPTO_WORK_EXCEEDED
   │    kernel.facts + kernel.decide    → kernel codes           (evidence, roles, invariants)
   │    ► verified-fact slot: fact rules         → ADMISSION_RULE_*   (policy plane)
   │    plan joins cascade; events → bindings (conditions, mappings)  (binding plane)
   │    derived commands re-enter this loop
   ▼
commit all plans, or none; write BindingReceiptV1
```

Authority establishes who is acting and what evidence is valid. The policy plane decides
whether this deployment admits the command. The kernel decides whether the transition is
valid and what it writes. Bindings decide what happens next. Each layer has one owner, and a
later layer cannot weaken an earlier one.

The two slots exist because rules have two kinds of input:

- **Submitted inputs** (the command, parameters, configuration, context, and lookups) are
  available before any expensive work. Rules over them run early, so a denied command
  reserves no crypto work.
- **Verified facts** exist only after the kernel has verified evidence, and one stock kernel
  verifies inside `decide` (§2.1). Fact rules therefore run only after an approved decision.
  A command with a bad signature is rejected with the kernel's own code, never with a rule
  code that would disclose or misattribute role information.

### 5.2 Rule model

```yaml
rules:
  - id: transfer-limit               # [a-z][a-z0-9-]{0,62}, unique across rules and bindings
    command: transfer                # optional; omitted = every command of the component
    deny: TRANSFER_LIMIT_EXCEEDED    # [A-Z][A-Z0-9_]{0,62}, not starting with ADMISSION_RULE_
    params:
      maxAmount: { type: integer }   # integer | text | bytes | boolean | binding; optional default
    require:                         # 1..8 clauses; all must hold
      - expr: 'command.amount > 0 && command.amount <= params.maxAmount'
```

A `binding` parameter evaluates as text. At construction, its value must be the id of a
binding in the same profile whose command target is the attached component. A typo in an
"only through binding X" rule therefore fails construction instead of silently denying every
command.

A clause is either an expression clause (`expr:`, a boolean `yano-x-cel-v1` expression) or a
lookup clause (`lookup:`). A lookup clause reuses the binding lookup form, with key sources
drawn from the rule scopes:

```yaml
      - lookup: { component: suppliers, key: { context: sender }, exists: true }
```

Scoped sources extend the existing source forms (`field`, `literal`, `fn`, `expr`) with
`{ context: <name> }`, `{ command: <name> }`, `{ param: <name> }`, `{ config: <name> }`, and
`{ fact: <name> }`. `{ field: <name> }` keeps meaning an event field and is legal only in
bindings. Each scoped source is legal only where its scope is (§5.3).

Lookup expectations are `exists`, `absent`, `eq: <literal>`, and `eq: { <scope>: <name> }`.
They use the `eq` key of the existing binding lookup form, so rules and bindings share one
spelling. The component named by a lookup must exist in the profile.
Lookups read through the cascade overlay, so they see writes from earlier steps of the same
cascade, exactly as binding lookups do. A lookup key that fails to build (wrong type, over
limit, or invalid for the owner's `lookupKey`) is a rule error, `ADMISSION_RULE_ERROR`.

A component attaches rules in evaluation order:

```yaml
components:
  - id: wallet
    machine: balances
    admission:
      - rule: transfer-limit
        params: { maxAmount: 10000 }
```

Every parameter without a default must be supplied. Parameters are normalized with defaults
filled before encoding, as component configuration is (ADR-031.1 §5.3), so stating and
omitting a default produce identical bytes. Parameter names are CEL identifiers,
`[a-zA-Z][a-zA-Z0-9_]{0,62}` other than CEL reserved words (`in`, `null`, `true`, and so on),
because rules reference them as `params.<name>`. Rules are sorted by id and parameters by name,
both by unsigned UTF-8 bytes. Deny codes may not start with `ADMISSION_RULE_`, which is reserved
for the engine's own codes (§5.8).

Every rule must be attached to at least one component. A rule is type-checked against the
kernel of each component it is attached to, so an unattached rule cannot be checked and fails
construction with `RULE_UNATTACHED`.

A rule is type-checked **per attachment**, against the kernel of the component it is
attached to. The same rule can therefore be attached to two `balances` instances. Attaching
it to a machine without a `transfer` command, or a fact rule to a kernel that does not
declare the facts it reads, fails construction.

### 5.3 Inputs: expression scopes

`yano-x-cel-v1` keeps its operator set, types, error masking, overflow rules, and work
charges. This ADR amends it in three ways:

- field references carry a **scope**;
- a `TEXT_SET` value type is added, usable only through `facts.*`;
- an `in` operator is added: `<text> in <text-set>`.

Which scopes are legal depends on where the expression appears:

| Scope | Binding condition | Binding mapping | Admission rule |
|---|---|---|---|
| `event.*` | yes | yes | no |
| `context.*` | yes: the step that **produced** the event | yes, for data fields only | yes: the step being **admitted** |
| `command.*` | no | no | only when the rule names a command; DATA-role fields only |
| `params.*` | no | no | yes |
| `config.*` | no | no | yes |
| `facts.*` | no | no | yes; makes the rule a fact rule (§5.5) |

`context` fields:

| Field | Type | In a rule | In a binding |
|---|---|---|---|
| `height` | integer | Block height of the source message | Same |
| `sender` | bytes | The originator's sender, identical for every step | Same |
| `derived` | boolean | `false` for the source step, `true` otherwise | Whether the producing step was derived |
| `depth` | integer | Distance from the source step | Depth of the producing step |
| `binding` | text | Binding that derived this step; `""` for the source step | Binding that derived the producing step; `""` if it was the source |

`binding` is `""` at depth 0 so that expressions never meet an absent field. The receipt
keeps `bindingId = null` for the source step, as today. There is no `topic` field. A
component's topic is fixed, and every attachment and binding already names its component,
so a topic field would always hold the same value.

Excluded on purpose:

- **`timestamp`.** It is chosen by the proposer within bounds. Height is the house
  convention for deadlines (`deadlineHeight`, `validUntilHeight`).
- **Evidence-role command fields.** Rules cannot read them (`RULE_EVIDENCE_READ`). In the
  admission slot they are unverified, and verified outcomes are available as `facts.*`
  instead. In binding mappings, evidence fields still accept only direct event-field copies,
  never `context.*` or expressions (ADR-031.1 §5.3).
- **Event payloads in rules**, other steps' commands, receipts, and any state outside
  declared lookups.

**Why `context.*` is safe in bindings.** Every field is a consensus value that the engine
already holds for the producing step: the height, the originator sender, and the derivation
record. It adds no state read, no node-local input, and no
authority:

- a derived command still carries the originator's principal, whatever a mapping writes into
  a data field;
- evidence cannot be sourced from context;
- the baseline event already exposes the sender and topic.

Dry-run fixtures already supply context (`--context context.json`).

Scoped field references also serve as lookup key sources and as the `eq:` operand.
Stock catalog functions remain mapping and key sources only; an `expr:` cannot call them.

A CEL expression can select only fields whose names are CEL identifiers. Configuration keys and
command fields such as `value-format` or `genesis-cbor-hex` are therefore readable only through a
scoped source, for example a lookup key `{ config: value-format }`; the compiler reports an
attempt to select them with its position. `context` has exactly the five fields above, enforced
by the codec, and the `in` operator appears only in rules, because only facts have the text-set
type.

### 5.4 Command view

`command.*` is built by the engine from the step's wire body and the kernel's descriptors,
as the inverse of the existing mapping encoder:

1. **Select the command.** A kernel is **command-selectable** if either condition holds:
   - every command is `ARRAY_WITH_OPCODE`, and the opcodes are pairwise distinct; or
   - it declares exactly one command, and that command's layout is not `RAW_BYTES`.

   For `ARRAY_WITH_OPCODE`, the leading integer selects the descriptor. On a component whose
   kernel is not selectable, a rule that names a command or reads `command.*` fails
   construction with `RULE_COMMAND_UNSELECTABLE`. Duplicate opcodes are reported the same
   way; today nothing enforces opcode uniqueness. Rules without a command selector remain
   allowed. They may use `params.*`, `config.*`, `context.*`, lookups, and `facts.*`.

   `authenticated-map` (three `MAP` commands) and the ordered log (`RAW_BYTES`) are
   therefore unselectable. Rules on map components are command-agnostic and typically read
   `facts.*`. `governed-role-approvals` declares one `ARRAY_WITH_OPCODE` command, so it is
   selectable, but its only DATA field is opaque action bytes (`command.action`). The
   verified statement action is available as `facts.action`.
2. **Decode fields.** Every declared field, DATA or EVIDENCE, is decoded, by position or by
   key, into a scalar of the declared type, so that the round trip covers the whole body. Only
   DATA-role fields are exposed as `command.*`.
3. **Round-trip check.** The decoded fields are re-encoded through the mapping encoder, and
   the bytes must equal the body. If they do not, or step 2 failed, and the component has any
   command-selecting rule, the step rejects with `ADMISSION_RULE_INPUT`. This fails closed: a
   body the engine cannot classify canonically cannot be checked.

The kernel's codec has already accepted the body, so a descriptor that disagrees with its
codec is a latent bug. A kernel conformance test (Phase 2) covers every stock command whose
decoded fields the descriptor can represent. For those commands, the descriptor view of
`codec.encode(c)` must equal the codec's decoded fields and round-trip byte-exactly.

Some bodies are valid for the codec but cannot be represented by the descriptor. Their view
fails closed with `ADMISSION_RULE_INPUT`, and each kernel documents them. For example,
`balances` decodes `amount` as an unbounded `BigInteger`, while its descriptor declares a
signed 64-bit `INTEGER`. An amount at or above 2^63 is therefore refused by a
command-selecting rule. Without the rule, the kernel refuses it later.

Attaching a command-selecting rule therefore tightens a component: it also rejects bodies
the codec would accept in non-canonical form. Stock codecs already require canonical bytes;
a lenient third-party codec does not.

Building the view is charged like mapping encoding, on both work counters. At local ingress,
a body whose view cannot be built is rejected with `ADMISSION_RULE_INPUT`.

### 5.5 Verified facts (host contract)

Yano `core-api`, package `org.yanoproject.api.appchain.transition`, additive. These are the
exact signatures and Javadoc frozen in Phase 0:

```java
/**
 * One scalar fact that a transition kernel can establish by its own verification and expose to
 * declarative admission rules after an approved decision.
 *
 * <p>A fact is a kernel-owned output of verification, never an input: no binding, command,
 * configuration, or other plugin can supply one. Declaring a fact grants no authority; it only lets a
 * deployment rule deny a command the kernel already approved. The host neither evaluates rules nor
 * interprets facts; it only carries declarations and values across the plugin boundary.
 *
 * @param name identifier, {@code [a-zA-Z][a-zA-Z0-9_]{0,62}} and not a CEL reserved word, readable by rules as
 *             {@code facts.<name>}
 * @param type value type; {@link Type#TEXT_SET} values are sorted, duplicate-free text lists
 */
public record RuleFact(String name, Type type) {
    /** Frozen value types. Do not reorder: tooling exports the ordinals. */
    public enum Type { INTEGER, TEXT, BYTES, BOOLEAN, TEXT_SET }

    /** Maximum declared facts per kernel. */
    public static final int MAX_FACTS = 32;
    /** Maximum entries in one {@link Type#TEXT_SET} value. */
    public static final int MAX_SET_ENTRIES = 64;
    /** Maximum UTF-8 bytes of one {@link Type#TEXT_SET} entry. */
    public static final int MAX_SET_ENTRY_BYTES = 128;
    /** Maximum UTF-8 bytes of a {@link Type#TEXT} value, and maximum length of a {@link Type#BYTES} value. */
    public static final int MAX_VALUE_BYTES = 4096;
    /** CEL reserved words match the identifier grammar but cannot be selected as {@code facts.<name>}. */
    public static final Set<String> RESERVED_NAMES = Set.of("in", "as", "break", "const", "continue", "else",
            "false", "for", "function", "if", "import", "let", "loop", "namespace", "null", "package", "return",
            "true", "var", "void", "while");

    private static final Pattern NAME = Pattern.compile("[a-zA-Z][a-zA-Z0-9_]{0,62}");

    public RuleFact {
        if (name == null || !NAME.matcher(name).matches() || RESERVED_NAMES.contains(name)) {
            throw new IllegalArgumentException("invalid rule fact name");
        }
        Objects.requireNonNull(type, "type");
    }
}

public interface TransitionKernel<C, F> ... {
    /**
     * Declares the facts this kernel can establish for admission rules. The list depends only on
     * committed configuration, is fixed for the kernel's lifetime, and has at most
     * {@link RuleFact#MAX_FACTS} entries with unique names. Empty by default: a kernel built
     * against an earlier API level declares no facts.
     *
     * <p>Declarations and values are consensus-relevant for every profile whose rules read them:
     * changing which facts a kernel declares, or how it computes them, changes the kernel's consensus
     * semantics and requires a versioned profile decision.
     *
     * @return stable fact declarations derived only from committed configuration
     */
    default List<RuleFact> ruleFacts() { return List.of(); }

    /**
     * Returns the values of declared facts for a command whose decision was
     * {@link TransitionDecision.Approved} with exactly this facts instance. Callers invoke it only
     * after {@code decide(command, context, facts)} approved, and never for a rejection.
     *
     * <p>The method is pure: no I/O, clock, state reader, randomness, or node-local input. It
     * returns only values this kernel established by its own verification. A declared name that
     * is absent means "not established for this command". The result is never {@code null}; values
     * are {@code Long}, {@code String} (at most {@link RuleFact#MAX_VALUE_BYTES} UTF-8 bytes),
     * {@code byte[]} (at most {@link RuleFact#MAX_VALUE_BYTES} bytes), or {@code Boolean} for the
     * scalar types, and for {@link RuleFact.Type#TEXT_SET} a {@code List<String>} of at most
     * {@link RuleFact#MAX_SET_ENTRIES} entries, each at most {@link RuleFact#MAX_SET_ENTRY_BYTES}
     * UTF-8 bytes, strictly increasing by unsigned UTF-8 bytes (sorted and duplicate-free).
     *
     * <p>Callers validate the result defensively and treat a violation (a {@code null} result, key, or
     * value, an undeclared name, a wrong type, or an exceeded bound) as a deterministic rejection of
     * the command, never as a block failure. An exception is not a violation: like an exception from
     * {@link #decide}, it propagates as an implementation failure, because a node-local fault must
     * not become a consensus outcome.
     *
     * @param command the decoded command that was approved
     * @param context the execution context of that decision
     * @param facts the exact facts instance passed to the approving decision
     * @return values keyed by declared fact name; empty by default
     */
    default Map<String, Object> ruleFactValues(C command, TransitionContext context, F facts) {
        return Map.of();
    }
}
```

The host plugin boundary forwards both methods through its kernel facade
(`PluginSpiFacades.KernelFacade`), exactly as it forwards the other kernel accessors. Without
that forwarding a kernel loaded from a plugin bundle would silently declare no facts. This is
forwarding only; the host still never evaluates a rule.

The contract:

- `ruleFacts()` is pure and depends only on committed configuration. It returns at most 32
  facts, with unique names. A fact name is an identifier, `[a-zA-Z][a-zA-Z0-9_]{0,62}`, other than
  a CEL reserved word (`RuleFact.RESERVED_NAMES`), because rules read it as `facts.<name>`.
- `ruleFactValues` is pure: no I/O, clock, state reader, or randomness. It is invoked only
  with the facts object that produced an Approved decision. Values must follow the declared
  types:
  - `Long`, `String`, `byte[]`, or `Boolean` for the scalar types;
  - for `TEXT_SET`, a sorted, duplicate-free `List<String>` of at most 64 entries, each at
    most 128 UTF-8 bytes.
- The engine validates the result defensively: a `null` result, key, or value, an undeclared
  name, a wrong type, a TEXT or BYTES value over `RuleFact.MAX_VALUE_BYTES` (4096), or a TEXT_SET
  that is oversized or not strictly increasing by unsigned UTF-8 bytes. A violation rejects the
  step with `ADMISSION_RULE_INPUT`. Kernels are deterministic, so every member rejects
  identically, and no block aborts.
- An exception from `ruleFactValues` is not a violation. Like an exception from `decide`, it
  propagates as an implementation failure. Catching it could turn a node-local fault, such as a
  plugin being unloaded, into a consensus outcome that differs between members.
- Declarations and values are consensus-relevant: changing which facts a kernel declares, or how
  it computes them, changes the kernel's consensus semantics and requires a versioned profile
  decision.
- A fact exists only because a kernel established it. Bindings, commands, configuration,
  lookups, and other plugins have no path to write `facts.*`. This is the draft's "trusted
  facts" without a provider registry.
- Plugin API level rises from 11 (`PluginApiVersion.CURRENT_LEVEL`) to 12. Kernels built
  against level 11 keep the empty defaults and simply declare no facts.

Kernels that implement it in the first release:

| Kernel (machine id) | Facts |
|---|---|
| `authenticated-map-component`, any collection policy | `senderMember` BOOLEAN (membership of the sender at the candidate height, as the map sampled it); `collections` TEXT_SET (the distinct collection ids the approved batch writes) |
| `authenticated-map-component`, governed (configured with `actors` and `approvals`) | Also `directActorCount` INTEGER and `approvalCount` INTEGER, the numbers of verified direct-actor and approval-reference evidence items. When exactly one direct actor authorized the command, also: `actorId` TEXT, `organizationId` TEXT, `role` TEXT (the role required by the verified direct policy), `roles` TEXT_SET (the actor's roles in the verified actor record), and `policyId` TEXT (the verified direct policy) |
| `governed-role-approvals` | `actorId` TEXT, `organizationId` TEXT, `roles` TEXT_SET (from the eligibility snapshot the signature was verified against), `action` TEXT (`PROPOSE`, `APPROVE`, `REJECT`, or `CANCEL`), `policyId` TEXT and `policyRevision` INTEGER (from the signed statement) |

These tables were confirmed against the code in Phase 0 (§15): the map's verified direct facts
are `RoleAuthorizationCapability.DirectFacts` (policy, actor record, organization, key epoch),
and the approval kernel's are `ActorApprovalProcessor.ActorEligibility` plus the signed
`ActorStatementV1`. Actor roles are already sorted and duplicate-free (at most 16), role and
identifier text is at most 63 ASCII bytes, collection ids are at most 64 bytes, and a map
declares at most 64 collections, so every TEXT_SET fits its bounds. "Exactly one direct actor"
means `directActorCount == 1`, counting verified direct-actor evidence items.

Exact replays differ between the two kernels:

- `governed-role-approvals` recognizes a replay by the signed statement, not by message id: an
  existing matching proposal, or a prior decision with the same statement digest. The same
  staged command can therefore arrive in a new message, from another member, with a new sender
  sequence, or through a binding. It reaches `decide`, which verifies the signature, returns
  `EXACT_REPLAY`, and approves an empty plan. The facts are established and fact rules run.
- The map recognizes a replay from its receipt key, which is keyed by message id, before any
  verification, and approves an empty plan without facts; a fact rule would fail closed with
  `ADMISSION_RULE_ERROR`. This case is unreachable through the workflow, which returns the stored
  receipt for a replayed source message before evaluating anything.

Other stock kernels (`balances`, `kv-registry`, `approvals`, `doc-trail`, and the ordered
log) authenticate the member sender only and declare no facts. A fact rule attached to them
fails construction with `RULE_FACT_UNKNOWN`. To role-gate a member-authenticated machine,
compose it behind a role-verified component. For example, `governed-role-approvals` feeds a
binding into the target, and the target carries an `only-via-binding` rule (§6.3).

A multi-actor map batch establishes counts but no single-actor facts. A rule that reads
`facts.roles` for such a batch raises an absent-field error and denies with
`ADMISSION_RULE_ERROR`, so it fails closed. Per-actor facts are a future extension (§16).

### 5.6 Evaluation point and order

```text
decide(step):
    command = codec.decode(step.body)                          // existing
    kernel.admit(command); kernel.admit(command, ctx)          // existing
    view = commandView(step)  if any attached rule selects a command
    evaluate(admissionSlotRules(component), view, ...)         // attachment order
    kernel.workRequest(...)                                    // existing
    facts    = kernel.facts(...)                               // existing
    decision = kernel.decide(command, ctx, facts)              // existing
    if decision is Approved and component has fact rules:
        values = validate(kernel.ruleFactValues(command, ctx, facts), kernel.ruleFacts())
        evaluate(factSlotRules(component), view, values, ...)  // attachment order
    return decision

evaluate(rules, ...):
    for rule in rules:
        if rule.command != null and rule.command != view.name: continue
        outcome = clauses(rule, view, params, config, ruleContext(step), overlays, values)
        record(step, rule.id, outcome)
        if outcome is not HELD: throw BindingFailure(code(outcome)).atRule(rule.id, outcome.clause)
```

- `ruleContext(step)` comes from the engine's own `Step` record (component, context,
  binding, and depth). No `TransitionContext` change is needed.
- The command view is built once, before the admission slot, exactly when some attached rule
  (in either slot) names a command. If it cannot be built, no rule runs: the trace is
  `[0, [r, -1, null]]`, where `r` is the first command-selecting rule in evaluation order. A work
  budget exhausted while building it gives `EXPRESSION_CAPACITY_EXCEEDED` with the same trace.
- `ruleFactValues` is called only when at least one fact rule applies to the command (its
  selector matches, or it has none). If the values violate §5.5, the trace is `[h, [f, -1, null]]`,
  where `h` counts the admission-slot rules that held and `f` is the first applicable fact rule.
  Validating the values costs `1 + BindingWork.encoding(values)` on both counters.
- Attachment order is kept within each slot, and every admission-slot rule precedes every
  fact rule. Authors see the resulting order in `bindings validate`.
- `decide` today calls `kernel.facts` inline (L418). The facts object must be held so that
  `ruleFactValues` receives exactly the instance that produced the approval.
- A fact-rule denial discards an approved plan. That is safe because plans commit only at
  the end of a cascade (ADR-031.1 §5.4). Crypto work reserved and consumed for this step
  stays charged.

### 5.7 Combination semantics

- All rules attached to a component are evaluated in order for every command they select.
  The first rule that does not hold denies, and later rules are neither evaluated nor charged.
- There is no allow rule. A rule cannot make a kernel accept anything; it can only reject.
- Product defaults versus deployment overrides are resolved at authoring time, and the
  compiled IR is the single source of truth. A product that wants non-removable rules pins
  the profile digest in its blueprint lock; consensus does not model layering.

### 5.8 Deny semantics, receipts, and codes

Engine codes, added to the ADR-031.1 cascade code set:

| Code | When |
|---|---|
| `ADMISSION_RULE_DENIED` | A clause evaluated to false, or a lookup expectation failed |
| `ADMISSION_RULE_ERROR` | An expression raised an unmasked error: overflow, division by zero, an absent field or fact. Also a lookup key that could not be built (§5.2) |
| `ADMISSION_RULE_INPUT` | The command view could not be built canonically (§5.4), or a kernel returned facts that violate §5.5 |
| `EXPRESSION_CAPACITY_EXCEEDED` | Existing code; rule evaluation exhausted the cascade or block work budget |

**A denial at any depth rejects the whole source message.** If a rule on `audit` denies a
command derived from an item's final approval, the approval itself does not commit either.
The item stays pending with its prior approvers, as ADR-031.1 §7 describes for any downstream
rejection. This is the existing atomicity contract, and authors need to know that a rule on a
downstream component can block an upstream business action. `bindings dry-run` and the
Studio report show this.

Each step receipt gains a compact `rulesEvaluated` trace:

```text
StepReceiptV1  = [ ordinal, depth, bindingId / null, targetComponentId, messageId,
                   eventsProduced, conditionsEvaluated, rulesEvaluated,
                   status, code, rawBody ]
rulesEvaluated = [ heldCount, RuleFailureV1 / null ]
RuleFailureV1  = [ ruleId, failedClause, denyCode / null ]
                 ; denyCode is the rule's code for ADMISSION_RULE_DENIED, null for _ERROR and _INPUT
```

- A denial always names the clause that evaluated false, `0..7`, with the rule's deny code.
- `failedClause = -1` means the rule failed before any clause ran: the command view could not
  be built, the kernel returned invalid facts (`ADMISSION_RULE_INPUT`), or the rule's own
  precharge exhausted a work budget (`EXPRESSION_CAPACITY_EXCEEDED`). An input failure names
  the first rule that needed the missing input.
- A work budget exhausted inside a clause records that clause, with a null deny code, and the
  step code is `EXPRESSION_CAPACITY_EXCEEDED`.

- The trace is lossless because evaluation order is fixed. That order is admission-slot
  rules in attachment order, then fact rules in attachment order, skipping rules whose
  command selector does not match. Evaluation stops at the first failure. `heldCount` plus
  the committed IR and the command name therefore identify every rule that held. The command
  name of a derived step follows from its binding; for the source step it is the source
  message's own body, which the chain also records.
- A step costs 3 bytes of trace when no rule fails and at most 134 bytes when one does (a
  63-character rule id and a 63-character deny code). Recording every held rule's id would
  have cost up to 16 rules × 257 steps, which can exceed the 64 KiB receipt cap and turn
  legitimate cascades into `RECEIPT_CAPACITY_EXCEEDED` no-ops.
- `compactFailureTrace` keeps the failing step's `RuleFailureV1`. Its failed-step size
  invariant is re-derived with this term: at most 256 conditions of 127-character names
  (under 35 KiB), a 134-byte rule trace, and bounded metadata still fit the 64 KiB cap.
- The trace never carries fact values, so receipts disclose no roles or organizations beyond
  the rule id and deny code.

At local ingress, a static-rule denial returns
`AdmissionResult.reject("ADMISSION_RULE_DENIED/<ruleId>/<denyCode>")`. A static rule that
raises an error returns `ADMISSION_RULE_ERROR/<ruleId>`, a view that cannot be built returns
`ADMISSION_RULE_INPUT/<ruleId>`, and exhausted local work returns
`EXPRESSION_CAPACITY_EXCEEDED`. The message is not pooled, and the REST layer answers
HTTP 400. The host exposes only bounded symbolic codes (`[A-Z_]{1,32}`,
`AppSubmissionRejectedException`) to remote callers, so the REST body carries
`APPLICATION_REJECTED`. The full reason, including the rule and deny code, appears in the
node's DEBUG admission log and in `bindings dry-run`.

### 5.9 Advisory evaluation at local ingress

A rule is **static** when every clause is an expression that reads only `command.*`,
`params.*`, and `config.*`. Static classification is computed at profile construction and
published in the capability manifest.

`EventBindingWorkflow.validate` evaluates the static rules attached to the source component,
after `kernel.admit(command)` accepts. It uses a fresh local budget of
`maxExpressionWorkPerCascade` that is never persisted. The same method backs
`validateForBlock`, which the proposer also runs when selecting messages. The result is
still advisory: followers do not run it, and block-time evaluation is authoritative.

Around an ADR-015 activation, a message pooled under the old rules may be denied at block
time under the new ones. It then gets a receipt, which is the normal outcome for any
state-dependent rejection.

### 5.10 Authority across cascades

ADR-031.1 §5.11 is unchanged:

- `context.sender` is the originator for every step. A binding cannot make a command arrive
  as someone else.
- Rules express arrival constraints with no new authority concept:
  - "only through binding X": `context.derived && context.binding == params.binding`
  - "never through a binding": `!context.derived`
- Rules express role requirements over verified facts only: `params.role in facts.roles`.
  The kernel verified the actor's signature, key epoch, status, and organization before the
  rule sees the facts. The rule adds a deployment constraint; it cannot establish a role.
- Delegation, a system principal, and role-derived authority for derived commands stay
  deferred to the ADR-019 and ADR-025.2 domain (ADR-031.1 §13.5).

Integrators must also know the corollary that drives rule design: a derived command acts as
the originator. A binding that derives `balances.transfer` moves the originator's funds,
because `transfer` has no `from` field.

### 5.11 Limits and work accounting

A new `LimitsV1` field, appended:

| Limit | Default | Maximum |
|---|---|---|
| `maxRulesPerComponent` | 4 | 16 |

Structural maxima, enforced at construction and decode:

| Bound | Maximum |
|---|---|
| Rules per profile | 64 |
| Clauses per rule | 8 |
| Parameters per rule | 16 |
| Lookup clauses per rule | `maxLookupsPerCondition` |
| Expression nodes and depth | `maxExpressionNodes`, `maxExpressionDepth` |
| Declared facts per kernel | 32 |
| `TEXT_SET` entries and entry size | 64 entries, 128 bytes each |

Rule evaluation charges the existing work counters (ADR-031.1 §5.13), at the existing unit
costs per visited node, lookup, and scalar comparison. `in` costs its node's unit plus, for each
candidate compared, the bytes of both operands (the cost of an equality test), and it stops at
the first match. Validating the fact map costs `1 + BindingWork.encoding(values)`, and building
the command view costs `1 + body.length` before decoding plus the mapping encoder's charge for
the decoded fields before re-encoding them.

Unlike source-only preparation, rule evaluation charges **both** the per-cascade and the
per-block budget at every depth. Rules are optional extra work, and the block bound must
hold even for a block of one-component source messages. Work charged before a denial is not
refunded.

A consequence, already true for binding conditions: denied messages draw down the block
budget. A later legitimate cascade in the same block can then be refused with
`EXPRESSION_CAPACITY_EXCEEDED`, a no-op with a receipt that the sender can resubmit. The
default block budget is 32× the cascade budget, which bounds this. Phase 6 asserts that an
in-budget legitimate cascade after a run of denials still commits.

### 5.12 Commitment, activation, and governance

- Rules, attachments, and normalized parameters are sections of the binding IR, and
  therefore of the composite profile bytes. Two members with different rules fail closed at
  height 1 with the existing marker error.
- A changed rule, attachment, or parameter requires a new `workflowFromHeight` and an
  ADR-015 profile epoch: proposal, readiness, scheduled activation, and the configured
  `profile-governance.min-activation-lag`.
- Replay evaluates each height under the epoch active at that height. Receipts written under
  a retired epoch remain valid, provable state.
- Emergency tightening uses the same path. There is no node-local or break-glass override
  (ADR-015 decision 015-D12).
- Parameters are literals in this ADR. A governed parameter read from chain state needs a
  value-returning lookup, which `LookupClause` does not have (§2.1). It is deferred (§16).
- Fact **values** are live consensus state, such as an actor's current roles, and are
  governed by ADR-019 actor governance. Rules only read them.

### 5.13 Single-machine usage

"Policy without bindings" is a `declarative-composite` with one component, zero bindings,
and rule attachments. The blueprint schema already permits an empty `bindings` list.
Clients submit to the component's ingress topic (`<componentId>.command.v1` unless `topic:`
is set).

A chain selected with `state-machine=<id>` runs the machine standalone, outside the cascade
engine, and has no policy plane. Converting such a chain to a composite changes its state
namespace; in development, that means a new chain.

### 5.14 Wire contracts (amended in place, v1)

```text

    "yano-x-cel-v1",                 ; amended: scoped fields, TEXT_SET, `in`
    workflowFromHeight,

]
ComponentV1      = [ componentId, machineId, ingressTopic, configuration,
                     maxEffectsPerBlock, fromHeight, [ * RuleAttachmentV1 ] ]   ; 7 (was 6)

                                               ; defaults filled; attachments keep authored order
AdmissionRuleV1  = [ ruleId, denyCode, commandName / null, [ * ParameterV1 ], [ + RuleClauseV1 ] ]

                 / [ 2, ExpressionV1 ]                                     ; boolean expression

node         = [ 0, scalar ]
             / [ 1, scope, fieldName ]    ; 3 (was [1, fieldName])
             / [ 2, operatorId, [ * node ] ]
scope        = 0 event / 1 command / 2 params / 3 config / 4 context / 5 facts
```

The capability manifest keeps its `declarative-event-bindings` cross-cutting entry and the
`yano-x-binding-graph-v1` schema id. Rule metadata is added as attributes of that entry, as
an `admission` list of `(ruleId, componentId, command, denyCode, slot, static)` sorted by
`(componentId, attachment order)`. It is not a new entry. The manifest digest is therefore
still a single deterministic function of the profile. Entry attributes are a flat text map, so
each attachment is encoded as the keys `admission.<componentId>.<NN>.rule`, `.command` (`*`
for a rule without a selector), `.deny`, `.slot` (`admission` or `fact`), and `.static`
(`true` or `false`), where `NN` is the two-digit attachment index. The host keeps attributes
in sorted key order, so each component's attachments stay in attachment order.

Decode enforces the scope-by-use-site table (§5.3), not only the compiler.

Rules for the in-place amendment:

- Identifiers are unchanged: IR version `1`, `yano-x-binding-ir-v1`, `yano-x-cel-v1`,
  `yano-x-binding-functions-v1`, `BindingReceiptV1`, `composite/binding-receipt-v1/<id>`, and
  `composite/binding-receipt-key-v1/<id>`. Java class names are unchanged.
- Every amended structure changes arity. Pre-ADR bytes therefore fail strict decode, with a
  clear "binding IR predates ADR-031.3" error rather than a silent misreading. Tests pin this.
  Two envelopes keep their arity: the receipt envelope, whose steps changed, and the expression
  envelope, whose field nodes changed. An expression without a field reference therefore means
  the same under both layouts, and a receipt now requires at least one step, so no pre-ADR
  receipt decodes.
- `DeclarativeCompositeProvider.EXECUTION_VERSION` moves from `1.1.0`
  (`DeclarativeCompositeProvider.java:51`) to `1.2.0`, because execution semantics change.
- The composite profile layout (schema version 2) is unchanged. The IR bytes inside it
  change, and so does every digest.
- Experimental declarative chains, checked-in IR fixtures, golden vectors, showcase
  profiles, and Studio assets are regenerated. No ADR-015 epoch from pre-ADR bytes is
  supported.
- ADR-031.1 §5.3, §5.6, and §5.13 get an "amended by ADR-031.3" note pointing here.

## 6. Configuration and authoring

### 6.1 One machine, one rule

```yaml
spec:
  chains:
    - id: loyalty
      recipe: declarative-composite
      composite:
        components:
          - id: points
            machine: balances
            config: { minter: "<minter account id>" }
            admission:
              - rule: transfer-limit
                params: { maxAmount: 10000 }
        rules:
          - id: transfer-limit
            command: transfer
            deny: TRANSFER_LIMIT_EXCEEDED
            params:
              maxAmount: { type: integer }
            require:
              - expr: 'command.amount <= params.maxAmount'
        bindings: []
```

`transfer-limit` is static, so a transfer of 20,000 is rejected at the REST endpoint (HTTP
400) and is never pooled. The workflow's reason is
`ADMISSION_RULE_DENIED/transfer-limit/TRANSFER_LIMIT_EXCEEDED`; the REST body shows the host's
bounded code `APPLICATION_REJECTED` (§5.8). `mint` is not selected, so it is unaffected.
Positivity and sufficient balance remain the kernel's checks.

```yaml
  rules:
    - id: allowed-organization          # fact rule: reviews declares organizationId
      deny: ORGANIZATION_NOT_ALLOWED
      params:
        organization: { type: text }
      require:
        - expr: 'facts.action != "APPROVE" || facts.organizationId == params.organization'
    - id: operator-for-direct-writes    # fact rule: the map declares directActorCount and roles
      deny: ROLE_REQUIRED
      params:
        role: { type: text }
      require:
        - expr: 'facts.directActorCount == 0 || params.role in facts.roles'
  bindings:
    - id: apply-approved
      from: { component: reviews, event: role-approvals.proposal-approved.v1 }
      to:
        component: registry
        command: apply-action
        map:
          action: { field: action }
          approvalReference: { field: proposalId }
```

- `allowed-organization` restricts who may **approve** in this deployment, beyond what the
  approval policy requires. It runs only after the kernel has verified the approver's
  signature.
- `operator-for-direct-writes` requires the `operator` role for direct actor-signed writes.
  Approval-referenced writes arriving through `apply-approved` have `directActorCount == 0`,
  and the approval policy already governs them.

## 7. Worked examples

Using §6.2:

1. **An unregistered sender puts an order.** `registered-supplier` has a lookup, so it is not
   static and the message is pooled. At block time, step 0 denies with
   `ADMISSION_RULE_DENIED` and `rulesEvaluated = [0, [registered-supplier, 0, NOT_A_REGISTERED_SUPPLIER]]`.
   Nothing is written. This deliberately differs from ADR-031.1 §7, where the supplier check
   was a binding lookup: the order committed and only the proposal was skipped. As a rule,
   the check refuses the order itself.
2. **A registered supplier puts an order.** The rule holds. `order-to-approval` fires, since
   its producing step is not derived, and derives `approvals.propose` with `required = 2`.
   `minimum-quorum` holds at depth 1. The proposal commits with the order, in one batch.
3. **A binding author lowers `required` to 1.** Every order's cascade now denies at depth 1
   with `QUORUM_TOO_LOW`, and the order put at depth 0 does not commit either (§5.8).
   `bindings dry-run` shows this before deployment.
4. **Someone appends to `audit` directly.** `only-via-binding` reads `context`, so it runs at
   block time. Step 0 denies with `DIRECT_SUBMISSION_FORBIDDEN`.
5. **The second approver approves.** `approved-to-audit` derives `audit.append` at depth 1
   with `derived = true` and `binding = "approved-to-audit"`. The rule holds, and the approval
   and the audit entry commit together.

Using §6.3:

6. **An auditor from `audit-guild-b` approves.** The kernel verifies the signature and
   approves. `allowed-organization` then denies with `ORGANIZATION_NOT_ALLOWED`, and the
   approval is not recorded.
7. **An approval with a forged signature.** The kernel rejects with its own code. No rule
   runs, and the receipt reveals nothing about roles.
8. **A direct map write signed by an actor without `operator`.** The map verifies the actor
   and approves. `operator-for-direct-writes` denies with `ROLE_REQUIRED`.

Every outcome is a finalized, provable receipt. No block is aborted.

## 8. Deterministic execution guarantees

- Rule inputs are consensus values only:
  - committed IR;
  - the step's body;
  - the engine-built context;
  - overlay reads of declared components;
  - facts computed by a deterministic kernel from the same snapshot that produced its
    approval.

  There is no clock, randomness, environment, I/O, or node-local counter.
- Evaluation uses the existing interpreter, with pinned operator semantics, checked int64
  arithmetic, and error masking. The scoped-field node, `TEXT_SET`, and `in` have golden
  vectors.
- Evaluation order is fixed: slot, then attachment order, then clause order, then node order.
- Work is charged before allocation, on both counters, including for denials.
- The command view is a pure function of body bytes and committed descriptors, with a
  canonical round-trip check.
- Advisory local evaluation cannot affect state, receipts, or roots.

  - A rejected decision runs no fact rule.

## 11. Verification strategy

- **Determinism.** Cluster runs and replay from genesis reproduce roots, receipts, and work
  counters for every recipe and denial fixture.
- **Atomicity.** For every rule code, slot, and depth, no business write or effect from the
  cascade survives the block.
- **No bypass.** Direct and derived commands to a ruled component yield identical rule
  outcomes for identical inputs.
- **Authority.**
  - No rule input lets a derived command present a sender other than the originator.
  - Evidence-field reads, and evidence mappings from `context.*`, fail construction.
  - `facts.*` values come only from `ruleFactValues` after an approved decision.
- **Verified facts.** Forged, expired, revoked, or wrong-organization evidence never reaches
  a fact rule. Fact values equal the kernel's verified records. Receipts contain no fact
  values.
- **Language.**
  - Every scope and field type, in every legal use site, has compile, lower, decode, and
    evaluate vectors.
  - Every illegal pairing fails both the compiler and the decoder.
  - `in` has vectors for empty sets, a first match, a last match, no match, and the maximum
    size.
- **Command view.** Stock-kernel conformance passes; non-canonical bodies are refused;
  opaque commands are unselectable.
- **Limits.** Structural breaches fail construction. Runtime exhaustion yields the
  documented codes and never an exception.
- **Advisory ingress.**
  - A static-rule denial is reported before pooling.
  - Non-static rules and fact rules never run at ingress.
  - Removing ingress evaluation changes no root.
- **Governance.** Epoch activation works; old receipts stay provable; divergent members fail
  closed.
- **Dry-run parity.** Dry-run receipts equal cluster receipts byte-for-byte.
- **In-place amendment.** Pre-ADR IR and receipt bytes, and pre-ADR expressions with a field
  reference, fail decode with the explicit error. No code path accepts both layouts.

## 12. Acceptance criteria

This ADR is complete when:

1. §6.1, §6.2, and §6.3 run from configuration only on a three-member cluster with identical
   height, root, profile digest, and capability-manifest digest;
2. every command entering a ruled component, direct or derived, is evaluated against its
   rules. A denial at any depth or slot is a per-source-message no-op, with a provable
   receipt naming the rule, clause, and deny code;
3. rules cannot read evidence fields, timestamps, or undeclared state. They cannot grant or
   widen authority, or alter a command. Construction enforces each of these;
4. fact rules see only values the target kernel established by its own verification after
   an approved decision. The governed map and `governed-role-approvals` kernels provide them;
5. rule work is charged to both budgets, including on denial, and no rule outcome can abort a
   block;
6. static rules reject before pooling; non-static and fact rules never run at ingress;
7. rule changes activate only through ADR-015 epochs, and divergent rules fail closed at
   height 1;
8. binding conditions and mappings read `context.*` with the documented semantics, and
   evidence remains event-sourced;
9. `bindings validate`, `dry-run`, and `graph`, and the Studio editor, author and explain
   rules, with byte parity between dry-run and cluster receipts;
10. the amended v1 contracts are the only supported layouts, with golden vectors and CDDL,
    and pre-ADR bytes fail decode explicitly;
11. every stock kernel passes command-view conformance;
12. Yano X builds against a published Yano release that contains the host contract, not a
    local snapshot; and
13. the documentation and recipes in Phase 5 are published, and the open-item tracker
    carries the implementation rows.

## 13. Rejected alternatives

### 13.1 A CEL runtime or language-neutral policy engine in consensus

Rejected. Consensus runs a closed, versioned IR so that parser, protobuf, and optimizer
behaviour stay outside the state root (ADR-031.1 §5.13). A second engine doubles the
determinism surface. WASM or another language would need its own ADR and budget model.

### 13.2 A policy hook in the Yano host execution path

Rejected. The host executes `apply` opaquely and has no command-level pipeline. ADR-031 §5.3
and §13.4 keep the runtime application-policy agnostic. The host contributes only a
kernel-owned fact accessor. Evaluation stays in the one engine that sees every step.

### 13.3 A trusted-fact model with an open provider SPI

Rejected. A provider registry would let a plugin other than the target kernel assert facts
about a command it did not verify. Kernel-declared facts, produced only after the kernel's
own approval, give the same power with a single owner (ADR-031 §6.4).

### 13.4 Evaluating fact rules between `facts` and `decide`

Rejected. `governed-role-approvals` verifies the actor signature inside `decide`
(`ActorApprovalProcessor.java:217`), so its facts are only claims before `decide`. A rule
there could deny on unverified identity, and misattribute a forged-signature failure as a
role failure. The post-decision slot is correct for every kernel.

### 13.5 Role lookups against the actor registry for member-authenticated machines

Rejected. The member sender is not an actor identity, and no verified link exists between
them. Role-gating a member-authenticated machine is done by composition (§5.5, §6.3).

### 13.6 Allow rules, priorities, and exemptions

Rejected. Forbid-only conjunction is analyzable and cannot loosen a machine. Whether a
command is admitted does not depend on rule order. The reported rule and clause, and the
work charged, do depend on it; that order is committed, so it is deterministic.

### 13.7 Transformation policies

Rejected. A rule that rewrites a command breaks the guarantee that a mapped command reaches
its target exactly as a client-submitted one would (ADR-031.1 §5.3). It also breaks
byte-for-byte evidence copying, and it moves domain logic out of kernels. Transformation
belongs to bindings.

### 13.8 A separate policy workflow beside the event-binding workflow

Rejected. It would see derived commands only if the two workflows shared cascade state, and
workflow order would break global block order (ADR-031.1 §13.13).

### 13.9 Rules in node configuration

Rejected. Consensus behaviour must be committed and governed (ADR-031.1 §1.12; ADR-015).

### 13.10 Introducing v2 identifiers

Rejected while declarative composition is in development. New identifiers add churn in
queries, docs, and tooling with no deployed chain to protect. Arity changes make stale bytes
fail loudly, and new identifiers become mandatory once a release is public.

---

## 14. Consequences

**Positive**

- Configuration-only integrators can constrain stock machines per deployment, including by
  verified roles, without forks or JARs.
- Bindings cannot bypass rules. The no-bypass property follows from the engine's structure,
  not from convention.
- Denials are consensus-visible, explainable, provable, and reproducible in dry-run.
- Bindings gain `context.*`, which enables "direct-only" and "via-binding-only" conditions.
- No new runtime dependency, engine, or open SPI is added.

**Negative / costs**

- Every experimental declarative chain, fixture, and vector must be regenerated.
- A host API change (level 12) must be coordinated through local Maven publication and then
  a Yano release before a Yano X release.
- A downstream rule can roll back upstream business actions. This is correct under atomic
  cascades, but authors must be taught it (§5.8).
- Fact rules run after verification work, which stays charged when a fact rule denies.
- A command-selecting rule also rejects bodies that the codec accepts but the descriptor
  cannot represent canonically (§5.4).
- Denied messages consume block work budget, so under load a legitimate cascade can be
  refused for capacity and must be resubmitted (§5.11).
- Opaque command contents remain invisible, and multi-actor map batches expose only counts.
- Parameters are literals, so changing a limit is a governance epoch, not a state write.

## 15. Resolved choices and open questions

Resolved (2026-09-27):

1. Rules over verified roles are in the first release, through the host contract in §5.5.
   Development consumes Yano from local Maven.
2. Binding conditions and mappings get `context.*` (§5.3), with the safety argument recorded
   there.
3. The YAML key names are `rules`, `require`, `deny`, `params`, and
   `components[].admission`.
4. The v1 identifiers are amended in place; there is no v2 (§5.14).
5. This ADR introduces admission rules only (§16).

Closed in Phase 0 (2026-09-27), from the code:

6. Fact names and types (§5.5). The ADR's tables match the verified records:
   `RoleAuthorizationCapability.DirectFacts` for the map and
   `ActorApprovalProcessor.ActorEligibility` with the signed `ActorStatementV1` for
   `governed-role-approvals`. Fact names are CEL identifiers.
7. Non-governed map collections. Every map component, governed or not, declares
   `senderMember` and `collections`, a TEXT_SET of the collection ids the approved batch
   writes. A single collection id would not describe a multi-collection batch, and map commands
   are unselectable, so `collections` is the only way a rule can scope an open or owner
   collection, for example `!(params.collection in facts.collections)` to make one collection
   read-only for a component. The set is established by the kernel's own decision, not taken
   from an unverified command view. Governed maps add the actor and approval facts.

## 16. Other policy points (not in this ADR)

This ADR deliberately introduces one policy point. The others fall into two groups.

**Already binding features, and staying there:**

- **Event filtering:** binding `when` conditions.
- **State-transition guards:** conditions over `*After` event fields, such as `balanceAfter`.
- **Derived values:** mapping expressions.

**Each needs its own decision:**

| Point | Why deferred | Likely shape |
|---|---|---|
| Plan assertions (postconditions) | Need value reads of post-plan state and a failure contract | Clauses after the verified-fact slot, over the overlay with the plan applied; failure = cascade no-op |
| Governed parameters | `LookupClause` cannot yield values | A value-returning lookup source with a typed result |
| Per-actor facts for multi-actor batches | Scalars cannot describe several actors | An all/any quantifier over a bounded fact list |
| Opaque command views | `RAW_BYTES` and map actions are invisible | A kernel-provided command view, analogous to §5.5 |
| Effect admission | Effects are not commands, and quotas already bound them | Rules on effect targets |
| Delegation for derived commands | Belongs to the ADR-019 and ADR-025.2 authority domain | Governed delegation policy (ADR-031.1 §13.5) |

The verified-fact slot is where plan assertions would run, so the most likely next policy
point needs no new engine structure.
