## Deviations

Each entry names the ADR text it changes, why, and the commit that carries both.

1. **REST reporting of static-rule denials (§5.8, §6.1).** The host exposes only reasons
   matching `[A-Z_]{1,32}` to remote callers (`AppSubmissionRejectedException.safeCode`), so
   `ADMISSION_RULE_DENIED/<ruleId>/<denyCode>` reaches REST callers as HTTP 400
   `APPLICATION_REJECTED`. The workflow keeps the ADR's reason format (it appears in the DEBUG
   admission log and in dry-run); the ADR now states the REST behaviour. Changing the host's
   code sanitizer would be a host contract change beyond §5.5, so it is not made. The ADR also
   defines the ingress reasons for a static-rule error (`ADMISSION_RULE_ERROR/<ruleId>`), an
   unbuildable view (`ADMISSION_RULE_INPUT/<ruleId>`), and exhausted local work
   (`EXPRESSION_CAPACITY_EXCEEDED`), which it had left open.
2. **Plugin facade forwarding (§5.5, §9, Phase 1).** `PluginSpiFacades.KernelFacade` wraps
   every plugin-loaded kernel. Without forwarding `ruleFacts()` and `ruleFactValues(...)`, a
   kernel from a plugin bundle would silently declare no facts. The forwarding is a Yano
   `runtime` change beside the `core-api` contract. It evaluates nothing, so there is still no
   policy hook in the host execution path.
3. **Lookup expectation key (§5.2).** The ADR wrote `equals:`; the existing binding lookup form
   uses `eq:`. Rules reuse the binding form, so the key is `eq:` for both.
4. **Unattached rules (§5.2, Phase 3).** A rule is type-checked per attachment against the
   attached kernel; an unattached rule has no kernel to check `command.*`, `config.*`, or
   `facts.*` against and would be dead committed data. It fails construction with the new
   diagnostic `RULE_UNATTACHED`.
5. **Name grammars (§5.2, §5.5).** Parameter and fact names are CEL identifiers,
   `[a-zA-Z][a-zA-Z0-9_]{0,62}`, excluding the 21 CEL reserved words, because rules read them as
   `params.<name>` and `facts.<name>`. The descriptor naming rule also allows `.` and `-`, which CEL
   cannot select.
6. **`governed-role-approvals` selectability (§5.4, Phase 2).** It declares one
   `ARRAY_WITH_OPCODE` command, so §5.4's rule makes it selectable; Phase 2 had said it was
   "marked unselectable". Its view exposes only the opaque `action` bytes. Its conformance test
   lives in `capabilities/role-workflow`, which owns the kernel.
7. **Command view decodes every field (§5.4).** The round-trip check re-encodes the whole body,
   so every declared field, including EVIDENCE fields, is decoded; only DATA fields are exposed.
8. **Map facts for every collection policy (§5.5, §15).** Resolving open question 2, every map
   component declares `senderMember` and `collections` (a TEXT_SET of the collection ids the
   approved batch writes); governed maps add the actor and approval facts. Exact-replay
   behaviour of both kernels is now stated.
9. **Rule trace details (§5.8).** A denial always names clause `0..7` with its deny code;
   clause `-1` marks a failure before any clause (input or rule precharge). The Phase 0 list
   named `RuleOutcomeV1`; the normative name in §5.8 is `RuleFailureV1`.
10. **Contract freeze staging (Phase 0).** The amended CDDL and vectors are frozen under
    `031.3-contract-freeze/` and installed byte for byte in Phase 2; Phase 3 removed the staging copy
    once it was byte-identical to the installed files.
    Three existing tests decode `composition/contracts/.../declarative-bindings-v1-golden-vectors.properties`
    with the current codec, so installing the new vectors before the codecs change would leave
    the build red between phases.
11. **CDDL style and the pinned validator's limits (Phase 0).** `cddl-cli` 0.10.5 mis-validates
    bare repeated types and unnamed array alternatives (it rejects valid non-empty lists and
    accepts invalid ones), so the schema keys every repeated element and names every array
    alternative; this is equivalent RFC 8610. The validator also cannot evaluate a regular
    expression in map-key position, does not anchor regular expressions (it accepts rule ids
    `rA` and `9r` and deny code `aDENY`), does not check element regexps inside scalar lists, and
    does not enforce array-length upper bounds (it accepts 9 clauses, 17 parameters, 65 rules,
    258 steps). The normative schema keeps the precise map-key grammars; `verify-cddl.sh`
    validates vectors against a copy with plain text keys. The Java codec tests
    (`BindingPolicyPlaneContractTest`) cover the name grammars and length bounds the validator
    cannot.
12. **Host contract failure semantics (§5.5, Phase 0 review).** The result of
    `ruleFactValues` is never null; a null result, key, or value, a TEXT or BYTES value over
    `RuleFact.MAX_VALUE_BYTES` (4096, new), or a TEXT_SET that is not strictly increasing by
    unsigned UTF-8 bytes is a violation (`ADMISSION_RULE_INPUT`). An exception is not a
    violation: it propagates like an exception from `decide`, because catching it could turn a
    node-local plugin fault into a divergent consensus outcome. Fact and parameter names exclude
    CEL reserved words (`RuleFact.RESERVED_NAMES`). Changing declared facts or their computation
    is stated to be consensus-relevant. The facade truncates oversized byte arrays one byte past
    the bound, as it already does for maps and sets.
13. **Receipts carry at least one step (§1.12, §5.14, §11).** The engine always records the
    source step, but a zero-step accepted receipt had the same bytes under both layouts. The
    codec and CDDL now require at least one step, the published `receipt.accepted` vector carries
    a planned step, and the ADR's "pre-ADR bytes fail" claims are stated precisely (an expression
    without a field reference keeps its meaning).
14. **Input-failure traces and work costs (§5.6, §5.8, §5.11).** The command view is built once,
    before the admission slot, exactly when some attached rule names a command; a failure then
    runs no rule and names the first command-selecting rule. `ruleFactValues` is called only when
    an applicable fact rule exists; a violation names the first applicable fact rule after the
    admission-slot rules that held. Costs are defined: `in` charges each comparison like an
    equality test; fact validation costs `1 + BindingWork.encoding(values)`; the view costs
    `1 + body.length` before decoding plus the mapping encoder's charge before re-encoding. The
    worst-case rule trace is 134 bytes, not about 90.
15. **Codec-level use-site checks (§5.3, §5.14).** `context` has exactly five fields and `in`
    appears only in rules; both are enforced at construction and decode, and the CDDL expresses
    them. The reserved deny-code prefix `ADMISSION_RULE_` is now stated in §5.2.
16. **Phase ordering.** Phase 1 (Yano) and Phase 2 (Yano X) work was drafted in the working
    trees while the Phase 0 review ran. Each phase is still committed separately, and each commit
    is verified in a clean worktree built from the previous phase's commit.
17. **YAML rule authoring moves to Phase 3.** The Phase 3 and Phase 4 exit gates run rules from
    configuration on real nodes, so `BindingDocumentCompiler`'s `rules:`, `components[].admission:`
    and scoped source forms (ADR §10 Phase 5) land in Phase 3. The Phase 2 language export already
    advertises them; the rest of Phase 5 (schema, catalog, CLI, Studio, docs) stays in Phase 5.
18. **Snapshot versions and the Studio fixture regeneration.** Yano stamps every snapshot with its
    commit (`0.1.0-pre18-<commit>-SNAPSHOT`), so every gate names the exact stamped version, and
    distribution tasks also need the matching `-PyanoJvmDist` ZIP. `regenerateStudioFixtures`
    refuses snapshot hosts by design (ADR-031.2 C1), and the Studio fixtures embed the host version.
    Phase 2 main code does not yet use the level-12 API, so Phase 2 regenerated them against the
    published pin 0.1.0-pre17. From Phase 3 on the runtime needs level 12, which no published
    Yano has yet, so `regenerateStudioFixtures` gains an explicit opt-in: it accepts an unpinned
    host only when `-PunreleasedStudioHost` names the exact `-PyanoVersion`, and it warns that
    the output must be regenerated against the published host. The default still refuses
    (verified). The fixtures then record `0.1.0-pre18-f92d8b1-SNAPSHOT` and API level 12 until
    the release handoff regenerates them.
19. **Rule diagnostics by layer (§10 Phase 3).** Attachment parameters not declared by the rule
    fail with `RULE_PARAMETER_UNKNOWN`, which the ADR's list lacked. `RULE_SCOPE_INVALID` cannot
    reach `BindingProgram`, because the IR codec enforces the use-site table (deviation 15);
    the authoring compiler reports it, for YAML source keys and, through a scope flag on the CEL
    error, for CEL identifiers, keeping the expression position. A malformed fact declaration
    is `KERNEL_CONTRACT_INVALID`, and a non-bytes rule lookup key is `BINDING_TYPE_MISMATCH`, as
    for bindings. The authoring compiler also reports `RULE_EVIDENCE_READ`: it declares a selected
    command's evidence fields for type checking and rejects any clause that reads one. Authoring
    reports a structural bound overrun (too many rules, attachments, parameters, clauses) with the
    existing structural codes (`EXPECTED_ARRAY`, `EXPECTED_OBJECT`, `DOCUMENT_STRUCTURE_INVALID`) and
    an expression-limit overrun as `EXPRESSION_INVALID`, as it does for bindings; `RULE_LIMIT` is the
    profile-construction code. The `ADMISSION_RULE_*` codes are receipt codes and live in the
    receipt-code table, not in `BindingDiagnostic.CODES`. The ADR's Phase 3 list now says so.
20. **Phase 3 node gate and recipe location.** The ADR asked for a single-node devnet. The
    §6.1 and §6.2 recipes instead run on the existing three-node N2N harness (`BindingRecipesIT`),
    which is strictly stronger: it also checks offline receipt-byte parity for every finalized
    block, restarts all members, and replays one from genesis. Studio's Node tests load every
    `examples/bindings/*.yaml` through its draft model, which learns rules only in Phase 5, so the
    two recipes live in `tooling/devtools/src/integrationTest/resources/admission-recipes/`
    until Phase 5 moves them to `examples/bindings/`. The host bounds a static-rule ingress
    rejection to `APPLICATION_REJECTED` (deviation 1), so the harness asserts that code on the
    node and the exact workflow reason on the same catalog-built composite.
21. **Manifest attribute encoding (§5.14).** Capability-manifest entry attributes are a flat
    text map that the host stores in sorted key order, so the ADR's `admission` list is encoded as
    `admission.<componentId>.<NN>.{rule,command,deny,slot,static}` keys with a two-digit
    attachment index. Within a component the keys sort in attachment order; across components the
    order is the deterministic key order (so `a-b` sorts before `a`), not strictly by id. §5.14 now
    states the encoding.
22. **Phase 4 node gate and "wrong organization".** As in deviation 20, the §6.3 recipe runs on
    the three-node harness (with offline receipt parity, restart and replay from genesis) instead
    of a single-node devnet, and lives with the integration-test resources until Phase 5. A command
    never claims an organization; it comes from the verified actor record. The negative tests
    therefore cover an unknown and an inactive organization (both rejected by the kernel before
    any fact exists), and the recipe covers a verified organization that the rule does not allow
    (`ORGANIZATION_NOT_ALLOWED`). The ADR's Phase 4 text says so. The approval-referenced path
    (`directActorCount == 0`, `approvalCount == 1`) is proven end to end by a role-gated variant of
    the stdlib DPP qualification, since the §6.3 recipe's organization rule prevents an
    independent approval by design.
23. **Phase 5 documentation and generated copies.** `www` pages under `bindings/` are imported
    from `docs/appchain/bindings/` (AGENTS.md: `docs/` is the source of truth), so the ADR's new
    `www` page is `docs/appchain/bindings/07-admission-rules.md`, registered in the site's import
    map, sidebar and learning-path test. The Studio copy of the blueprint schema is generated from
    the devtools resource by the Studio build and is not tracked; only the devtools schema and its
    pinned digest change. The ADR's Phase 5 text says so.
24. **Phase 5 exit gate and fixtures.** The dry-run engine's byte-for-byte reproduction of the
    cluster receipts is `BindingRecipesIT`, which replays every finalized block of all three
    recipes through the same `BindingDryRun` code the CLI runs. In addition, `StudioFixturesIT`
    runs the packaged `bindings dry-run` over each recipe's public fixtures
    (`examples/bindings/fixtures/<recipe>/fixture-N.json`, chained with `--prior-result`) and
    requires the expected receipt code for every block; `BindingCliIT` checks the CLI outputs. A
    static rule refuses at fixture admission, as at a node's ingress, so the §6.1 over-limit
    fixture (`fixture-3.json`) ends in `FIXTURE_ADMISSION_REJECTED` with the full reason rather
    than a receipt. §6.3
    needs a governed context, which ships beside its fixtures; it is not a Studio starter because
    Studio's starters use the tutorial context. The CLI adds `admission` (validate) and `rules`
    and `refusal` (dry-run) only when rules exist or ran, so documents without rules produce
    byte-identical outputs. Studio's advisory checks reuse the compiler's `RULE_*` codes and add
    one local advisory code, `RULE_DENY_CODE`.
