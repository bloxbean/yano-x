Namespaces, writer policies and session keys

Every message on an app chain names a topic, such as freight/acme/shipments. On any chain the topic is a label. On a chain sealed with a topics: block, a topic registry in the chain’s state also decides who may write each topic, and every member enforces it before any state machine sees the message. Yano owns the registry, its checks and its proofs; Yano X supplies the appchain topics commands, the clients and the composite rules.

The examples on this page follow one chain: a freight consortium whose members share delivery records. The consortium owns the freight/ namespace, each member company runs its own namespace below it, and Acme’s drivers record delivery scans on freight/acme/shipments from a web app.

One topic name, used everywhere

Section titled “One topic name, used everywhere”

A chain gets a registry from its draft: add topics: to the chain (./yano.sh appchain new --topics <chain>=members, or answer the wizard), with governed membership. It is sealed into the chain’s genesis; see configure an application. Without it, topics work as before and anyone who can submit to a node may write any topic.

Names form a tree:

  • A namespace ends in / and covers every topic below it. The longest matching entry wins: freight/acme/ can override single fields of freight/, and an omitted field inherits. writers: open, an empty delegate list and schema: none are explicit overrides. Retirement is inherited, and a child cannot undo it.
  • A topic no entry covers follows the draft’s unregistered: setting. open, the default of appchain new, accepts it as before. reject refuses it with TOPIC_UNREGISTERED, and the chain then makes blocks only from registered topics. Topics starting with ~ are system topics.
  • Changes take effect later: a committed change activates after the chain’s activation lag (10 blocks by default), never retroactively, so every earlier message stays verifiable under the policy it was written under.

A write on a protected topic

Section titled “A write on a protected topic”
  • A direct write carries the policy’s threshold of writer signatures instead of a credential.
  • A credential stands in for one writer. Its issuer must be listed under delegate and belong to a 1-of-n writer set; it cannot satisfy a 2-of-n policy by itself. A change to the allowed issuers takes effect at its activation height.
  • Signatures bind the chain generation, so a credential copied to a fresh chain grants nothing. A write also binds the topic, payload hash, nonce and expiry, and the host rejects reused, revoked, expired or out-of-scope writes.
  • The machine sees the payload, not the frame. Machine hooks receive the verified payload through getBody(), while the message id, receipt and message proof follow the submitted frame. Do not strip a frame from an archived message or make up a replacement id.
CodeThe write was refused because
TOPIC_UNREGISTEREDno entry covers the topic, and the chain rejects unregistered topics

Registry commands have their own codes: TOPIC_COMMAND_INVALID, _DENIED, _EXPIRED, _STALE, _LIMIT and _SUPERSEDED.

Payload schemas

Section titled “Payload schemas”

Topic schemas use the same yano-cbor-schema-ir-v1 evaluator as authenticated-map. CDDL is compiled by CddlSchemaCompiler before submission; members only evaluate the committed IR. Put a topic schema on an opaque machine such as ordered-log. Typed kernels such as balances already define their command format and reject a second topic schema. Composite rules can read the verified payload; see admission rules.

All of these are reads. In an entry name, encode the trailing slash: /topics/entries/freight%2F. Owners’ commands are submitted as ordinary messages on ~topics/registry; members’ votes go through the privileged POST /admin/topics/governance, which topics approve calls on each operator’s own node. See the REST API.

Proofs and trust

Section titled “Proofs and trust”

An entry-state proof establishes one registry record at a root. It does not establish a topic’s effective policy: ancestors, the absence of overrides and the configuration also matter. appchain topics resolve returns a topic-policy-v1 effective-policy bundle for a candidate height, anchored to its parent state’s root. It includes the configuration revision and source entry revisions, including disabled and unregistered outcomes.

Entry-state proofs come from the generic state proof API, not a separate topic-entry-v1 typed endpoint. Studio labels them as entry-only proofs, and its downloaded peer responses are not independent verification. For authorship, appchain topics verify requires the message, frame, generation and complete effective-policy, replay, revocation and schema evidence, plus independently trusted block/root information; the how-to lists the inputs. It refuses entry-only data. A valid signature alone does not establish current authority or finality.

Preview upgrade boundary

Section titled “Preview upgrade boundary”

This implementation pins the Yano host at 0.1.0-pre19, API level 13, with its matching ordinary JVM ZIP. Qualify it on a fresh app-chain genesis. Existing retained deployments remain on their exact host, profile and genesis; this change supplies no in-place migration or reset procedure.

The old collection schema vectors keep their IR bytes and results. The merged core evaluator also hardens the work budget by charging bytes examined in literal comparisons. A pathological legacy value can therefore be rejected at that budget boundary; the regression suite records this case. This is an intentional prerelease boundary, not a claim that every historical state can be replayed under the new host. The host also adds a committed clock-skew field to its consensus profile. Keep old stores with the binary that created them.
