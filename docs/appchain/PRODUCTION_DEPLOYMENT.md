# From demonstration to production

Every recipe, showcase chain, and product in this repository ships with a launcher, demo actors,
and fixed local keys, and every one of those is a demonstration convenience. This guide says what
changes when a consortium runs an app ledger for real: how the genesis is agreed, where keys live,
what each service is allowed to reach, and which parts are still gated.

Yano is pre-release. Nothing here makes a `preview` or `EXPERIMENTAL` component production-ready on
its own; read its status first.

## The short version

| Demo | Production |
|---|---|
| Seeds derived from a public string | Keys generated by each actor, on their own machine, never transmitted |
| One process holding every seed | One signer per organization, holding only its own key |
| A fixed local API key | A per-caller key, rotated, never in a shell history or a repository |
| Loopback HTTP, no TLS | TLS on every reachable endpoint, with a reverse proxy in front |
| Members and threshold chosen by a script | Members agreed by the consortium, threshold a governance decision |
| Anchoring to a self-contained devnet | Anchoring to preprod or mainnet from a funded, protected key |
| One operator playing every role | Each organization operating its own node and signer |

## 1. Agree the genesis

The genesis fixes the collections, the schemas, the roles, the policies, and the actors with their
public keys. Its hash is the genesis id, and every authorization is signed against it, so agreeing
it is the first governance act and changing it later means a different ledger.

**Each actor generates its own key.** On the actor's own machine, never on the operator's:

```bash
PUBLIC_KEY="$(./yano.sh appchain role public-key --seed-file <seed>)"
./yano.sh appchain role key-proof --chain <chain-id> --actor <actor-id> --actor-revision 1 \
  --key <key-id> --public-key "$PUBLIC_KEY" --valid-from-height 1 --valid-until-height 0 \
  --seed-file <seed>
```

The public key and the key proof travel to the operator. The seed does not: it stays in a file
readable only by its owner, or in a key store or HSM the organization already trusts.

**The operator assembles the genesis** from the organizations, actors, public keys, key proofs,
and policies the consortium agreed: with `appchain role bootstrap` for
[role approvals](state-machines/role-approvals.md), or with `appchain bindings recipe` for a
[governed binding recipe](DECLARATIVE_BINDINGS_CLI.md#generate-governed-recipes-for-your-own-chain).

**Every participant regenerates it independently and compares the genesis id.** The generator is
deterministic: the same descriptor, members, and threshold always give the same id. A participant
who cannot reproduce the id should not join the ledger. Publish the id where members can check it.

Note what cannot be changed afterwards without a new ledger: the collections, their policies, the
actors declared at genesis, the block interval, and the message size bounds. Adding an actor later
is a governance action on the role workflow.

## 2. Members, threshold, and nodes

The member set is the list of node keys whose signatures certify a block, and the threshold is how
many must sign. Both are consortium decisions, not defaults, and every verifier must pin the same set.

Size the threshold against two separate risks. Up to `n − t` members can be offline while the ledger
keeps finalizing blocks. Dishonest members are a separate assumption: the fault bound `f`, set as
`consensus.max-byzantine-members`, is 0 by default, and the node refuses to start unless
`2t − n > f` and `t ≤ n − f`. A threshold of two of three therefore tolerates one member being down,
but not one dishonest member: it cannot be configured with `f = 1`. Tolerating one dishonest member
takes, for example, four members with a threshold of three and `f = 1`.

Each organization runs its own node, with its own storage, and its own signing key. Do not run a
"cluster" of nodes owned by one operator and call it a consortium: the threshold then proves only
that one operator signed several times. The showcase launcher does exactly that, which is why it is
a demonstration.

Node configuration is the chain entry plus its generated genesis properties, applied to every
node. The block interval and message size in the generated properties are part of the genesis
identity: a node started with different values will not agree.

Give each node its own data directory, back up its authoritative stores, `chainstate/` and
`appchain-chainstate/` (see [where data lives](../site/concepts-where-data-lives.md)), and decide a
retention policy for proofs and history before you need one. Historical answers need proof retention: a verifier asking
about height H needs the node to still hold it.

## 3. Keys and signing

This is where a demonstration differs most from a deployment.

**Do not run a shared signer in production.** A service that signs for every actor whose seed it
was started with lets whoever reaches it write as any of them. In a demo that is the point; in a
deployment it collapses the distinction the ledger is there to make. Each organization signs only
for its own actors, on its own machine, reachable only by its own operators. Hardware and
wallet-held keys are not implemented yet.

**API keys** authenticate callers to the node, and are not identities. Issue one per caller, keep
them out of shell history and repositories, and rotate them.

**Authorization lifetimes** are bounded in blocks and one-use. A signer that is offline long enough
for its authorization to expire simply retries; do not raise the lifetime to avoid that.

## 4. Network and services

Everything binds to loopback by default. That default is correct, and exposing a service is a
deliberate act:

| Service | Exposure | Notes |
|---|---|---|
| Node REST API | private to the operators and services that need it | never public; put TLS and a reverse proxy in front |
| Your application's read service | public, read only, if it serves proofs | no secret, no write route |
| A signer | private to one organization's operators | holds keys; never public, and never without TLS if it leaves the host |
| Static UIs | static files | can be public; they hold no secret beyond what the operator types |

A UI served over HTTPS cannot call a service over plain HTTP. Either serve both over HTTPS, or host
the UI behind the same reverse proxy as the service so they share an origin.

## 5. Anchoring to Cardano

The demo anchors to a devnet the cluster runs itself. In production, anchoring is what turns
"the consortium says so" into "a public chain carries it".

- Choose the network deliberately, and confirm public anchoring explicitly. Preprod for testing;
  mainnet only when the operator accepts the cost and the permanence.
- Anchoring needs a funded wallet key. Keep it in a file the launcher reads, owner-only, outside
  the data directory, and treat it as a production secret. Never pass a seed on a command line.
- Only some ledgers need anchoring. Anchor the ones whose evidence must be independently checkable
  later, and leave the rest.
- Verifiers reach the top trust level by reading the anchor datum from a Cardano source they trust
  and verifying against the block it commits to. Plan how your verifiers get that datum: a public
  resolver, a block explorer, or their own node.
- Nothing public should carry personal data. On-chain metadata and datums are permanent.

## 6. What the demo does that production must not

- Derive seeds from a public string. Every demo actor's key is computable by anyone.
- Use the known local API key, or leave one in an environment printed by a launcher.
- Run one signer holding every organization's key.
- Run all members from one operator, one host, and one directory.
- Bind services to a public interface without TLS.
- Treat a `preview` or `EXPERIMENTAL` component as a supported one.

## 7. Per-product notes

- **Evidence** publishes to object storage, IPFS, and Kafka through connectors. Give each connector
  its own credentials, and treat the effect secrets as production secrets.
- **Cardano History** answers from the L1 data its node observed. Proofs are pinned to the latest
  L1-confirmed commitment, so its chain must be anchored.
- **The eUTxO ledger** is experimental and for disposable test funds only.

## 8. Before you go live

- The genesis id is reproduced independently by every member.
- Each organization holds its own signing key, and no key is on a machine that did not generate it.
- The member set and threshold are recorded where verifiers can obtain them.
- TLS terminates in front of every reachable endpoint, and the node API is not among them.
- Anchoring, if used, has a funded key that is backed up and access-controlled.
- Retention is decided, backups are tested, and a member can be restored.
- Every verifier knows which trust level they require.
- Each component's classification and its deferred stages are written down where the operator's
  stakeholders can read them.
