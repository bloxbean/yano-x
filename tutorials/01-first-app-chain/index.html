Tutorial 1 — Your First App Ledger

To run this outcome with other operators, follow Set up an application.

  • Goal: run three members on one machine and watch them finalize the same event.
  • You’ll learn: how a submission becomes final, what members agree means, how to get a proof for a message, and what a restart keeps.
  • Before you start: an extracted Yano X JVM distribution, Java 25, curl, jq, and python3. The rehearsal picks the first free HTTP ports from 8080 and node ports from 13337, and prints them. No earlier tutorial is needed.
  • Level: beginner
  • Time: about 15 minutes for sections 1–5. The optional extras add 10–15 minutes.
  • Outcome: three members finalize the same ordered event, expose the same state root, and keep both across a restart.

This tutorial uses Yano’s self-contained Cardano devnet and the built-in ordered-log state machine. It needs no external Cardano node, wallet, funds, Kafka, or plugin.

Yano’s tooling calls an app ledger an app chain, so the commands below say appchain.

What you will see

Section titled “What you will see”

Here is the whole tutorial in one picture. Each step shows the command you run at that point. The “What if” scenarios show what happens when a member is down.

1. Choose the working directory and start

Section titled “1. Choose the working directory and start”

Every tutorial runs ./yano.sh from the directory that contains it. Choose one setup.

From an extracted release, use its top-level directory, the one containing yano.sh and yano.jar:

From a source checkout, follow the Yano X distribution build, extract the JVM archive it produces, and use that top-level directory. Yano X has no :app task. For the curated thirteen-chain demo, use the showcase quickstart instead.

The remaining commands are the same for both setups:

try runs the real setup steps on this machine and prints each command as it runs it. A coordinator creates an application called demo with one chain, orders, which uses the audit-log recipe: the ordered-log state machine. Three operators, alice, bob and carol, each make a member key and a node directory under ./appchain-try/, and the coordinator seals the application. Then each operator joins and starts their node:

  • alice is the lead. Her node produces the local Cardano devnet, is a member, and proposes every block of orders;
  • bob’s and carol’s nodes are members that follow alice’s devnet.

With three members, the threshold is a majority: 2. Startup can take a few minutes, because alice’s node starts first and the others download its devnet genesis.

✓ You should see the numbered steps, then a message finalized at the same height and root on every node:

Each node’s HTTP port is in its node.json. Read the three ports into your shell; the commands below use them:

2. Confirm agreement

Section titled “2. Confirm agreement”

✓ You should see members online 3/3, each member online, then:

members agree means every online member reports the same chain identity. If two members report different state roots at the same height, status also prints a warning that names the height. It is more than “three processes are running”, but it is a comparison, not a vote.

Open the status pages if you prefer a UI:

3. Submit a business event

Section titled “3. Submit a business event”

Submit through bob’s node rather than through the proposer:

✓ You should see a JSON object with a messageId.

You did not sign anything. Bob’s node checked the command, signed the envelope with its own member key, and gossiped it. Alice’s node put it in a block, two of the three members voted for that block, and every member applied the same bytes. The submission itself only means “queued on bob’s node”.

After a few seconds, inspect the finalized blocks and agreement:

✓ You should see a new block with "messageCount": 1 and certSignatures of at least 2, then chain orders with a higher height and members agree.

4. Capture a message ID and its proof

Section titled “4. Capture a message ID and its proof”

This time, submit through carol’s node and keep the message id:

✓ You should see a JSON object with messageId, "chainId": "orders", and "topic": "orders".

Wait until the message is final. A finalized message has a block height:

✓ You should see final at height followed by a number greater than 0.

Then request a typed proof that the message is recorded:

✓ You should see "presence": "PRESENT", "claim": true, and a position with the message’s height, index, topic, and sender.

The typed subject resolves the public message ID to its namespaced physical state key and connects that record to the member’s committed state root. The sender is carol’s member key, because carol’s node accepted and signed the envelope; jq -r .publicKey appchain-try/carol/yano-node/node.json prints it. Tutorial 7 connects a state root to a Cardano anchor.

5. Stop and restart

Section titled “5. Stop and restart”

stop keeps both the L1 and the app ledger data. Stop the three nodes, then start them again with the lead first, because the other nodes follow her devnet:

✓ You should see ✓ Stopped carol; its data is kept for each node, then ✓ Node alice is up at http://127.0.0.1:… for each node, then the same height and members agree as before the stop.

The retained heights and roots return unchanged before any new traffic is finalized. Explore what each node keeps in its directory, for example appchain-try/alice/yano-node:

  • node.json: the operator name, public key, addresses, and ports;
  • secrets/: the member key and the node’s API key;
  • apps/demo.chain: the sealed application the node joined;
  • config/: consensus.yaml and node.yaml, written by join, and local.yaml for the node’s own settings;
  • data/: chainstate (Cardano L1), appchain-chainstate (the app ledger), and appchain-indexers (rebuildable read indexes);
  • logs/node.log: the node’s log.

appchain-try/coordinator/ holds the draft, the member cards, and the sealed demo.chain. See where each setting lives.

This is a useful distinction:

  • restart: the same chain identity and retained state;
  • try --clean: delete the rehearsal; the next try seals a new application with a new identity and history.

The members and the threshold are sealed in demo.chain. To try different values, rehearse in a new directory (see Go deeper).

What you just proved

Section titled “What you just proved”
  • A submission can enter through any member, and that member signs it.
  • A threshold of members, not one REST server, finalizes the ordered block.
  • All members deterministically derive the same state root.
  • A message has a proof against that root.
  • A retained restart recovers the same application history.

You did not yet prove Cardano settlement or the truth of the order fields. Those are separate trust layers.

Optional extras

Section titled “Optional extras”

These sections reuse the running rehearsal. Skip them if you are short of time.

A. Run a small ordered-log load test

Section titled “A. Run a small ordered-log load test”

The distribution includes the showcase’s parallel load driver, examples/showcase/tools/loadtest.sh. It finds members on consecutive HTTP ports, starting at YANO_SHOWCASE_HTTP_BASE. try gives alice, bob and carol consecutive ports when they are free; check that $BOB and $CAROL are $ALICE + 1 and $ALICE + 2. Start with a bounded workload of 500 messages, 10 concurrent submitters, and payloads of about 256 bytes, all sent to alice’s node:

Plain load-test mode suits any-bytes machines such as ordered-log. It submits numbered UTF-8 bodies on the load topic, waits for the pending pool to drain, and reports two different rates:

  • SUBMIT rate measures how quickly an ingress REST API accepts messages.
  • FINALIZE rate measures how quickly messages enter threshold-certified blocks; this is the meaningful chain-throughput measurement.
  • dropped (429 pool) means backpressure worked because the pending pool filled. Reduce concurrency or tune the pool and block limits deliberately.
  • errors are non-backpressure request failures and should be investigated.

Spread submissions across all ready members to exercise gossip from every ingress path, then confirm that every member still agrees:

This is a functional throughput exercise, not a production benchmark. Results depend on the machine, the JVM, the devnet producer, the block interval, the payload size, and the member count. Record those inputs when comparing runs. The test appends real finalized messages to the retained orders history.

For capacity settings and workload boundaries, see the ordered-log reference.

B. Try an effect

Section titled “B. Try an effect”

An effect is an external action, such as a webhook call, that a state machine commits as part of a final block and an executor node carries out. Tutorial 6 runs the full emit, delivery, result, and proof lifecycle: a stock approval reaches its threshold and one node calls a local webhook receiver. It needs its own rehearsal, so finish or clean up this one first.

A production workflow should carry an explicit business id or finalized source message id in its committed command or effect payload. The proof establishes that the effect intent was committed; a real external action also depends on a trusted executor and a verifiable receipt.

C. Governed member onboarding

Section titled “C. Governed member onboarding”

The application is governed, so its members can add a fourth node, dave, on the same host. These are the same steps as in grow and change your application.

First, dave makes a key, a node directory, and a member card from the sealed file. Choose two free ports for his node; the example uses the ones after carol’s:

✓ You should see ✓ Wrote …/dave.member with dave’s key id.

Then every existing operator approves the card on their own running node. Each approve waits until enough operators have approved, so on one machine run the three in parallel:

With 2 of 3, a fourth member would leave 2 of 4, which cannot certify blocks (a threshold must be more than half the members). approve therefore raises each chain’s threshold to 3 first and waits until that is active, then adds dave and waits again, then restarts the operator’s node once to connect to him.

A change activates ten blocks after enough operators approve, and a chain makes blocks only when it has messages. --heartbeat lets approve send small heartbeat messages to an idle chain. On an ordered-log chain such as orders each heartbeat is a permanent entry on the appchain.heartbeat topic; your existing entries are unchanged. Without --heartbeat, send ordinary traffic instead.

✓ You should see orders: first raising the threshold from 2 to 3 (4 members), then ✓ orders: dave is a member and Restarting this node to connect to dave … from each operator.

When every operator has approved, dave joins and starts. join shows the application and asks you to confirm the fingerprint:

✓ You should see members online 4/4 and chain orders … members agree members 4, 3 signatures. The new member votes from the height at which the change activated.

A newly joined node accepts submissions only from that activation height on. Before then, a submission through dave’s node is refused with HTTP 503 (“not an active member at height … yet”). Check a chain’s memberActiveForNextBlock field and retry once it is true:

Clean up

Section titled “Clean up”

If you added dave, stop his node first: try --clean stops only alice, bob and carol.

try --clean stops the nodes and deletes everything under appchain-try/, including the chain identities.

Troubleshooting

Section titled “Troubleshooting”
You seeWhat it means and what to do
…/appchain-try already exists. Look around with …An earlier rehearsal is still there. Look at it with status, or remove it with ./yano.sh appchain try --clean.
The rehearsal stopped at that step (exit …)The command printed just above failed. If a node did not start, read the first error in its log, for example appchain-try/bob/yano-node/logs/node.log.
members report different state roots at height … from statusA node can be one block behind while status reads it. Run status again after a few seconds. If it persists, check that node’s log.
Port … is already in use by another program. from requestChoose other free ports for dave with --http-port and --node-port.
This node must be running; run yano.sh appchain start first from approveStart that operator’s node with start --node-dir, then run approve again.
orders: still waiting for … and exit code 3 from approveNot every operator has approved yet, or the chain has not made ten more blocks. Run the same approve again: it continues where it stopped.
