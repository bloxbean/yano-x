Tutorial 8 — Extend Yano Without Forking It

To run a plugin chain with other operators, follow Set up an application after step 6.

  • Level: Java application developer
  • Time: 30–60 minutes for a first plugin
  • Outcome: build and sign a small state-machine plugin, install the same JAR in every member’s JVM distribution, and run it on a sealed chain.

You will write a shipment machine that records the latest status of each shipment. It is deliberately small: the point is the path from scaffold to a pinned, verifiable JAR. The plugin pages explain each part in depth; this tutorial links to them instead of repeating them.

Before you start

Section titled “Before you start”

  • Java 25 and Gradle 9.1 or later, the first Gradle release that runs on Java 25 (Yano X itself builds with Gradle 9.4.1). The generated project has no Gradle wrapper; step 5 shows how to build with your own gradle or add a wrapper.

  • An extracted Yano X JVM distribution. This tutorial assumes /opt/yano-x and runs every ./yano.sh command from that directory.

  • A 32-byte publisher seed, written as 64 hexadecimal characters to a file outside any repository, for signing. For a throwaway tutorial key in an owner-only directory of your home:

  • The exact Yano host version of your distribution. Run jq -r .version yano-distribution-v1.json in the distribution’s top-level directory; step 2 uses it directly. The host and Yano X have separate versions: yano-x-distribution-v1.json holds the Yano X version.

1. Choose the smallest extension

Section titled “1. Choose the smallest extension”

A Java plugin is the last rung, not the first. Check whether configuration or declarative bindings already model your outcome:

The extension ladder describes every rung. A chain built from declarative bindings is a composite chain: create it with ./yano.sh appchain new <app> --chain flow=bindings:<file>, or with a bindings: entry in the draft, as Set up an application shows. No Java is needed for that rung.

2. Scaffold the plugin

Section titled “2. Scaffold the plugin”

The scaffold is a small Gradle project. It compiles against the host API as compileOnly, so the JAR never packages Yano API classes. It contains:

  • src/main/java/com/example/shipment/ShipmentStateMachineProvider.java, the provider, which does no business work yet;
  • its META-INF/services/org.yanoproject.api.appchain.AppStateMachineProvider entry;
  • the runtime manifest META-INF/yano/plugins/plugin-bundle.shipment.json; and
  • the product catalog META-INF/yano/appchain-component-catalog-v1.json, which declares the capability state:shipment.

The tool refuses a non-empty output directory. Other modes are composite-role, effect-executor and sink.

The generated build.gradle resolves the host API from Maven Central. If your distribution’s host version is a commit snapshot (it ends in -SNAPSHOT), add maven { url = uri('https://repo.bloxbean.org/maven/snapshots') } to its repositories block.

3. Implement the machine

Section titled “3. Implement the machine”

Replace the generated provider file with this one. A message body is the UTF-8 text <shipment-id>=<status>; the machine stores each shipment’s latest status.

Three rules matter here, and Consensus rules explains them all:

  • apply(AppBlockExecutionContext, AppStateWriter, AppEffectEmitter) is the host’s only execution entry point. It runs on every member and must give byte-identical state: no clock, randomness or I/O.
  • validate is a filter at ingress, not a security boundary. apply must still treat every message as hostile and bound its work.
  • A rejection reason is a public code: at most 32 uppercase letters or underscores.

Read Determinism rules before you add more logic. To act on an external system, emit an effect from apply and let an executor perform it after finality; see effects.

4. Test it

Section titled “4. Test it”

The scaffold has no tests yet. Add JUnit to shipment-plugin/build.gradle, using the same Yano version as its compileOnly line:

Then unit-test validate and apply, including empty, oversized and malformed bodies, in src/test/java/com/example/shipment/ShipmentTest.java:

Run it with (cd shipment-plugin && gradle test). Then climb the testing ladder: replay, hostile input, an embedded multi-member cluster, and a packaged JVM cluster. The plugin template shows unit, conformance and domain API tests for a similar machine.

5. Sign, build and validate

Section titled “5. Sign, build and validate”

Sign the exact catalog and runtime manifest, then build the JAR so it carries the signature:

The scaffold ships no Gradle wrapper, so gradle jar uses the Gradle on your PATH. To pin a version for your team instead, add a wrapper once and build with it:

plugin sign prints PLUGIN_CATALOG_SIGNED key=example-release-2026 public-key=<64 hex characters> output=…; that public key is the <64-hex-public-key> for --trust-key here and in step 6. plugin validate prints PLUGIN_CATALOG_VALID and SNAPSHOT_WRITTEN shipment-catalog.json, and yano-plugins validate prints VALID.

Pass the seed by file only, and keep it out of the repository. plugin validate verifies the signature and exports a data-only snapshot; yano-plugins validate runs the node’s structural checks. Neither runs your code. SPI and manifest explains what the signature does and does not cover.

6. Install it in every member’s distribution

Section titled “6. Install it in every member’s distribution”

Copy the exact JAR into plugins/ of the Yano X distribution of every operator, before the application is sealed. Each operator should first check the JAR they received themselves:

seal records the SHA-256 digest of every bundle in plugins/, and join and start refuse a distribution whose bundles differ. So every operator must run the identical JAR, and a missing or rebuilt JAR is caught before the node starts. seal does not read the plugin’s signed component catalog: verifying the signature is the plugin validate step above, which each operator runs.

7. Run it on a chain

Section titled “7. Run it on a chain”

A chain selects a custom machine with the custom-plugin recipe and the machine id as the stateMachine answer. To try it alone, create a one-member devnet application. It uses its own node directory and ports, so it does not clash with other tutorials:

--answer writes the machine id into the draft, which you can check:

Then make the key, seal, join, and start:

join shows the chain fingerprint and asks you to confirm it matches the one seal printed. In a script, pass --expect-fingerprint <fingerprint> instead.

✓ You should see chain shipments custom-plugin in the sealed summary, then [Live] with members online 1/1 from status.

Submit a shipment update through the node, then look it up:

✓ You should see a height of 1 or more. A body your validate refuses, such as bad, is rejected at submission with "code":"INVALID_SHIPMENT_COMMAND".

Stop the node with ./yano.sh appchain stop --node-dir shipment-node.

For members on separate machines, list every operator in --operators and follow Set up an application: every operator installs the same JAR first, and the fingerprint they compare covers its digest. Each node checks the JAR again at start-up, before your code runs; How plugins load lists those checks.

8. Change it safely later

Section titled “8. Change it safely later”

Changing what apply computes is a consensus change, not a rolling upgrade. Never roll new semantics out member by member: give the change a governed activation height, or a new machine id and namespace. Consensus rules describes the options.

A rebuilt JAR has a new digest, so each node’s start refuses it until its operator accepts it with ./yano.sh appchain join shipments.chain --node-dir shipment-node --accept-bundles. Agree the change with every operator first; the command only makes the change explicit.
