Tutorial 3 — Choose a Stock State Machine

To run this outcome with other operators, follow Set up an application.

  • Level: beginner for selection, advanced for wire integration
  • Outcome: choose the smallest built-in deterministic model that matches your application, encode its commands, and configure a chain for it.

Selecting a state machine is a consensus decision. Every member must use the same machine id and settings. For a new chain it is configuration; for an existing chain, changing it needs a governed profile activation or a new chain.

4. Choose the machine for each chain

Section titled “4. Choose the machine for each chain”

When you set up an application, each chain names a recipe: a stock state machine with the settings it needs. List the recipes and the answers each one needs:

MachineRecipe
ordered-logaudit-log
kv-registryowned-registry

A machine without a recipe of its own, such as balances, uses the custom-plugin recipe with its stateMachine answer. Read the machine’s reference page for the settings it needs.

To rehearse a choice on one machine, give try one --chain <id>=<recipe> per chain. new takes the same options for a real application:

For more than a couple of chains, or for answers and settings, write the chains in a small template and pass it with --from:

answers: fill in what a recipe asks for; --answer <chain>.<name>=<value> does the same on the command line. settings: are flat chain settings that seal fixes for every member; --setting <chain>.<key>=<value> adds one, and --without <chain> leaves a template chain out. Settings that seal derives from the draft, such as members, threshold, sequencing, and membership, are refused there. A mistyped recipe or a missing answer stops try before anything runs and leaves no rehearsal behind.

✓ You should see seal list one line per chain with its recipe and genesis, for example chain workflow approval-workflow genesis …, and the final status show every chain with members agree.

seal writes every chain setting, including the state identity (commitment profile, format fingerprint, and genesis id), into the sealed <app>.chain file, and appchain join turns it into each node’s configuration. You never edit those files by hand, and no member can run different settings. To add a chain to a live application, see grow and change.

5. Configuration is not arbitrary composition

Section titled “5. Configuration is not arbitrary composition”

Configuration selects and parameterizes semantics that already exist. It cannot safely express new component order or terminal transitions, because those change every member’s state root. Use, in order of preference:

  1. stock configuration when one machine or profile already fits;
  2. declarative bindings when stock components must react to each other’s events; see declarative bindings;
  3. a composite plugin when components need a new committed order or transition; or
  4. a custom state-machine plugin for new business state or rules.

Common mistakes

Section titled “Common mistakes”
  • Treating a REST API key as an approval identity.
  • Changing machine settings on one member only.
  • Treating 202, or a final message, as proof that state changed.
  • Putting large or secret documents in replicated command bodies.
  • Adding network, clock, DNS or random behavior inside apply().
  • Reusing a machine id after changing its deterministic behavior.
