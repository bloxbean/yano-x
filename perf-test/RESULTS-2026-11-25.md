# Yano X throughput study — Yano 0.1.0-pre22 / CCL 0.8.0-pre8 (2026-11-25)

Base: yano-x `main` at `00274933`, branch `build/yano-0.1.0-pre22`, with the fixes below applied.
Load was generated with a standalone REST load generator (fixed rate and concurrency, finalized msg/s read from
block summaries, sampled submit→block latency); the generator and profiling helpers are not part of this commit.
Benchmark application (`appchain new perf --from perf.template.yaml`): chains `orders` = audit-log
(ordered log), `registry` = owned-registry (key-value), `credits` = custom-plugin `balances`; each with
`block.interval-ms: 1000`, `block.max-messages: 5000`, `pool.max-messages: 50000`. Messages are node-signed REST
submissions spread round-robin over the ingress nodes, 128-byte payloads.

Hosts: Apple M4 Max laptop (busy, local runs) and a benchmark VM (QEMU generic CPU model — no AVX/AVX2/BMI2/ADX,
Java 25 Corretto). Cross-host links used SSH tunnels with ≈ 325 ms RTT.

## Ed25519 (CCL 0.8.0-pre8)

| verifier | M4 Max µs/verify | VM µs/verify | alloc/verify | M4 verifies/s (8 thr) |
|---|---|---|---|---|
| i2p (CCL ≤ pre7 default) | 113.8 | 300.1 | 634 KB | 66 k |
| BC `Ed25519Equation` (pre8 default) | 53.3 | 124.2 | 6 KB | 145 k |
| BC raw `Ed25519.verify` (cofactored; reference only) | 43.3 | 101.9 | 7.6 KB | 179 k |

Signing (i2p EdDSAEngine) 67 µs (M4) / 144 µs (VM). pre7 and pre8 accept the same signatures (libsodium
parity landed in pre7). VM CPU = QEMU generic model, no AVX/AVX2/BMI2/ADX.

## Bottlenecks found and fixed (yano-x)

1. Every committed-state read decoded (and re-encoded for the canonical check) the whole tip block just to get
   its state root: `MpfAuthenticatedStateBackend.snapshot` / JMT backend, `AppLedgerStore.captureCommittedState`,
   `rootMatchesHeight`. Topic write-rule checks do this per pooled message on the proposer, per REST submit and per
   inbound gossip message → O(pool × block size); 94 % of proposer time. Fix: `AppLedgerStore.committedStateRoot`
   (last-height cache; blocks are append-only after APP_FINAL).
2. Block signatures verified sequentially on the single per-chain engine thread (70 % of engine time after fix 1).
   Fix: verify a block's envelopes in parallel ahead of the ordered per-message rules (`signedEnvelopes`).
3. `BalancesStateMachine.apply` called `context.block()` (deep copy of all 5000 messages) per message → quadratic.
   Fix: take it once per block (as kv-registry, doc-trail and approvals already do). Balances 1.2k → 2.5k msg/s.
4. Correctness: consensus verification read the replaceable global `CryptoConfiguration` verifier. Pinned to
   `new EdDSASigningProvider(new BouncyCastleEd25519Verifier())` in `AppMessageSigner` and `EvidenceVerifier`.

## Results

Local M4 (busy laptop), 3 nodes, orders @1000 msg/s: baseline 0 finalized in the run (accepted 647/s) →
fix 1: 274 msg/s, 57 % delivered → fix 1+2(admission): 949 msg/s, 99.7 %, p50 2.4 s. Saturation after fixes
2–3: ~2.5 k msg/s (5000-msg blocks every 2.0 s); with parallel verification blocks every 1.0 s (~5 k msg/s burst).

VM cluster A (3 nodes, all on VM), finalized msg/s (all ~100 % delivered):

| chain | 1000 | 2000 | 3000 offered |
|---|---|---|---|
| orders | 1000 | 2034 | 2535 (p50 3.6 s) |
| registry | 983 | 1966 | 2533 (p50 2.3 s) |
| credits before fix 3 | 992 | 1212 | 1180 |
| credits after fix 3 | – | 1927 | 2456 (p50 3.6 s) |

Cluster B (2 VM + laptop over SSH tunnel, RTT ≈ 325 ms): VM-only ingress orders 1000/2000/3000 → 984/1969/2953
msg/s, p50 ≈ 0.49 s, laptop follower keeps up. Ingress spread over all 3 at 300 msg/s → 1946 of 9000 accepted
messages lost (= 1946 stale-sender-seq drops on the laptop), p90 35 s.

Cluster C (4 VM + laptop, threshold 3), VM ingress: orders 993/1986/2483, registry 2000/2354, credits 1985/2529
(at 1000/2000/3000). A repeat orders @3000 run collapsed to 201 msg/s with ~24 k accepted messages lost.

## Remaining bottlenecks (not fixed; need Yaci/Yano or design work)

- App-message gossip (Yaci N2N AppMsgSubmission, protocol 100): pull window 10 messages per round (Yano X's
  transport config leaves Yaci's default `batchSize` 10, and Yaci caps it with `MAX_UNACKNOWLEDGED = 10`),
  per-link outbound queue of 1000, O(n) `ConcurrentLinkedQueue.size()`, WARN/INFO log per message/batch.
  ≈20 msg/s per link at 325 ms RTT.
- Consensus messages share that queue with user gossip → under overload votes/timeouts are dropped and a chain
  can stall indefinitely (seen locally at height 198; views diverged; pools frozen).
- Gaps in a sender's gossip become permanent loss: once seq N is finalized, pooled seq < N is dropped as stale,
  although the origin node returned 202.
- Inbound gossip: Ed25519 verification on the Netty event loop (54 % of those threads) + relay enqueue costs.
- Each message is still Ed25519-verified ~2× per node (admission + block). A verified-envelope cache keyed by
  the exact envelope bytes would halve it.
- Fixed-delay 1 s propose tick serialises build → round → next tick; proposing on commit would pipeline.
- Restart left one chain in view changes for ~2.5 min (height 181) while load was offered.
