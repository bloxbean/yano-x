Active development Yano X is working toward its first developer preview. Until then, explore the docs to learn the ideas behind Yano X and what it makes possible. Follow on GitHub ↗

CLI reference

./yano.sh is the public CLI, shipped inside the Yano X JVM distribution. There is no separate yano-x executable. Run it from the directory that contains it. Yano’s tooling calls an app ledger an app chain, so every command lives under appchain.

The setup commands below are the one way yano.sh runs app ledger nodes: try rehearses them on one machine, and the others set up and run an application with other operators. Every other appchain command runs the offline developer tools. Read command help from the version-matched executable when an option is uncertain: the binary you run is the authority for its version.

Set up and run an application

Section titled “Set up and run an application”

These commands set up an application that several operators run together, each on their own node. try runs the same steps on one machine first. Only public files travel between operators: the draft, the member cards, and the sealed .chain file, sent by hand or carried by join links. Set up an application walks through them.

With join links, the coordinator serves the draft instead of sending files, and each operator’s request sends the card, waits for the seal and joins:

Common options:

  • try: --chain <id>=<recipe> or --chain <id>=bindings:<file> (repeatable; default one orders=audit-log chain), --answer <chain>.<name>=<value>, --from <template.yaml>, --setting <chain>.<key>=<value>, --without <chain>, --topics <chain>=members|anyone|registrars:<a>+<b> (all as for new), --dir <dir> (default appchain-try), --clean. It gives each node the first free ports from 8080 (HTTP) and 13337 (node).
  • new: --network devnet|preview|preprod|mainnet, --operators alice,bob,carol (the first is the lead), --chain <id>=<recipe> or --chain <id>=bindings:<file> (repeatable), --answer <chain>.<name>=<value> (repeatable; the wizard asks for any answer a recipe still needs), --from <template.yaml> (start from a template’s chains and defaults), --setting <chain>.<key>=<value> (repeatable; a sealed chain setting), --without <chain> (leave out one of the template’s chains), --topics <chain>=members|anyone|registrars:<a>+<b> (repeatable; protect that chain’s topics with namespaces and choose who may create a top-level namespace), --threshold majority|two-thirds|all|<n>, --membership governed|static, --sequencing fixed|rotating (default fixed: the lead proposes every block), --output <dir>, --force, --yes.
  • invite: --serve (required), --host <public-host>, --port (default 7099), --expires-hours (default 24), --seal (seal without asking once every card is in).
  • request: --name, --host <public-host>, --node-port (default 13337), --http-port (default 8080), --key <seed-file>, --output <dir>, --no-wait (with a link: send the card and return), --yes.
  • join: --expect-fingerprint <fp> (required with --yes), --listen <port>, --peer <name>=<host:port> (repeatable), --replace, --accept-bundles.
  • start: --timeout <seconds>, --foreground.
  • status: --json, --wait live --timeout <seconds>.
  • inspect: --json, --map-genesis <chain>.
  • approve: --heartbeat, --timeout <seconds>, --yes.
  • anchor: --chain <id>, --stop, --take-over, --key <wallet-seed-file> (use a funded wallet you already have), --ada <devnet-funding>, --timeout <seconds>, --yes.
  • ui: --dir <work-dir>, --port <port>, --no-open.
  • Every command that acts on a node takes --node-dir (default ./yano-node). Node-only settings go in that directory’s config/local.yaml, which join creates and never rewrites; start refuses it if it sets a sealed consensus key. The node’s API key is in secrets/api.key; it is needed only for privileged and admin endpoints, because reads and message submissions are open unless broad API authentication is enabled.

A template for --from is a draft-shaped YAML file: chains: and, optionally, threshold, membership, sequencing, and network. Each chain has an id and a recipe, and optionally capabilities, answers, settings (flat dotted keys, sealed), authenticatedMap, and bindings:

Exit codes: 0 success, 1 failure, 2 usage error, 3 not ready yet or timed out. Every command ends with a Next: line.

Topic policies

Section titled “Topic policies”

For a chain whose draft has topics:, these commands manage a namespace’s owners, writers, and payload schema, check a topic’s policy, and issue session-key credentials. See Topic policies and Topic session keys.

In a node directory (--node-dir, default ./yano-node) the commands use this node, its API key and, when the application has one chain, that chain. Elsewhere pass --peer <url>, and --chain <id> to init, resolve, delegate and doctor (plan, sign and submit read the chain from the file); --api-key-env <name> reads an API credential from the named environment variable, and --snapshot snapshot.json plans offline. --json prints the machine-readable result instead (with submit it still waits unless you add --no-wait). For an existing entry, init starts the update from the active policy, and plan and sign list every field that changes. With a node, delegate checks the scope’s policy first; offline (--generation) it cannot. Signing keys are 32-byte Ed25519 seed files, never command arguments. Plans are immutable: regenerate and sign again an expired or stale plan. No tool votes on a member’s behalf.

Configuration tools

Section titled “Configuration tools”

These commands work on configuration files directly.

config effective prints YAML by default and redacts secret values. Both resolved commands leave out environment variables and system properties unless you pass --include-environment or --include-system-properties. --metadata <descriptor|plugin.jar> adds a plugin’s configuration metadata to validate, effective, and explain.

Plugin tooling

Scaffold modes: state-machine, composite-role, effect-executor, sink. None of these commands load provider classes, run plugin code, fetch a registry, or install a JAR. See Scaffold, sign, install.

Safety rules

Section titled “Safety rules”
  • Never request, print, copy, infer, or commit secret values. Refer only to documented environment-variable or secret-provider names.
  • Never invent configuration keys, values, defaults, recipes, or compatibility claims. If a capability is unavailable in your release, it is unsupported.
  • Keep the chain fingerprint, genesis ids, resolved configuration, release, plugin-bundle, and consensus identities distinct.
  • Do not mutate a running node or call privileged runtime APIs unless that is what you intend.

These are the same rules the in-repo configure-yano-appchain agent skill follows; see Using Yano X with AI agents.
